## 0. 结论

1. **4bit 量化基本不改变路由。**
   - Mixtral：top-2 平均重合，prefill 86%、decode 90%。
   - GLM：top-8 平均重合，prefill 80%、decode 85%。
   - Hit@1 两种精度相同（差 ≤ 1.2 pt）。
   - 所以 Mac 上用 4bit 做的路由分析，可以代表 bf16。
2. **Anchor pool（历史轨迹匹配）对"提前多层预测"有实打实的帮助，但没有达到 plan 里最强的那条判据。**
   - "提前 1 层"仍然是 GATE（HOBBIT 式 gate）最好。
   - 提前 2–4 层时，"anchor 投票 + GATE"比最强基线高：
     - 短答案：2.6 / 5.8 / 6.3 pt（h=2/3/4）；
     - 长推理：1.7 / 3.1 / 4.5 pt。
   - anchor 单独用不算准（约 .62），但几乎不随提前层数衰减：h=1 到 h=8 只掉 3 pt。GATE 每层掉约 6 pt。
   - A2 的判据：
     - "h=3 时比 GATE 高 ≥ 5 pt"：成立（+5.8）；
     - "h=3 时达到 GATE 在 h=1 的水平（≈.79）"：不成立（.72）。
   - A1（覆盖率 ≥ 50%）：在相似度阈值 0.9 时覆盖 46–48%，刚好卡在线上。
   - 在这批被覆盖的 token 上，anchor 在 h=3 的 recall 是 .76–.77，GATE 在**同一批 token** 上是 .66–.67。
3. **K0：在 H200 + vLLM 上，3–4 跳检索的耗时远大于生成，不是五五开。**
   - 4 跳时检索占端到端：8B / 30B 模型 90–94%，70B 模型 71–78%。
   - 3 跳时按总量是 21–57%，但每个请求的中位数只有 3–18%。检索时间的分布极度长尾。
   - 结果是 KV prefetch / 流式 prefill 能省的上限很小：
     - 4 跳时，假设"所有路径片段的 KV 都已就绪"，首 token 延迟（TTFT）只能降 3–4%（8B / 30B）、14–18%（70B）；
     - 3 跳 70B 能降 55%，但此时检索本身只有几十毫秒。
   - **在这个设置下，真正的瓶颈是检索本身。** KV prefetch 要成立，需要 prefill 更重的场景：大模型、长上下文、批量服务、端侧设备。详见 §4.5。
4. **跨请求的片段复用（K-H2 预览）：CWQ 高，WebQSP 低。**
   - CWQ 全测试集、不限池容量：三元组 59–63%，路径 35–52%。
   - WebQSP：三元组 20–25%，路径 13–17%。

## 2. bf16 和 4bit 的路由一致性

对比方法：
- 同一份 prompt（token id 完全相同），逐 (token, 层) 比较选中的 expert 集合。
- decode 只比较两边生成内容相同的前缀部分。
- bf16 是 H200 上 HF transformers 批量跑的；4bit 是 Mac 上 MLX 一条一条跑的。
- Mixtral 的 MLX prompt 开头少一个 BOS，对齐时错开一位。

| 模型 / 数据集 | top-k 完全相同（prefill） | 平均重合（prefill） | 平均重合（decode） | 前 / 中 / 后三分之一层（prefill） | 答案字符串相同 | Hit@1 bf16 / 4bit |
|---|---|---|---|---|---|---|
| Mixtral-8x22B / CWQ | 73.7% | 85.5% | 90.0% | 88 / 85 / 86% | 72% | .468 / .472 |
| Mixtral-8x22B / WebQSP | 74.5% | 86.0% | 89.9% | 88 / 86 / 87% | 80% | .760 / .768 |
| GLM-4.5-Air / CWQ | 22.3% | 79.7% | 85.5% | 86 / 79 / 78% | 76% | .442 / .442 |
| GLM-4.5-Air / WebQSP | 24.4% | 81.2% | 84.1% | 87 / 81 / 81% | 80% | .736 / .748 |

解读：
- 不一致主要是"排名靠后、分数接近的那一两个 expert 换了"。
- GLM 是 top-8，集合完全一致的概率自然低，但 8 个里平均对上 6.4–6.8 个。
- 越深的层不一致越多，这是量化误差逐层累积的结果。
- 结论：Mac 上用 4bit 得出的缓存命中、预测准确率等**相对**结论可以沿用。绝对数值可能有几个点的偏差。

## 3. Anchor pool：P1 采集 + P2 离线比较

### 3.1 设置

- **任务**：decode 时，在第 l 层（l 只算 MoE 层，GLM 共 45 层）预测第 l+h 层的 top-8 expert。指标是 recall@8：预测的 8 个里猜中几个，除以 8。每个 (token, l) 等权。
- **池子**：
  - W1 测试时，池子是 Wtrain 的全部 decode token（11,205 个）。
  - W2c 测试时，池子是 Wtrain 加上 W2c 中**其他**请求的 decode token（共 21.4 万；同一请求自己的记录排除在外）。W2c 随机抽 2 万个 token 评估。
- **方法**：

| 名称 | 做法 |
|---|---|
| TOKID | 这个 token id 在池子里第 l+h 层最常用的 expert |
| GATE | HOBBIT 式：把第 l 层 MoE 的输入送进第 l+h 层的 gate（推理时当场算；第一轮采 h ≤ 4，第二轮补到 h ≤ 8） |
| TOK+GATE | TOKID 频率 + 0.5 ×［在 GATE 集合中］。**和 AV+GATE 输入相同、只差"在池子里找相似记录"这一步**，是最公平的对照 |
| A1-sim | 池子里最相似的 1 条记录在第 l+h 层用的 expert |
| AV-sim | 最相似的 8 条，按相似度加权投票 |
| AV+GATE-sim | 投票比例 + 0.5 ×［在 GATE 集合中］ |

- **相似度**（比较的都是第 l 层的状态）：
  - route-w：最近 w 层选中的 expert 集合的重合度；
  - logit：第 l 层 router 打分的中心化余弦；
  - proj：64 维随机投影的余弦。
- **检索范围**：
  - `-tok`：只在同一个 token id 的记录里找；
  - `-glob`：在全池里找最近邻。

### 3.2 结果（recall@8）

命名规则：`<预测方式>-<相似度>-<检索范围>`。
- 预测方式：A1 = 只用最相似的 1 条；AV = 前 8 条按相似度加权投票；AV+GATE = 投票 + 0.5 × GATE。
- 相似度：route1/2/3 = 最近 1/2/3 层选中 expert 的重合度；proj = 64 维随机投影的余弦；logit = router 打分的中心化余弦。
- 检索范围：tok = 只在同一个 token id 内找；glob = 全池找；hier = 池子里有这个 token 就在同 token 内找，没有就全池找。
- 每列最高的加粗。GATE 的 h=5–8 是第二轮重新采集补上的（`traces_v3`，`--gate_ahead 8`）。重新采集时生成的内容和第一轮完全一致，h ≤ 4 的数字也相同。

### 3.3 覆盖率和阈值（A1）

AV-logit-glob，h=3，"最高相似度 ≥ τ"才算匹配上：

| 负载 | τ | 覆盖率 | h=1 AV / GATE | h=2 | h=3 | h=4 |

| CWQ | 0.9 | 47–48% | .781 / .788 | .776 / .714 | **.773 / .663** | .769 / .617 |

- GATE 在这批 token 上的成绩，和它在全部 token 上的成绩几乎一样（h=3 时 .663 对 .660）。所以"相似度高的 token"并不是 GATE 本来就容易预测的那部分。anchor 在这批 token 上的优势是真实的：h=3 时高 10–11 pt，h=4 时高 13–15 pt。
- h=1 时 GATE 仍然更好或持平。
- 所以合理的策略是："提前 1 层用 GATE；提前 2 层以上、并且匹配上了，就用 anchor；匹配不上就退回 GATE"。目前的固定权重组合还没有按置信度和 h 来调。

### 3.3b 先限定同一个 token id，再比相似度？

plan §3.1 的设计是"按 token id 分池"。这里在同一批"token id 在池子里出现过"的 token 上（W1 占 83%），比较"只在同 token 内找"（tok）和"全池找"（glob）。h=3，用 router 打分做相似度：

| | tok | glob |
|---|---|---|
| W1 CWQ：anchor 单独 | .637 | **.661** |
| W1 CWQ：anchor + GATE | .685 | **.735** |
| W2c：anchor 单独 | .619 | **.653** |
| W2c：anchor + GATE | .693 | **.720** |

先 tok、找不到再 glob 的分层方案（hier），也不如直接 glob。

按"该 token 在池子里出现的次数"拆开（W1 CWQ，h=3，anchor 单独）：

| 出现次数 | 占测试 token | tok | glob |
|---|---|---|---|
| 0 | 17% | –（退回 GATE） | 可用 |
| 1–7 | 30% | .508 | **.556** |
| 8–63 | 26% | .682 | **.702** |
| ≥ 64 | 26% | .743 | .744 |

- 候选多时，两者一样：全池找最近邻时，本来就倾向找到同一个 token。
- 候选少时，限定同 token 只能拿不太像的记录投票。全池最近邻的相似度明显更高：top-1 平均 0.88 对 0.82。
- 越深的层，glob 的优势越大（浅层 +1.9 pt，深层 +2.6 pt）：深层的状态更多反映上下文，而不是当前 token 本身。
- 结论：router 打分里已经带了 token 的信息，额外按 token id 分池没有帮助；池子小时还有害。
- 工程上，按 token id 分池仍然可以作为**加速检索的索引**（只在出现次数多的 token 内找），但不应该作为硬性限制。
- （W2c 的分桶数字受"排除同一请求"影响：出现次数可能全来自同一请求，此时实际没有候选。所以只看总体对比。）

### 3.4 怎么理解

1. **两种信号互补。**
   - GATE 依赖"当前 hidden state 和未来几层的输入很像"，所以随 h 衰减很快，每层约 6 pt。
   - anchor 依赖"同样状态的 token，以后会走同样的路"，几乎不衰减，但起点低。
   - 两者在 h≈4 左右交叉（CWQ：AV-logit-glob .623 > GATE .613）。按趋势外推，h ≥ 5 时 anchor 单独用就会比 GATE 好，但 h ≥ 5 的 GATE 这次没有采，还需要验证。
2. **增益来自"找相似轨迹"，不是来自"知道是哪个 token"。** TOK+GATE 用了同样的信息，只少了相似度检索，在 W1 h=3 时比 AV+GATE 低 6 pt。
3. **router 打分是最好的状态描述。** logit > proj > route。全池找最近邻（glob）比只在同一 token 里找（tok）更适合和 GATE 组合，因为它对没见过的 token 也有用。
4. **池子越大，基线也越强。** 在 W2c 上池子有 21 万 token，TOK+GATE 明显变强，AV+GATE 的领先缩小到 h=3 时 +3.1、h=4 时 +4.5 pt。
5. **还缺的东西**：
   - 匹配的耗时和内存（全池 21 万 × 128 维，每层一次最近邻搜索，需要用近似搜索或缩小池子）；
   - "需要提前几层"要用 tsim 代入硬件参数才能算出来（P3）；
   - 两种信号按置信度切换或加权，目前 β 固定为 0.5。

### 4.2 生成：vLLM，batch=1

- prompt：GraphRAG-Opt 的 few-shot M0 格式，每条检索到的路径一行（最多 50 条），套 chat 模板并关掉 thinking。
- vLLM 0.11，关掉前缀缓存。
- 每个请求分三次计时：
  1. 完整 prompt，只生成 1 个 token，得到 prefill 耗时；
  2. 完整生成：贪心解码到换行或最多 64 token，减去 prefill 得到 decode 耗时；
  3. 去掉所有路径的 prompt（只剩说明和问题），只生成 1 个 token。
- 8B 和 30B 各用一张卡，70B 两张卡 TP=2。

| 模型 | 固定开销 | 每 token |
|---|---|---|
| Qwen3-8B | 5.6 ms | 23 μs |
| Qwen3-30B-A3B | 16.4 ms | 23 μs |
| Llama-3.1-70B | 12.2 ms | 137 μs |

- 中位数：每个请求检索占端到端比例的中位数。

| 模型 | 跳数 | prompt 长度 | 检索 | prefill | decode | 检索占比（总量） | 检索占比（中位数） | Hit |

### 4.3 能重叠多少

对比三种首 token 延迟（TTFT）：
- **base**：检索完，再 prefill 整个 prompt；
- **stream**：每条路径一产出就单独 prefill（GPU 空闲时，把已到达的路径打包算一次），检索结束后只 prefill 问题部分。片段拼接的代价没有算进去。
- **pool**：所有路径片段的 KV 都已经在池子里，检索结束后只 prefill 问题部分。这是任何 KV 复用 / 预取方法的上限。

| 模型 | 跳数 | TTFT base | stream | pool | pool 能省 |
|---|---|---|---|---|---|
| Qwen3-8B | 3 | 107 | 112 | 85 | 21% |
| Qwen3-8B | 4 | 1,273 | 1,262 | 1,238 | 3% |
| Qwen3-30B-A3B | 4 | 1,283 | 1,288 | 1,248 | 3% |
| Llama-3.1-70B | 3 | 237 | 247 | 106 | **55%** |
| Llama-3.1-70B | 4 | 1,465 | 1,404 | 1,259 | 14% |

（时间单位均为 ms，CWQ。）

- **stream 在 3 跳及以下反而更慢**：每条路径单独 prefill 都要付一次固定开销（5–16 ms），而路径要等很久才陆续到。
- **4 跳时 GPU 有足够的空闲**：检索时间 / prefill 时间的中位数是 6–8（8B / 30B）、1.4（70B）。可是 prefill 本身只占端到端的 3–15%，所以最多也只能省这么多。
- 对照 K-H1 的两条判据：
  - "检索占 30–70%"：只有 70B 4 跳（71–78%）和 8B / 30B 3 跳（按总量 48–57%）大致满足；按中位数看都不满足。
  - "检索期间 GPU 空闲 ≥ prefill 的 50%"：4 跳满足，3 跳不满足（中位数 0.1–0.5）。

### 4.4 片段复用（K1 预览）

- 全测试集，按 shuffle 后的随机顺序到达，池子容量不限。
- 统计每个请求的片段中，"之前的请求已经出现过"的比例。

| 数据集 | 跳数 | 路径 | 三元组 | "实体–关系"行 | 每个请求的三元组数 |
|---|---|---|---|---|---|
| CWQ | 2 | 52% | 62% | 65% | 11 |
| CWQ | 3 | 42% | 63% | 65% | 47 |
| CWQ | 4 | 35% | 59% | 63% | 59 |
| WebQSP | 2 | 17% | 20% | 23% | 22 |
| WebQSP | 3 | 14% | 25% | 29% | 53 |
| WebQSP | 4 | 13% | 25% | 29% | 69 |

- CWQ 的问题是从 WebQSP 改写组合来的，很多问题围绕同一批主题实体，所以复用率高。
- K-H2（≥ 30%）在 CWQ 上成立，在 WebQSP 上不成立。
- 这是容量不限的上限；有限容量下的命中率要在 K1 里再测。

### 4.5 这对 KV prefetch 方向意味着什么

1. **在"H200 + vLLM + 8B 到 70B + 短答案"这个设置下，检索和生成不是五五开。**
   - 4 跳时检索压倒一切，3 跳以下检索又可以忽略。
   - proposal 的 53.6% 应该是生成侧更慢的设置（比如 HF generate）。我们用 vLLM，生成快了很多，检索占比就被推到 80–94%。
2. **KV prefetch / 流式 prefill 的收益上限 = prefill 占端到端的比例。** 这个比例在 4 跳时只有 3–15%。所以在服务器上，**先优化检索本身更划算**（GraphRAG-Opt 的 JbiDFS、剪枝、GPU 图遍历），KV 复用排在后面。
3. **KV prefetch 可能真正有价值的场景**（需要在 K0 里补测）：
   - **端侧**（Mac）：8B 的 prefill 大约慢一个数量级，1,600 token 估计要几百毫秒到 1 秒以上，和检索在同一量级；
   - **大模型或 MoE offload**：prefill 本身很重；
   - **批量服务**：prefill 争抢 GPU，排队时间算进 TTFT；
   - **更长的上下文**：路径上限从 50 提高到几百条，或者 S-B 这种文档型的 HippoRAG 场景。
4. **流式逐条 prefill 不划算，按批打包或依靠池子命中更好。** 每条路径的固定开销太高；pool 的上限比 stream 高得多。所以方向应该是"跨请求复用 + 提前预取"，而不是"边检索边逐条算"。这和 CWQ 上 60% 的三元组复用率是吻合的。

## 6. 下一步建议

**Anchor**
1. P3：把 AV+GATE（按置信度切换）的提前 h 层预取接进 tsim，算出"decode 停顿 vs h"，回答 A3（停顿能否减少 30% 以上）。
2. 补采 h = 5–8 的 GATE，验证 h ≥ 5 时 anchor 单独用比 GATE 好。
3. 测匹配本身的开销：全池最近邻 → 每个 token 限定候选 / IVF / 降维。要求比每层计算时间少一个量级。

**KV prefetch**
1. 在 Mac 上用 MLX 测同样的 K0：8B 和 30B-A3B 的 prefill 都慢得多，看是否接近五五开。这是最可能让这个方向成立的场景。
2. 服务器上加一个批量服务的设置（比如 vLLM 在线服务，请求按 Poisson 到达），看 prefill 排队后 TTFT 的构成。
3. S-B（HippoRAG 2，MuSiQue / 2Wiki；集群上已经缓存）：文档型检索，prompt 更长。
4. 如果服务器场景仍然是检索主导，建议在 proposal 里把这个方向表述为"检索加速 + 跨请求片段 KV 复用"，而不是"和检索重叠"。
