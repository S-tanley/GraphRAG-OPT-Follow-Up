## 0. 结论

1. **"检索还没结束就开始算 KV"本身已经有人做过，但都是针对平铺的文档列表。**
   - RAGCache、HedraRAG（SOSP'25）、AquaPipe（SIGMOD'25）、Stream2LLM（MLSys'26）都会基于向量检索的中间结果推测式地 prefill。其中 Stream2LLM 已经是多用户、考虑 GPU 争用的版本。
   - "利用排队时间或空闲 GPU 给排队请求预算 KV"也有了（Shared RAG-DCache、PCR、LMCache）。
   - "文档到来前先 prefill 问题"也有了（Teola）。
   - 这些都不能再作为我们的贡献。
2. **真正的空白**（四份调研结论一致）：
   - **A. 随图遍历增量产出的路径 trie 上做 KV 预算。** 已有系统都假设结果是一个排好序、不断被修正的 top-k 列表，列表一变就重来，或者只保留公共前缀。图遍历产出的是不断长大、共享前缀的路径集合。用 trie mask（只看自己的祖先），剪枝、重排后已算好的 KV 依然有效。目前没有人做。注意：我们 10-15 的实验显示，免训练的 trie mask（M2）相对完整 prefill 掉 2–7 pt，在 M2 下做 LoRA 后才打平；GraphRAG-Opt 本身是完全独立编码（M1，掉 4–12 pt）。
   - **B. 把推测式预算当作"最低优先级、只填空闲"的工作，并量化它对其他用户的干扰。** 包括浪费比例、命中率、其他请求的 TPOT / p99。没有人报告过这些。Stream2LLM 自己显示，调度不当时 p99 会恶化到原来的 0.19 倍 [D]。
   - **C. 跨用户共享推测出来的 KV**：多个正在检索的用户走到同一批热门实体时共用。
   - **D. 端侧统一内存上，CPU 图遍历和 GPU prefill 的重叠**：没有人研究过。
3. **我们的多用户模拟给出了一个关键的量化结论：多用户下，大收益来自"跨请求复用片段 KV"，而不是"把计算提前"。**
   - 只做"边检索边预算"（P2）：首 token 延迟（TTFT）p50 降 5–15%。负载越高越小，因为 GPU 没有空闲。
   - 再加跨请求复用（P3，命中率 35%）：降 22–85%，而且越接近饱和收益越大，吞吐还能提高。例如 70B、KG 4 跳时，吞吐 3.82 → 5.32 请求/秒。
   - 这种"减少工作量 → 减少排队"的效果只在多用户下出现，单请求的工作（CacheBlend、TurboRAG）看不到。
4. **最适合的 RAG 任务**（同时满足下面几条中的大部分）：
   - 检索跑在 CPU 上，不占 GPU；
   - 结果逐步产出；
   - prefill 重（大模型、长上下文、端侧）；
   - 片段在用户间复用多。

   排序：
   - ① **KGQA 多跳路径检索**：端侧，或服务器上的大模型；
   - ② **共享语料上的企业 / 领域 RAG**：重排 + 片段 KV 复用，但这里主要是"预取已有 KV"，而不是"重叠计算"；
   - ③ **开放域 QA + CPU 大规模向量检索**；
   - ④ **多轮对话 RAG**：用户思考时间提供了更大的窗口；
   - ⑤ **多步 / agentic 检索**。

   不适合：GraphRAG global、ToG 这类 LLM 主导的检索，小语料检索，长文档 RAG，代码补全，多模态。
5. **两个必须先验证的风险**：
   - **(a) 检索时间是否只是实现慢**：我们的 Python 路径枚举 4 跳平均 1.2 s，C++ 的 PathEnum 在大图上典型查询只要毫秒级 [D]。优化后，可重叠的窗口可能只剩"路径特别多"的尾部查询。
   - **(b) 短片段 KV 拼接的准确率**：没有任何工作在不训练的情况下验证过 10–30 token 的 KG 三元组。需要用整条路径或"实体 + 一跳邻居"做单位，并利用 trie 让共享前缀精确复用。

## 1. 问题拆解

把"检索期间的 KV 工作"拆成三种机制，它们的收益来源和前提不同：

| 机制 | 做什么 | 收益上限 | 前提 |
|---|---|---|---|
| **M1 重叠计算** | 检索期间，用 GPU 空闲算力预先 prefill 已经产出的片段或候选 | 首 token 延迟最多省 min(检索时间, prefill 时间) | 检索不占 GPU；结果逐步产出或可预测；GPU 有空闲 |
| **M2 跨请求复用** | 片段 KV 存在池子里（GPU / CPU / SSD），其他请求命中就不用算 | 减少 GPU 总工作量：降延迟、提吞吐 | 片段在用户间重复出现；拼接后准确率可接受 |
| **M3 分层预取** | 检索期间，把预计会用到的片段 KV 从 CPU / SSD 提前搬到 GPU | 隐藏加载时间 | 有 M2 的池子；检索时间 ≥ 加载时间 |

已有工作覆盖了 M1 的平铺列表版本、M2 的单请求 / 批内版本，以及 M3 的排队触发版本。空白在于三者的**图遍历 + 多用户 + 端侧**组合。

## 2. 已有工作地图

### 2.1 检索期间推测式 prefill（M1，平铺列表）

| 工作 | 机制 | 单 / 多用户 | 检索类型 | 收益 | 和我们的区别 |
|---|---|---|---|---|---|
| RAGCache（TOCS'25） | IVF 分阶段；每阶段的当前 top-k 推测式 prefill，结果变了就重来；文档 KV 树 | 多（只在待 prefill 少于上限时推测；只在 0.1 请求/秒下评估过） | IVF，约 30 万文档，top-2 | TTFT 1.2–4×；推测流水单独最多 1.6× [D] | KV 依赖文档顺序；浪费的推测工作没有测量 |
| HedraRAG（SOSP'25） | 工作流 DAG（注意：它的"graph"是工作流图，不是知识图谱）；部分检索结果先生成，部分生成结果先检索 | 多（按利用率触发） | IVF4096，3800 万段 | 延迟 2.2–18.2×（数字需核对）[D] | 平铺 top-k，k 很小；仅向量检索 |
| AquaPipe（SIGMOD'25） | 磁盘 ANN 的部分结果提前返回并开始 prefill；错了就移除或重算 | 单 | DiskANN 类 | 藏住 56–99% 的检索时间 [S] | 无多用户调度 |
| **Stream2LLM（MLSys'26）** | 对流式到来的上下文 prefill：爬网时追加，ANN 时更新；内容变化时只作废最长公共前缀之后的 KV；两阶段调度 + 重算 / 换出代价模型 | **多**（vLLM，显式处理 GPU 争用） | 网页爬取、DiskANN | 中位 TTFT 3.9–11×；p95 2.5× [D] | **最接近的竞争者。** 前缀语义：前面任何变化都会让后面全部作废，超过 10% 的 ANN 请求要作废 1 万以上 token [D]；没有"低优先级只填空闲"的概念；只测 prefill |
| GLM / Graph-CoT 服务（arXiv 2511.01633） | 以一跳"顶点块"为单位检索，便于前缀复用；**图检索和 decode 流水** | 多 | 图（Graph-CoT） | 延迟最多 −90%，吞吐 15× [D] | **图 RAG 方向最接近。** 重叠的是检索和 decode，不是检索期间的路径 KV 预算；没有 trie 结构的路径 KV |

### 2.2 利用排队 / 空闲预算或预取 KV（M1 / M3，检索完成后）

- **Shared RAG-DCache**：给等待超过阈值的请求检索 top-k，并在空闲 GPU / CPU 上预算 KV；跨实例共享磁盘 KV。数字前后不一致 [D]。
- **PCR**：根据等待队列从 SSD 预取到内存，逐层搬到 GPU；TTFT 最多 2.47× [D]。
- **LMCache**：给排队请求异步预取。
- **Cache-Craft**（SIGMOD'25）：请求排队时就开始预加载 [D]。

它们的预取都在**检索完成之后**，由调度队列触发。

### 2.3 其他相关

- **Teola**：文档到来前先 prefill 指令和问题（我们 K0 里的"question 提前"）[D]。
- **InferCept**：调用工具期间，用空闲算力分块重算**已知**上下文的 KV。这是"填空闲"的机制模板 [S]。
- **KVFlow / CacheScout / PBKV**：按 agent 工作流预测，预取固定提示的 KV [D]。
- **SPAgent**：按负载计算收益来决定是否接纳推测动作。这是接纳策略的模板 [D]。

### 2.4 片段 KV 复用的准确率（M2 的前提）

| 方法 | 单位 | 位置处理 / 修补 | 是否需要训练 | 准确率 |
|---|---|---|---|---|
| CacheBlend（EuroSys'25） | 512-token 片段 | RoPE 重新旋转 + 重算约 15% token | 否 | 自己的评测接近无损；**独立复现在 2Wiki / MuSiQue / RULER 上低 7–18%** [D] |
| EPIC（ICML'25） | 文档 / 512-token 片段 | 重算每段开头 k ≤ 32 个 token | 否 | 降 0–7% [D] |
| TurboRAG / Block-Attention / KVLink | 文档 | 独立编码 + 微调 | **是** | 微调后接近完整 prefill；不微调时 Block-Attention 平均 67.9 → 48.0 [D] |
| APE（ICLR'25） | 上下文 | 共享位置区间 + 共享前缀 + 温度 | 否 | RAG 上达到 98% [D] |
| **ProphetKV / FusionRAG（SIGMOD'26）** | 片段 | **按问题选 15–20% token 重算** | 否 | 96–101% / 约 99%；比不看问题的选法好 8–50 pt [D] |
| SubGCache（AAAI'26） | 一组查询的代表子图 | 普通前缀 | 否 | 基本不掉；TTFT 最多 6.68× [D] |
| DepCache（SIGMOD'26） | 关系路径 | "依赖注意力" | 不明 | "不掉" [S] |

对 KG 场景的启示：
- **短片段是高风险区**：没有工作在不训练的情况下验证过 10–30 token 的三元组。每段从位置 0 开始会形成虚假的注意力汇聚，而 EPIC 式"重算开头 32 个 token"对 20 token 的三元组等于全重算。
- 建议：
  - 用整条路径或"实体 + 一跳邻居"（≥ 100 token）做单位；GLM 的 Graph-CoT 服务也因此改用顶点块 [D]；
  - **共享前缀的路径精确复用前缀 KV**，只在分叉点独立，这正好是 trie 结构；
  - 用共享前缀或哑 token 消除汇聚。
- **question 在前与预算 KV 有冲突**：完整注意力下 question 在前能提高 1–11 pt [D]，但前提是文档 KV 看得到问题，预先算好的 KV 看不到。建议的格式：
  - [系统 + 问题]（提前 prefill）→ 拼接的路径 KV → 末尾重复问题（检索后 prefill）；
  - 提前算好的问题 query 向量还能用来在检索期间就选好要重算的 token（ProphetKV / FusionRAG 式）。

## 4. 我们的多用户模拟

### 4.1 设置

脚本 `experiments/kv_prefetch/mu_sim.py`，结果在 `outputs/kv_prefetch/mu/`。

- **请求**：按泊松过程到达，每个场景 800–2000 个请求，丢弃前 10% 作为预热。
- **检索**：W 个 CPU 工作线程。KG 场景使用实测的每题检索时间和每条路径的产出时刻；文本场景使用实测的编码 / 搜索 / 重排时间。重排在同一块 GPU 上时，按 GPU 工作计入。
- **GPU**：连续批处理。每轮迭代时间 = 基础开销 + 每 prefill token 成本 × token 数 + 每 decode 序列成本 × 序列数。每轮先 decode，再处理检索已结束请求的 prefill（每轮 token 上限内分块），剩下的预算再做低优先级预算（每轮最多 512 token）。参数标定：
  - H200 8B：4.5 ms + 23 µs/token；
  - H200 70B（双卡）：20 ms + 137 µs/token；
  - Mac 8B-4bit：8 ms + 340 µs/token；
  - Mac 30B-A3B-4bit：6 ms + 230 µs/token。
- **四种策略**：
  - P0：检索完整段 prefill；
  - P1：前缀 + 问题在请求到达时就低优先级 prefill；
  - P2：再加上片段一产出就低优先级预算，检索结束后只剩末尾、没算完的片段，以及已算片段的 15% 重算；
  - P3：P2 + 跨请求片段池，命中率 h，命中的片段不用算。
- **场景**：KG 4 跳（CWQ + WebQSP，cap 50，平均 1689 token）在服务器 8B / 70B 和 Mac 8B / 30B-A3B；文本"稠密 + 重排"（重排和 LLM 同卡、或在独立设备）；维基 2100 万段 CPU IVF nprobe 128。

### 4.2 结果

下表列首 token 延迟 p50，括号里是相对 P0 的变化。

| 场景 | 负载（请求/秒） | GPU 利用率（P0） | P0 | P2：边检索边预算 | P3：+ 复用（h=35%） |
|---|---|---|---|---|---|
| KG 服务器 8B | 2 / 6 / 10 / 12 | 14 / 39 / 57 / 64% | 424 / 441 / 451 / 499 ms | −5 / −6 / −5 / −6% | −8 / −7 / −9 / −11% |
| **KG 服务器 70B** | 1 / 3 / 5 / 6.5 | 35 / 78 / 99 / 100% | 0.74 / 1.28 / **12.1 / 34.2 s** | −8 / −10 / −2 / −1% | −22 / **−43 / −85 / −82%** |
| KG Mac 8B | 0.3 / 0.6 / 0.9 / 1.2 / 1.4 | 19 / 37 / 54 / 71 / 81% | 0.95 / 1.07 / 1.22 / 1.62 / 2.10 s | −12 / −13 / −9 / −12 / −5% | **−35 / −37 / −39 / −48 / −55%** |
| KG Mac 30B-A3B | 0.5 / 1.0 / 1.5 / 2.0 | 21 / 41 / 61 / 79% | 0.73 / 0.80 / 1.01 / 1.48 s | −15 / −12 / −12 / −14% | −37 / −36 / −42 / −52% |

**吞吐**：70B KG 在 5 / 6.5 请求/秒时，实际完成量从 P0 的 3.89 / 3.82 提高到 P3 的 4.27 / 5.32 请求/秒（+10% / +39%）。

|---|---|---|---|
| 0（等于 P2） | −10% | −2% | −12% |
| 15%（≈ WebQSP 路径级） | −31% | −56% | −30% |
| 35%（≈ CWQ 路径级） | −43% | −85% | −48% |
| 60%（≈ CWQ 三元组级） | −58% | −94% | −64% |

### 4.3 从模拟得到的认识

1. **单用户上限在多用户下打了折扣。** 端侧 KG 单用户的上限是 −47% 到 −52%，多用户 P2 只有 −5% 到 −15%。原因：
   - 路径大多在检索后半段才产出（检索进行到一半时只出了 37–39% 的路径）；
   - 端侧把全部路径预算一遍本身就要约 0.5 s 的 GPU 时间；
   - 负载一高，GPU 就没有空闲。
2. **复用的收益随负载增加，而重叠的收益随负载减少。** 两者互补：低负载时重叠有用，高负载时复用决定成败。
3. **p99 几乎不变**：p99 由检索的尾部（路径特别多的查询，几秒到十几秒）决定。要改善尾延迟，需要限制或排序路径（只预算得分高的），或者优化检索本身。
4. **在服务器文本 RAG 上，推测式预算会造成伤害。** 预算稠密检索的前 10 个候选，只覆盖最终 top-5 的约 55%，多出来的工作会挤占正常请求。这和 Stream2LLM 的观察一致：不当的流式 prefill 会让 p99 恶化。
5. **模拟的局限**：
   - 复用命中按独立概率抽样，没有建模池容量、换出和 KV 加载时间（服务器 DRAM → GPU 很快；Mac 是统一内存，不需要搬运）；
   - 没有建模拼接的准确率；
   - GPU 成本模型是线性近似；
   - 检索线程数是假设的（服务器 16、Mac 8）。

## 5. 什么样的 RAG 任务适合

### 5.1 判据

| 判据 | 为什么重要 | 量化标准（建议） |
|---|---|---|
| ① 检索不占用 LLM 的 GPU | 否则没有空闲可用（重排同卡时 P2 = 0） | CPU 图遍历、CPU ANN、远程搜索 API |
| ② 检索时间和 prefill 时间同一量级 | 收益上限 = min(两者) | 0.3 ≤ 检索 / prefill ≤ 3 |
| ③ 结果逐步产出或可预测 | 一次性返回就没有东西可提前算 | 图遍历、分阶段 IVF、多步检索；或者重排前的候选集 |
| ④ prefill 占生成时间的大头 | 短输出时 TTFT ≈ 端到端 | 端侧、大模型、长上下文、短答案 |
| ⑤ 片段跨用户复用 | 多用户下的主要收益来源 | 路径 / 片段命中率 ≥ 15% |
| ⑥ 片段足够长，或有共享前缀 | 拼接的准确率 | ≥ 100 token，或者以 trie 组织 |

### 5.2 排序

| 排名 | 任务 / 设置 | 满足的判据 | 证据 | 主要机制 |
|---|---|---|---|---|
| 1 | **KGQA 多跳路径检索，端侧（Mac）** | ①②③④⑤⑥ | 检索 0.45 s 对 prefill 0.4–0.6 s，检索占 39–57% [我们]；CWQ 三元组复用约 60% [我们]；多用户 P3 降 35–55% [我们] | M1 + M2，统一内存不需要搬运 |
| 2 | **KGQA 多跳路径检索，服务器大模型（70B）** | ①③④⑤⑥（②部分满足） | 4 跳 prefill 235 ms 对检索 1.2 s；接近饱和时 P3 让 TTFT 降 82–85%，吞吐 +10% 到 +39% [我们] | 以 M2 为主，M1 为辅 |
| 3 | **共享语料的企业 / 领域 RAG（重排在独立设备或 CPU）** | ①②④⑤（③：候选集） | 片段复用非常集中，94% 跨用户 [D]；RAGPulse 90% 的引用命中已出现过的段落 [D]；prefill 占推理 55–77% [D] | 以 M3 为主：重排期间把候选的已有 KV 从 CPU 搬上来，而不是重新算 |
| 4 | 开放域 QA + CPU 大规模 IVF / 磁盘 ANN | ①②③④ | 检索占 TTFT 35–47% [D]，占端到端 36–72% [我们]；但已有 RAGCache、AquaPipe、Stream2LLM | M1，与已有工作重叠最多 |
| 5 | 多轮对话 RAG | ①④⑤（轮间窗口） | 轮间约 40% 文档重叠 [D]；用户思考时间远长于检索 | M2 + M3，在两轮之间预取 |
| 6 | 多步 / agentic 检索（本地索引） | ①③ | 每题 2.7–6.5 次检索 [D]；每跳增量 prefill 小 | 主要价值在不让 KV 被换出（SearchAgent-X 已做） |

**不适合**：
- **GraphRAG global / map-reduce**：检索本身就是几百次 LLM 调用。
- **LLM 主导的图探索（ToG、KGP、RoG 规划）**：检索时间 8–90 s 都在 LLM 调用上。
- **小语料稠密检索**：8 ms，没有可藏的。
- **长文档 RAG**：检索 < 1%，内容是每个用户自己的。
- **代码补全**和**多模态**：检索毫秒级，用离线预算更合适。
- **服务器上普通的短答案文本 RAG**：prefill 只有 20 ms，推测式预算反而有害 [我们]。

## 6. 定位建议

> 已有系统在**排好序的文档列表**上做推测式 prefill（RAGCache、HedraRAG、AquaPipe、Stream2LLM）。我们针对 **KG / 图检索中逐条产出、共享前缀的路径 trie**：
> - 检索期间按路径前缀增量预算 KV；
> - 用 trie / 位置无关的注意力，保证剪枝和重排后已算好的 KV 仍然有效；
> - 在多个用户之间共享遍历和路径 KV；
> - 把推测工作当作可抢占、只填空闲的最低优先级工作，并报告它对其他用户的干扰。
>
> 在端侧（统一内存）和服务器大模型两个设置下评估。

和 GraphRAG-Opt 的关系：
- trie mask（M2，我们 10-15 的 follow-up，不是 GraphRAG-Opt 本身的做法）是"让路径 KV 在剪枝后依然可用"的前提；它免训练时掉 2–7 pt，LoRA 后打平。GraphRAG-Opt 本身是完全独立编码（M1）；
- GraphRAG-Opt 已有"同一实体对只搜一次"的批内去重，可以扩展成跨用户、流式的共享遍历：一次 DFS 产出的路径分发给所有订阅的请求。

需要和下面几项明确区分：
- **Stream2LLM**：前缀语义，平铺列表；
- **GLM Graph-CoT 服务**：检索与 decode 流水，顶点块前缀复用；
- **SubGCache**：检索后按簇共享子图 KV，不重叠。

## 7. 风险和需要先做的实验

| 风险 | 为什么 | 怎么验证 |
|---|---|---|
| **检索时间可能主要来自实现** | PathEnum（C++）在 10^6–10^7 条边的图上典型查询只要毫秒级，第一批 1000 条路径在 1 s 以内 [D]。我们的 Python BFS 4 跳平均 1.2 s，可能主要是实现开销 | 统计每秒产出的路径数和第一条路径的时间；换一个 C++ / 剪枝过的枚举器重测。如果只剩尾部查询慢，定位要改成"尾部查询 + 路径数上限 + 按得分流式产出" |
| **短路径 KV 拼接的准确率** | 没有不训练就验证过 10–30 token 单位的工作 | K2：路径 / 顶点块单位 + trie 前缀精确复用 + 按问题选 15–30% 重算；在 CWQ / WebQSP 上对比完整 prefill |
| **question 在前与预算 KV 的冲突** | 预算的 KV 看不到问题 | 比较 "[问题] → 路径 KV → [重复问题]" 与完整 prefill |
| **推测浪费和干扰** | Stream2LLM 显示调度不当会让 p99 恶化 | 在真实 vLLM 或 MLX 原型上扫负载，报告浪费比例和其他请求的 TPOT / p99 |
| **复用率依赖数据** | 开放域 wiki 只有 0–7%；KG 和企业语料高 | 用 RAGPulse 真实日志评估企业场景；KG 用 CWQ / WebQSP 并按主题实体排序到达 |

**建议的下一步顺序**：
1. **检索实现的诊断**：路径产出速度、第一条路径的时间，以及 C++ 枚举器的对照。约 1 天，决定定位是否成立。
2. **K2 准确率**：路径 / 顶点块 KV 拼接，加 trie 前缀复用和按问题选重算，在 CWQ / WebQSP 上测。约 2–3 天。
3. **端侧原型**（Mac，MLX）：CPU 路径枚举线程 + GPU 增量预算 + 路径 KV 池，多个本地并发请求，实测 TTFT 和干扰。
4. **服务器原型**：在 vLLM 上加一个低优先级的预算队列（参考 InferCept 的填空闲机制），用 70B 测 KG 的负载曲线。
