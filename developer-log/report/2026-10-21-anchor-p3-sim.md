## 0. 结论

1. **anchor + GATE 的预取在 12 个设置里有 11 个比最强基线好，但幅度不大。**
   - "最强基线"取四者中最好的：不预取、提前 1 层、GATE 多层、TOK+GATE 加阈值。每个都在 LRU 和 MoE-Infinity 两种缓存策略里取更好的。
   - 长答案（CoT）：decode 停顿再降 3–11%，每 token 延迟（TPOT）降 1–9%。
   - 短答案：停顿降 2–8%；Mac 缓存 75% 时反而高 5%。
2. **A3 不成立。**
   - 判据：相对"提前 1 层 + MoE-Infinity 缓存"，停顿降 ≥ 30%，每 token 延迟降 ≥ 15%。
   - 实际：相对提前 1 层，停顿降 13–25%。
   - 完美预测的上限还很高：Mac 50% 缓存时 36.8 对我们的 51.4；75% 时 1.9 对 10.1。差距主要在预测精度，不在提前量。
3. **三个比"anchor 能不能用"更有价值的发现：**
   - **带宽受限时，猜错的预取比不预取更糟。**
     - 提前 1 层预取在 8/12 个设置里比不预取还慢（H200 50%：37.3 对 31.4）。
     - 猜错的约占 25–30%，它们既占带宽，又挤掉有用的 expert。
   - **按置信度只取有把握的 expert，是最大的一块收益。**
     - 不只 anchor，TOK+GATE 加上阈值后也能超过所有固定取 8 个的方法。
     - anchor 投票的概率更准，在这之上又多降 4–11%。
     - 最优阈值随带宽压力变化：缓存越小，阈值越高。
   - **对同一层的预测要前后稳定。**
     - 提前 1 层时换成 GATE（单看 recall 略高）反而更慢，因为前面几层按 anchor 发出的加载白费了。
     - 一次预取 16 个也会更慢。
4. **长 decode 时，LRU 比 MoE-Infinity 式缓存更好**（Mac 25%：156 对 168）。在 CoT 上，最优组合大多是"LRU + anchor 预取"。

## 1. 做了什么

### 1.1 补采 GATE h=5–8

- GLM-4.5-Air bf16，`--gate_ahead 8`，重新采 W1 CWQ（500 题）和 W2c CoT（200 题），输出到 `traces_v3`。
- greedy 生成和第一轮完全一致，h ≤ 4 的数字也一致。
- 补完后的完整准确率表见上一份报告 §3.2。

### 1.2 逐 token 导出预测（`experiments/moe/anchor_dump.py`）

- 对每个 decode token、每个当前层 l、h=1..8，存下各预测器给第 l+h 层的排名前 16 个 expert 和对应分数，再加上 anchor 的置信度。
- 预测器：
  - GATE；
  - TOK+GATE；
  - AV：anchor 投票，router 打分相似度，全池搜索；
  - AVG：AV + 0.5 × GATE；
  - ORACLE：真实的 top-8。
- 池子：
  - W1 用 Wtrain（1.1 万 token）；
  - W2c 用 Wtrain 加 W2c 中其他请求（21.4 万 token），不含自己。
- 导出的预测和离线分析一致：W1 上 GATE / AVG 在 h=3 是 .660 / .720；W2c 上 GATE / AVG 在 h=6 是 .530 / .661。

### 1.3 模拟器（`experiments/moe_edge/tsim_ahead.py`）

在原 tsim 上扩展，原文件不改：
- **加载队列按截止层排序**：越早需要的越先加载。提前 1 层时，行为和原 tsim 相同。
- **新预测覆盖旧预测**：同一目标层收到新预测后，撤掉还在排队、但已不在新预测里的 expert。
- **预取保护**：预取进来、还没用到的 expert 在目标层跑完之前不会被换出。缓存里只剩这种 expert 可以换出时，新的预取直接放弃。
- **策略写法** `ah<H>:<预测器>[:m<M>][:p<阈值>]`：
  - 在第 l 层，为 l+1..l+H 层各发出前 M 个预测；
  - 加了 `:p` 时，只发分数 ≥ 阈值的那些。AVG 的分数 = 投票比例 + 0.5 ×［在 GATE 集合中］，范围 0–1.5。

## 3. 分析

### 3.1 瓶颈是带宽，不是提前量

- 以 Mac、缓存 50% 为例：
  - 每个 token 平均缺 45 个 expert，也就是每层约 1 个；
  - 读一个要 1.15 ms，而每层只算 0.73 ms。
  - 所以即使提前量无限、预测完美，每层也要等约 0.4–0.5 ms。
- 完美预测从提前 4 层增加到 8 层，停顿几乎不变（W1：24.0 → 23.4）。
- 所以对 anchor 来说，"能提前更多层"本身用处有限。真正要紧的是**预测得准、取得少**，把带宽留给真正需要的 expert。

### 3.2 猜错的预取有代价

- 固定每层预取 8 个时，被浪费的加载在 20–46% 之间：GATE 多层最高，anchor + GATE 最低。
- 在带宽受限时（缓存 25–50%，以及整个 H200 设置），这些浪费会让"提前 1 层"甚至慢于"不预取"。
- 这也解释了为什么 GATE 多层几乎没有收益：提前越多层，GATE 越不准，浪费越多。

### 3.3 按置信度预取：收益最大的一环

- 只发出分数高于阈值的预测之后，所有带分数的预测器都明显变好。
- 以 CoT、Mac、缓存 25% 为例：
  - anchor + GATE 从固定 8 个的 174.3 降到 145.7（阈值 1.1）；
  - TOK+GATE 从 176.8 降到 151.2（阈值 0.9）。
- 最优阈值和带宽压力对应：
  - 缓存 25% 时最优是 0.9–1.1，几乎只取"anchor 投票过半、并且 GATE 也选了"的 expert；
  - 缓存 75% 时最优是不加阈值，因为带宽有富余，多取有利。
- **anchor 在这里的贡献**：在同样做阈值的前提下，比 TOK+GATE 再低 4–11%。它的投票比例比"这个 token 过去的频率"更能说明下一层是否真会用到某个 expert。

### 3.4 预测要稳定

- 在 W1、Mac、缓存 50%、提前 4 层时：
  - MIX（提前 1 层用 GATE；2 层以上置信度 ≥ 0.9 时用 anchor + GATE，否则用 GATE）：42.4；
  - 全程都用 anchor + GATE：40.5。
  - 在 100 题的冒烟测试里，"只有提前 1 层换成 GATE"的版本是 46.9，对比全程 anchor + GATE 的 44.4。
- 说明对同一个目标层，前后几次预测保持一致很重要，否则排着队和已经加载的 expert 会白费。
- 一次取 16 个（recall@16 有 .88）同样更慢：100 题冒烟测试里是 64.3 对 44.4。

### 3.5 缓存策略

- 长 decode 时，LRU 优于 MoE-Infinity 式（Mac 25%：156 对 168；H200 50%：42 对 45）。原因是 decode 有很强的时间局部性：最近用过的 expert 很快会再用。
- 短答案时则相反：W1 decode 只有约 5 个 token，prefill 留下的使用频率更有用。

## 4. 局限

1. **阈值和提前层数是事后挑的**：每个设置都选了最优值，这对 anchor 和 TOK+GATE 一视同仁，但会高估实际效果。需要一个按队列拥挤程度自动调整阈值的在线策略（§5）。
2. **GATE 没有分数**：只存了 top-8 编号，没法给 GATE 单独加阈值。这对 GATE 不太公平，下次采集要把 GATE 的打分也存下来。
3. **TOK+GATE 加阈值只跑了 mi 缓存**，没有和 LRU 组合；在 CoT 上，它和 anchor 的差距可能被高估了一些。
4. **硬件参数**：Mac 的设置用的是 bf16 的路由，配 4bit 的大小和带宽。上一份报告 §2 显示两者路由重合 80–85%，量级可信，但具体数字会有偏差。
5. **没有计入匹配本身的耗时**：全池 21 万条记录做最近邻搜索，每层一次，实际实现时需要近似搜索或更小的池子。
6. **模拟器的简化**：
   - 只有单个加载通道；
   - 计算时间用带宽模型估算；
   - batch = 1；
   - CoT 只用了 50 个请求。

## 5. 下一步建议

1. **自适应阈值**（优先做）：按加载队列里待加载的数量，或者预计还要等多久，动态调阈值。目标是不靠事后挑阈值，也能拿到 §2 里的大部分收益。
2. **采集时存 GATE 的打分**，给 GATE 多层也做阈值，补上这个公平性缺口。
3. **测匹配的开销**：每层一次 128 维近似最近邻搜索（如 faiss IVF），池子缩到 1–5 万条，看准确率掉多少、每层要多少微秒。
4. 如果 1–3 之后仍然稳定领先最强基线 5–10%，再进入 P5：在 Mac 的 `offload_engine.py` 上实现原型，测真实的 TPOT。
5. 换一个角度：这次最大的收益来自"按置信度预取"，而它本身并不依赖 anchor。可以把"置信度感知的预取 + 缓存"作为主线，anchor 作为其中的一个预测器。这样定位更稳。
