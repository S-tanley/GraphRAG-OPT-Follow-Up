## 0. 结论

1. **合并模拟器 `tsim_mu.py` 完成，回归完全通过。**
   - 在真实 trace 上复现 P3（13 组）和 Q1（13 组）：P3 的最大相对误差 1.8e-10（只是浮点舍入），Q1 完全相等；加载、撤销、放弃的计数也相同。
   - 另有 11 个单元测试，其中两个在合成 trace 上和 `tsim_ahead`、`tsim_async` 逐数对比。
2. **补采的 trace 齐了。**
   - GLM 的 W1 500 题、CoT 前 72 个请求，和 v3 逐 token 相同。
   - Qwen3 采了 GSM8K test 200 题、thinking 模式 50 题（≈1,055 token / 请求）、GSM8K train 200 题。
   - GATE-h 的打分前 8 和编号的一致率 100%。
   - 校准后的 GATE 概率可以迁移：在 W1 上校准用到 CoT，ECE ≤ 0.011；Qwen3 从 train 用到 thinking 模式，ECE ≤ 0.037。
3. **P3 的公平性缺口补上以后，anchor 的额外收益几乎消失。** 这是本阶段最重要、也和预期不符的结果。
   - 设置：新硬件参数，CoT 50 个请求。
   - 给 GATE 也加上校准过的阈值后，最好的 anchor 配置比最强基线只再降停顿 0.1–4.4%（TPOT 0.1–2.2%）。P3 里是 3–11%。
   - Mac 缓存 50% 时两者完全一样（53.9 对 53.9 ms/token）。
   - 按置信度只预取有把握的 expert，仍是收益的主要来源：比"提前 1 层"降停顿 19–25%，和 P3 的 19–25% 一致。但这一块 GATE 自己就能拿到。
   - 如果不允许每个设置单独挑阈值，6 个设置共用一组配置：anchor+GATE 平均比各设置最优差 5.3%，校准后的 GATE 差 6.6%，anchor 只稳一点。
4. **C2（保护已在缓存里、被预测到的 expert）几乎没有作用。** 同一策略开、关 C2 的停顿差 ≤ 0.4%；只有完美预测在 Mac 缓存 75% 时差 1.4%。原因是 LRU 下这些 expert 本来就很少被选中换出。
5. **浪费分解：浪费主要来自"最终预测也错"，不是"早期预测被修正"。**
   - 不加阈值时（提前 1 层、GATE 多层），59–91% 的预取加载没被用到，几乎全是最终预测也错。
   - 带宽受限时（缓存 25–50%），最好的配置浪费 5–17%，其中被后来的预测撤掉的只占 0–4%。所以 plan §2.3 的冻结窗口最多只能省这一小块。
   - 缓存 75% 时，最好的配置用低阈值多取，浪费 29–49%，其中被修正的占 6–19%。这时带宽有富余，多取反而更快。
   - 按首次预测的距离分：只在提前 1 层时才被预测到的加载，浪费率最高（15–66%）；提前 8 层就有把握的最低（1–29%）。
   - "目标层执行前被换出"在所有配置里都是 0，P3 的保护是有效的。
6. **要你决定**：anchor 在 plan 里的定位，以及阶段 1.4（在线轨迹池，约 1.5 天）还做不做、做多少。见 §6。

## 1. 文献补查（0.1）

详见 `report/2026-10-21-moe-mu-related.md`，这里只列对 plan 有影响的几条：

- **常驻 + 流动分区**：最像的是 Diff-MoE（SC'25：每层分全局热门 / 短期热门 / 冷三档，面向多请求 batch；全文在付费墙后，常驻区怎么填、是否刷新没能确认）和 Mira（arXiv 2609.38090：HOT 区每隔固定 token 数做有上限的换入换出，STAGE 区放预测出的 expert）。两篇 2026 年的工作（arXiv 2608.12103、2608.07911）都说明固定不变的常驻集在负载变化或 continuous batching 下会输给按近期使用排序的方法：常驻区必须能刷新，也必须留流动区。
- **组件 1（相似性组 batch）已有几乎相同的负面结果**：arXiv 2608.07911 在 24 个会话、每步 8 个、最多等 4 步、上一 token 路由 + 贪心最小并集的设置下，miss 只降 4.6–4.8%（oracle 5.9–7.9%）。我们 A0 的数字（不同 expert 数降 9–15%，吞吐 +9–15%）比它大，但设置不同（N 更大、长 CoT）；阶段 3 要在它的设置下复现一次，正面回应。
- **组件 3（顶替）的规则 DAOP（DATE'25）已有**："两个预测 expert 都在 CPU 上时，把分数低的换成 GPU 上下一个最高分的"。新意只能放在多用户、改动预算和长推理准确率上。
- **组件 2**：FineMoE（EuroSys'26）用 gate 概率前缀按 cosine 匹配历史 iteration，是最接近 anchor 的已有工作；区别是它只取最像的一张图、固定预取距离，我们是 kNN 投票、每个 expert 有自己的置信度、看到 8 层。
- 没找到同时做"多用户 batch + offload + 顶替"的工作。
- 0.1.3 选的基线（已写进 plan §3）：Mira 式 HOT + STAGE 分层缓存（对照组件 4）、Cache-Prior 的 logit 偏置路由（对照组件 3），外加 2608.07911 设置的复现（对照组件 1）。
- 注意：其中 2026 年的几篇是没有经过同行评审的预印本，数字都是论文自报。

## 2. 合并模拟器 `tsim_mu.py`（0.2）

### 2.1 结构

- **两种运行方式**：
  - `seq`：请求一个接一个跑，每个请求先 prefill（预取窗口 2 层）再 decode，缓存跨请求保留。这就是单用户（N = B = 1），和 P3 相同。
  - `pool`：N 个流循环 decode（每个流从 trace 的随机位置开始，到尾再绕回），不含 prefill；每步选 B 个前进（fcfs / prev / oracle，和 A0 相同）。这就是 Q1 的同步多用户。
- **每步每层**：attention + 路由（整个 batch 一次）→ 对 l+1..l+H 层发出预测（batch 内取并集；新预测覆盖旧预测，撤掉不再预测的排队项）→ 本层需要的 expert 缺的按需加载（优先于预取）→ 分组矩阵乘法。一个加载通道，预取队列按截止层排序。
- **缓存** = 常驻区（ρ × C，固定集合，不参与换出；已实现 R-glob、R-layer 两种填法）+ 流动区（lru / lfu / moeinf）。
- **保护**：P3 原有的"预取进来、目标层还没跑的 expert 最后换出；只能换出这种 expert 时放弃新预取"；C2 开关：被预测到、本来就在缓存里的 expert 也受保护。
- **浪费分解**：每次预取加载记下"最早是哪个 h 的预测把它排进队列"和目标层，最后归为六类：命中目标层 / 目标层没用但之后的 token 用上 / 目标层执行前就被换出 / 早期预测被后来的预测撤掉 / 最终预测也包含它但目标层没用 / 结束时还在缓存里没用过。
- **硬件参数**（微秒）：`h200_pcie`、`mac_ssd`（Q1 用的微基准）、`h200_resident`（全部 expert 在 HBM：同样的计算时间，没有加载）；另保留 `p3_glm4bit`、`p3_h200`（P3 的带宽模型），只用于回归。

## 3. 补采 trace（0.3）

### 3.1 采集改动（0.3.1）

- `collect_traces_v2.py --gate_topm 16`：每个 decode token、每层 l、h = 1..8，存第 l+h 层 router 对第 l 层 MoE 输入的前 16 个 expert（`dec_gate_idx`）和打分（`dec_gate_score`）。
- 和 plan 的两处不同：
  - **打分存 fp32，不是 fp16。** GLM 的选择打分是 sigmoid + bias，bias 约 20；fp16 在 20 附近的精度只有 0.016，比 sigmoid 部分的差别还粗。已有的 `dec_score`（v2 / v3，fp16）有同样的问题：GLM 的 router 打分在存下来时已经被量化过，anchor 的相似度就是在这个精度上算的。
  - **前 k 个编号直接取 route 的结果**，再按打分补后 8 个。第一版直接 `topk(16)` 时，Qwen3 只有 89% 的（token，层，h）前 8 和 `dec_gate_h` 一致：Qwen3 的 router 在 bf16 里算 logit，第 8、9 名打分完全相等的占 20%，`topk(16)` 和 `topk(8)` 遇到并列时选法不同。改后一致率 100%，且打分在 16 个上单调不增（route 选中的 8 个不低于其余）。
- 每个 batch 后用 nvidia-smi 读每卡余量，低于 15 GB 就在存完这个 batch 后停下（可续跑）。

### 3.2 数据（0.3.2、0.3.3）

| 模型 / 任务 | 请求数 | decode token（平均 / 最长） | 准确率 | 和 v3 的一致性 |
|---|---|---|---|---|
| GLM-4.5-Air · W1 CWQ（batch 48） | 500 | 2,824 个（≈5.6 / 请求） | Hit .442 / F1 .390 | 500 / 500 生成相同；路由、GATE-h 编号相同 |
| GLM-4.5-Air · W2c CoT（batch 24） | 72（前 3 个完整 batch） | 73,086 个（≈1,015 / 请求） | Hit .069（CoT 打分只取 "Answer:" 后一行，和 v3 同一口径） | 72 / 72 生成相同；路由、GATE-h 编号相同（2,631 万格） |
| Qwen3-30B-A3B · GSM8K test，thinking 关 | 200 | 240 / 885 | .955 | – |
| Qwen3-30B-A3B · GSM8K test，thinking 开 | 50 | 1,055 / 2,048（3 题打到上限） | .960 | – |
| Qwen3-30B-A3B · GSM8K train，thinking 关（池子 / 校准，plan 外加） | 200 | 229 / 478 | .950 | – |

- 所有 v4 trace 的 GATE 前 8 和 `dec_gate_h` 一致率 100%，打分没有非有限值。
- GLM 用 v3 的 batch 大小（W1 48、CoT 24），CoT 跑前 72 个请求（3 个完整 batch），保证逐 token 可比。
- 过程：
  - GLM 先放在 GPU0+1（每卡 118 GiB）跑 W1，第 2 个 batch 后 GPU1 只剩 12 GB，余量检查让进程停下（已存的 96 题和 v3 完全一致）。
  - 改成等 Qwen3 让出 GPU2 后用 GPU0+1+2（每卡 75 GiB）。这个上限下 accelerate 把少量权重放到了 CPU，每个 batch 慢约 40%，但结果和 v3 逐题相同，所以没有重启。
  - Qwen3 单卡（GPU2），thinking 模式 batch 25 时余量最低 42 GB。
- Qwen3 的 thinking 关闭时 decode 只有约 240 token，真正的长推理负载是 thinking 模式那 50 题（约 1,000 token / 请求，和 GLM CoT 相当）。

### 3.3 GATE 打分的校准（0.3.4）

- `anchor_dump.py` 新增两个预测器：
  - **GATEs**：GATE-h 前 16 个 expert，按"校准后的 GATE 概率"排序，分数就是这个概率，可以像 anchor 一样加阈值；
  - **AVGs**：anchor 投票比例 + 0.5 × GATE 概率（原来的 AVG 是 + 0.5 ×［在 GATE 前 8 中］）。
- GATE 概率 = P(这个 expert 在第 l+h 层真实的 top-k 里 | h, 归一化间隔)，归一化间隔 =（它的打分 − 第 9 名的打分）/（第 1 名 − 第 16 名）。在校准集上每个 h 分 24 档统计命中率，并强制随间隔单调不减。校准集：GLM 用 W1 CWQ 500（按你的要求，校准在 W1、测试在 CoT），Qwen3 用 GSM8K train 200。
- **校准能迁移到测试负载**（预测概率分 10 档，比较平均预测值和实际命中率）：
  - GLM（W1 → CoT 50）：ECE 在 h = 1 / 2 / 4 / 8 分别为 .011 / .004 / .004 / .003，各档几乎重合；
  - Qwen3（GSM8K train → thinking 50）：ECE .019 / .025 / .031 / .037，而且偏保守：高档的实际命中率比预测高 2–8 个点，即 GATE 在长推理上比在短答案上更准。
- 新导出（v4）和 P3 用的导出（v3）在 CoT 50 个请求上，AV、AVG、GATE、TOKGATE 完全相同，所以 0.4 里旧预测器的数字可以直接和 P3 对比。

### 4.3 不事后挑阈值时（6 个设置共用一组配置）

每个预测器家族只选一组配置（淘汰策略、提前层数、阈值），在 6 个设置上都用它，看离各设置最优（所有非完美预测的配置中最好的）差多少：

| 家族 | 最好的固定配置 | 平均差距 | 最大差距 | 各设置（H200 25/50/75%，Mac 25/50/75%） | 对照：每个设置单独挑（家族内） |
|---|---|---|---|---|---|
| 不加阈值（不预取 / 提前 1 层 / GATE 多层） | lru/ah8:GATE | +20.4% | +27.3% | +23 +27 +20 +23 +19 +10% | +13.0% |
| TOK+GATE 阈值 | lru/ah8:TOKGATE p0.6 | +11.4% | +19.2% | +14 +10 +6 +12 +6 +19% | +6.5% |
| GATE 阈值（校准） | lru/ah8:GATEs p0.7 | +6.6% | +20.8% | +5 +4 +6 +3 +0 +21% | +2.2% |
| anchor+GATE | lru/ah8:AVG p0.9 | +5.3% | +24.5% | +3 +1 +2 +1 +0 +25% | +0.1% |

- anchor 对阈值确实不那么敏感。以 Mac 50% 为例，四个阈值下的停顿：
  - anchor：62.1 / 55.5 / 53.9 / 55.1；
  - GATE：63.2 / 60.1 / 53.9 / 58.0。
- 但用一组固定配置时，anchor 也只比校准后的 GATE 好约 1 个点。
- 两者在缓存 75% 时都要差 20–29%：带宽有富余时，最优阈值低得多，淘汰策略也要换成 moeinf。这正是阶段 1.2.3 自适应阈值要解决的问题。

### 4.4 C2（0.2.6 / 0.4.1）

同一策略 C2 开 / 关的停顿比（按预测器家族取中位数）：所有家族、所有设置都在 −0.0% 到 −0.4% 之间，只有完美预测在 Mac 75% 是 −1.4%。

- 原因：LRU 下，被预测到的 expert 大多刚被用过，本来就不会被选中换出；moeinf 下按请求内使用次数排序，也很少轮到它们。
- 结论：C2 不需要单独作为组件，保留开关，默认打开（代价为零）。

## 5. 局限

1. **阈值仍是事后挑的**（§4.2，和 P3 相同）；§4.3 的"固定一组配置"只是粗略的对照，自适应阈值在阶段 1.2.3 做（W1 上校准、CoT 上测）。
2. **单用户、CoT 50 个请求**；W1 和 Qwen3 的 0.4 重跑没有做（数据已备好）。
3. **GATE 概率的校准集是 W1**：用在 CoT 上没问题，但如果之后在 W1 上评估，就是在校准集上测，要换校准集。
4. **硬件模型**：Mac 的设置用 bf16 的路由配 4bit 的大小和带宽（和 P3 相同）；H200 的 attention 是非融合实现（0.17 ms / 层），融合 kernel 下计算更短、可重叠的时间更少。
5. **保护的语义沿用 P3**：后来的预测撤掉某个已读入的 expert 时，它的保护不会解除（直到目标层跑完）。从 §4.5 看，这类情况在带宽受限时 ≤ 4%，影响很小。
6. **GLM 的 router 打分在 v2 / v3 / v4 里都是 fp16 存的**（§3.1），anchor 的相似度是在这个精度上算的；GATE 打分是 fp32。两者不完全对等，但对 anchor 只会更不利。

## 6. 对后续的影响 / 需要你决定

**anchor 的定位。**
- 在单用户、层内预取这件事上，校准后的 GATE 加阈值已经拿到 anchor+GATE 几乎全部的收益：带宽受限时只差 0.1–2.2%，缓存 75% 时差 4–5%。而 GATE 没有额外开销。anchor 则需要在线轨迹池、每层一次近邻搜索，阶段 1.4 估计要 1.5 天的工程。
- 但 anchor 有一个 GATE 做不到的用途：**预测下一个 token 的路由**（阶段 3.1 的 P-anchor，给相似性组 batch 用）。GATE 只能在同一个 token 内往后看几层。

可选方向：
- **A（按原 plan）**：anchor+GATE 继续作为组件 ② 的主预测器，阶段 1.4 照做。
- **B（我建议）**：
  - 组件 ② 的主预测器改为"校准后的 GATE + 阈值"，anchor+GATE 保留为对照（导出已有，不费事）；
  - 阶段 1.4 缩小为只服务 3.1：在离线池上测 P-anchor 的下一 token recall，以及小池、近似搜索的 recall 和匹配耗时；不做在线写入、淘汰、合并的完整工程；
  - 省下的时间放在 1.2（自适应阈值，按 h 分层）和 1.3（顶替）上。
- **C**：先不定，等阶段 3.3 看多用户下预测汇总时 anchor 是否更有价值，再决定 1.4 做多少。

**决定（2026-10-21）：方案 C。** 阶段 1 的 1.1–1.3 两种预测器（校准后的 GATE、anchor+GATE）都跑；1.4 推迟到阶段 3.3 之后再定。

其余几点不需要决定，会照此推进：
- C2 默认打开，不作为单独组件（§4.4）；
- 冻结窗口（plan §2.3、1.2.2）预期收益小：被修正的浪费在带宽受限时 ≤ 4%。照做，但不指望它；
- 阈值按 h 分层值得在 1.2 里加一项（h=1 的加载最不可靠）。
