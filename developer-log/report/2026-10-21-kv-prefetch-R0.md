## 0. 结论

1. **检索窗口基本消失，走 R0.5 的第三个分支：重叠只在多用户共享 / 复用里成立。**
   - 用编译实现加距离剪枝之后，KG 4 跳检索在服务器 CPU 上平均 0.25 ms，p99 约 1 ms；在 Mac 上平均 0.1 ms。同一请求的 prefill 是 43 ms（服务器 8B）到 590 ms（Mac 8B）。
   - **四种设置、三类检索方式**："检索 ≥ prefill"的请求占比都是 **0%**（判据：Mac ≥ 30%，服务器 70B ≥ 50%）。把检索和 prefill 重叠，首 token 延迟最多能省 0.0–0.6%。
   - V-H0 不成立。
2. **K0 测到的 1.2 s 几乎全部是实现开销。** 以 CWQ 4 跳、服务器 CPU 为例：
   - RoG 的 Python BFS 平均 1314 ms；
   - 同一算法改用 C++ 是 5.7 ms（快 230 倍）；
   - 再加"到终点的距离"剪枝是 0.25 ms（再快 23 倍，合计约 5000 倍）。剪枝把展开的状态数从 18 万降到 1200。
   - 输出和原 BFS **逐条完全一致**（800 / 800 个题 × 跳数组合，包括顺序和 cap 截断）。
   - GraphRAG-Opt 的 JbiDFS 是 247 ms，比 Python BFS 快 5 倍，但比剪枝版慢约 1000 倍。
3. **不知道终点的真实检索同样是毫秒级**（结论以这两种为主）：
   - (a) 从主题实体展开 4 跳的**全部**简单路径（每题中位数 32 万条，最多 1540 万条），按问题–关系相似度保留前 50 条：服务器平均 5 ms，p99 41 ms。逐跳 beam（宽 50）约 1 ms；
   - (b) RoG 规划式检索沿规划关系落地：0.1 ms。这里不含规划 LLM 的生成时间，那部分在 GPU 上，不构成"GPU 空闲"的窗口。
4. **真正可能存在窗口的地方不在路径枚举，R0 没有测**：
   - RoG 数据集为每题附带了预先抽好的子图（≤ 2000 个节点、≤ 8000 条边）。真实系统要先从完整的 Freebase 抽子图、做实体链接，这一步可能很慢；
   - RoG 的规划 LLM 本身也要时间。
   - 两者都要另外搭环境（Freebase 存储）或用 GPU，见 §7.4，由你决定。
5. **R0.4：两处疑点都属实，但不影响论文的准确率表（Table 2）。** Table 2 用的是预计算的 RoG 规划路径，不经过 `BatchOptimizedRetrieval`。受影响的是：
   - 消融 / 调度脚本里的批检索；
   - rebuttal 里"批内去重带来加速"的说法，没有测量支撑。

   另外核实了三处和论文表述有关的问题（§6.3）：
   - Table 2 的 GraphRAG 列是直接复制 GraphRAG-R 列；
   - rebuttal 说"两列相等，实证了 JbiDFS 无损"，和代码不符；
   - JbiDFS 和 BFS 的路径集合并不相同（4 跳时还会产出有重复节点的路径）。
6. **建议**：
   - 定位转向"路径 KV 的跨请求复用 + 多用户调度"（V-H3）；
   - R2（单请求流水，V-H2）不再成立，建议取消或并入 R4；
   - R1 仍然需要做，但目的从"检索期间预算"改为"复用片段的准确率"，并按 §7.2 扫 cap；
   - R3 用优化后的检索时间重跑。

   详见 §7。

## 3. R0.2：优化版本

- **做法**：
  1. 先从所有答案实体做一次多源 BFS，得到每个节点到最近终点的距离（只需算到 hop − 1）。
  2. BFS 扩展子节点时，如果剩余跳数不够到达终点，就丢掉这个子节点。
  3. CSR 按 networkx 的 `G.adj` 顺序构建，重复边保持"后写覆盖"的语义。
- **为什么输出逐条相同**：
  - 剪枝只丢掉那些子树里不会产出路径的状态；
  - 先进先出的相对顺序不变，所以产出顺序和 cap 截断都和原 BFS 一样。
  - 这比 PathEnum 的 IDX-DFS 更严格：DFS 的产出顺序不同，cap 截断后得到的路径集合会不同。
- **加速的来源**（CWQ 4 跳，服务器）：
  - 换语言：1314 → 5.7 ms（230 倍）；
  - 换算法：5.7 → 0.25 ms（23 倍）。
  - p99 从 19.7 s 降到 1.1 ms，长尾基本消失。
- **语言和算法各占多少**（补测：只加剪枝、仍用 Python，`r0_py_prune.py`；输出和原 BFS 800 / 800 一致）。Mac CPU，平均 / p99，ms：

| | 不剪枝 | 剪枝 |
|---|---|---|
| Python，CWQ 4 跳 | 475 / 8442 | 3.0 / 20 |
| C++，CWQ 4 跳 | 1.5 / 27 | 0.09 / 0.3 |
| Python，WebQSP 4 跳 | 371 / 2967 | 4.7 / 71 |
| C++，WebQSP 4 跳 | 1.1 / 8.2 | 0.10 / 0.3 |

  只换语言和只换算法，单独都能快 80–300 倍，单独都足以让窗口消失（Mac prefill 约 550 ms）。所以 K0 的 1.2 s 不只是"Python 慢"：原 BFS 不朝终点剪枝，把 3 跳内能走到的所有简单路径都展开了一遍，这个算法问题和语言问题同样大。

## 5. R0.3：检索时间对 prefill 时间

- **prefill 的估算**：
  - 每题 prompt 长度 = 只有问题时的长度（取自 K0）+ 每条路径一行的 token 数（Qwen3 分词器）。K0 的 `prompt_len` 恰好等于这个和。
  - prefill 时间 = f0 + c × token 数，按 K0 的实测拟合（`r0_summary.py`）。

| 设置 | f0 | c（每 token） | 对 K0 实测的误差（中位数） |
|---|---|---|---|
| 服务器 8B | 5.6 ms | 23 µs | 2.4% |
| 服务器 70B | 12.2 ms | 137 µs | 1.4% |
| Mac 8B | 28.6 ms | 306 µs | 7% |
| Mac 30B-A3B | 42.0 ms | 196 µs | 9% |

- **4 跳的结果**：表中每格是"检索 ≥ prefill 的请求占比 / 重叠能省的首 token 延迟上限"。上限 = Σmin(检索, prefill) / Σ(检索 + prefill)。

| 设置（gold 4 跳 prefill 平均） | 数据集 | Python BFS（K0） | JbiDFS | C++ BFS | **C++ 剪枝** | (a) open_top | (a) open_beam | (b) RoG 规划 cap50 |
|---|---|---|---|---|---|---|---|---|
| 服务器 8B（43 / 46 ms） | CWQ / WebQSP | 68% / 2.6%；70% / 3.4% | 48%；46% | 4%；4% | **0% / 0.6%** | 0% / 8.5% | 0% / 1.7% | 0% / 0.3% |
| 服务器 70B（237 / 254 ms） | CWQ / WebQSP | **55% / 9.5%；55% / 12.2%** | 16%；18% | 2%；0% | **0% / 0.1%** | 0% / 1.7% | 0% / 0.3% | 0% / 0.1% |
| Mac 8B（544 / 591 ms） | CWQ / WebQSP | 16% / 20%；22% / 22% | 2%；8% | 0% | **0% / 0.0%** | 0% / 0.5% | 0% / 0.1% | 0% / 0.0% |
| Mac 30B-A3B（371 / 401 ms） | CWQ / WebQSP | 30% / 20%；25% / 23% | 7%；11% | 0% | **0% / 0.0%** | 0% / 0.7% | 0% / 0.1% | 0% / 0.0% |

- **V-H0 判据**（4 跳检索 ≥ prefill 的请求占比：端侧 ≥ 30%，服务器 70B ≥ 50%）：
  - 用 K0 的 Python BFS，服务器 70B（55%）满足；Mac 只有 16–30%，勉强接近；
  - **优化后全部是 0%**，包括把 4 跳全部穷举的 open_top。
- **服务器 8B 的 open_top 一栏**：上限 8.5% 看起来不小，但这是因为 8B 的 prefill 只有 56 ms，绝对值只有约 5 ms。
- **3 跳**：检索更短，结论相同。
- **分位数**：优化后检索的 p99 也只有 0.3–41 ms，远低于对应 prefill 的中位数，不存在"只剩尾部查询"的情况。

## 6. R0.4：GraphRAG-Opt `retrieval.py` 的核对

只读核对，复现脚本是 `experiments/kv_prefetch/r0_batch_check.py`：
- 直接调用原来的 `BatchOptimizedRetrieval`；
- 对照版和它的代码相同，只是每题在自己的子图上枚举，路径的拼接顺序保持一致，所以两者的差别只来自图被覆盖；
- 题目取测试集前 512 题（数据集原顺序），切成连续的批，3 跳。

### 6.1 疑点一：冗余率恒为 0（属实）

- **原因**：`retrieval.py:105-107` 的 `total_pairs` 和 `unique_pairs` 都是 `len(pair_to_graph)`，所以 `pair_redundancy_ratio` 恒为 0，`efficiency_gain` 恒为 1.0。
- **另一个统计量也没有意义**：`path_redundancy_ratio`（`:135`）是用"对数"除以"路径数"，把两种单位混在一起，实测在 0.00–0.97 之间乱跳。
- **按正确的定义**（1 − 去重后的对数 / 出现次数）：

| 批大小 | CWQ | WebQSP |
|---|---|---|
| 16 | 4.3% | 25% |
| 64 | 7.0% | 28% |
| 512 | 18.6% | 30% |

- **`main.py` 的打印也有问题**：`main.py:319-320` 把各批的统计量直接相加，所以打印出的 "Efficiency" 实际上等于批数。
- **对论文的影响：没有。** 论文的冗余数字（Fig:red，36.8%）来自 `exp_batch_redundancy.py`，算的是 (实例数 − 去重数) / 实例数（`:65-77`），公式正确，而且用的是预计算路径。`retrieve_batch` 的统计量没有出现在任何报告的数字里。

### 6.2 疑点二：`pair_to_graph` 被后面问题的子图覆盖（属实）

- **原因**：`retrieval.py:102`。批内多道题共用同一 (起点, 终点) 对时，只在**最后一道题的子图**上枚举，结果分给所有这些题。

| 数据集 | 批大小 | cap | 路径和"在自己子图上枚举"不同的题 | 路径不在自己子图里的比例 | 答案覆盖率（原 → 修正） |
|---|---|---|---|---|---|
| CWQ | 16 | 8 / 不限 | 1.4% / 2.0% | 0.2% / 0.3% | 0.764 → 0.760 |
| CWQ | 64 | 8 / 不限 | 3.9% / 5.3% | 0.8% / 0.9% | 0.764 → 0.760 |
| CWQ | 512（ablation_kgqa / hf_reuse 的用法：整个分片一批） | 8 / 不限 | **12.1% / 16.8%** | 2.2% / 3.2% | 0.770 → 0.760 |
| WebQSP | 16 / 64 / 512 | 8 / 不限 | 0% | 0% | 不变 |

- **WebQSP 没有影响**：共享同一对的题，子图完全相同。
- **CWQ 会出现"拿到别的题子图里的路径"**：0.2% 的题因此一条路径都没拿到（最后一道题的子图里没有这条路径）。
- 另外，`:117` 把每对的 `max_paths=50` 写死了。

**对论文的影响**（调用关系由子任务读代码梳理，我抽查了关键几处）：
- **Table 2（Hit / F1）不受影响**：`run_table2.py` 传的是 `--paths_dir precomputed_paths`，`table2_worker.py:89-99` 直接读预计算的 RoG 规划路径。
- **报告的消融**（`results/ablation_*.txt`）标注的都是 "RoG-plan (leak-free)"，不受影响。

## 7. R0.5：分支决定和建议

### 7.1 分支：窗口基本消失，重叠只在多用户共享 / 复用里成立

**依据**：
- 三类检索、四种设置，"检索 ≥ prefill"全部是 0%；
- 优化后检索的 p99 也远低于 prefill 的中位数，不存在"只剩尾部查询"的情况；
- K0 的窗口来自 RoG 那个 Python BFS 的实现开销。

**对定位的影响**：

| 调研报告列出的空白 | 现在的状态 |
|---|---|
| A：图遍历期间按路径 trie 增量预算 KV | 在 RoG 子图上**没有实际意义**（遍历 ≤ 1 ms） |
| B：只填空闲的推测调度 | 推测对象要改：不再是"本请求正在检索的路径"，而是"未来请求可能用到的热门路径 / 实体"（预取到 KV 池） |
| C：跨用户共享路径 KV | **成为主线** |
| D：端侧统一内存 | 仍然成立，但收益来自复用，不来自重叠 |

**和已有工作的区分会更难**，需要靠这几点：
- trie mask / LoRA-M2 让路径 KV 的复用与位置、顺序无关；
- 复用粒度是路径 / trie 前缀；
- 多用户调度。

最接近的工作变成 SubGCache（检索后按簇共享子图 KV）、KVLink、Block-Attention。

### 7.2 R1 的 cap 方案（按你的要求提出）

**背景**：
- 10-15 的实验显示，路径越多，免训练 M2 掉得越多：M2-hyb 从 cap 8 时的 −3 到 −7 扩大到 cap 30 时的 −2 到 −9。
- LoRA-M2 在 cap 30 时，相对 LoRA-M0 + M0 打平（−1.0），但相对它自己的 M0 推理在 CWQ 上 −3.4（显著）。
- 损失都集中在路径 ≥ 5 条的题。
- cap 50 时，gold 终点平均 27–43 条路径；RoG 规划 cap 50 时是 24–30 条。

**建议**：
1. **免训练条件扫 cap ∈ {8, 30, 50}**：M0 / T / M1（路线 0）/ M2-hyb（路线 2，不重算）。
   - 规模：Qwen3-8B × CWQ / WebQSP 各 500 题，3 × 4 × 2 × 500 = 1.2 万次生成。
   - 估计在一块 H200 上约 1–2 小时。
2. **所有结果同时按"该题实际拿到的路径数"分桶**：1–4 / 5–15 / 16–30 / 31–50。每桶内做配对 McNemar。
   - 原因：cap 只影响路径多的题，按 cap 平均会把差异冲淡。
   - 判据"Hit@1 下降 ≤ 1 pt"同时看全体和 ≥ 16 条路径的桶。
3. **重算比例的扫描**（路线 0 / 2）只在 cap 8 和 cap 50 两端做，省 GPU。
4. **路线 1（LoRA）只训一个 adapter**：训练时每个样本的 cap 从 {8, 30, 50} 中随机抽取，三个 cap 都评测。如果 cap 50 不打平，再补一个只用 cap 50 训练的对照。**训练要你先同意。**
5. **R2–R4 使用的 cap** 取"选定路线和同 cap 的 M0 相差 ≤ 1 pt"的最大 cap。

### 7.3 R0 对后续阶段的影响（建议，需要你确认）

| 阶段 | 建议 |
|---|---|
| R1 | **保留**，目的改为"复用片段的准确率"。R1.2.4 / R1.4.2 的"检索期间按产出顺序算、剪枝后保留多少 KV"改为"跨请求复用时能保留多少 KV"（例如 T 用前缀缓存能复用的比例；M2 能复用的节点比例，10-15 实验 4 结果三已有雏形） |
| R1 的路径来源 | R1.0.2 原定用 `retrieval_timeline.py` 的 gold 终点路径。**建议改用不泄露答案的路径**：RoG 规划路径（和 Table 2、10-15 实验相同；cap 50 的重新落地本报告已经实现），或者 (a) 的 open_beam。理由：gold 终点的每条路径都以答案结尾，阅读任务被简化，拼接造成的准确率损失可能被低估。gold 路径可以作为辅助对照 |
| R2（Mac 单请求流水，V-H2） | **建议取消**：检索 ≤ 1 ms，重叠最多省 0.0–0.6% 的首 token 延迟，V-H2（降 ≥ 30%）不可能达到。端侧原型改为直接做 R4.1（多请求 + 路径 KV 池） |
| R3（多用户模拟） | **保留，先做**。mu_sim 的检索时间要换成优化后的（gold_cpp_prune / open_beam / rog_plan）。P2（边检索边预算）的收益会接近 0，P3（复用）的收益要重新算：检索不再占首 token 延迟的大头，prefill 占比上升，复用的相对收益可能更大。R3.2"共享遍历"已经没有意义（遍历只要 0.1 ms），建议删掉，改成"共享 KV 池的预取 / 推测"（空白 B 的新形式） |
| R4 | 基线里的 Stream2LLM 式（前缀语义的流式 prefill）在 KG 上没有窗口可用，可以降为次要基线 |

### 7.4 可能存在真实窗口的地方（R0 没有测，是否要测由你决定）

1. **从完整 KG 抽子图**：
   - RoG 数据集附带的是离线抽好的小子图。真实系统要在 Freebase（约 30 亿三元组）上做实体链接和邻域查询（SPARQL / 图数据库），时间可能是几十到几百毫秒，而且在 CPU / 远程存储上进行，正好是"GPU 空闲"的窗口。
   - 要测的话，需要在集群上加载 Freebase（数百 GB，工作量约几天）。
   - 我倾向于**先不做**，除非定位还想保留"重叠"这一条。
2. **RoG 规划 LLM 的时间**：需要 GPU，而且规划期间 GPU 不空闲（见 §4）。我倾向于**不测**。
