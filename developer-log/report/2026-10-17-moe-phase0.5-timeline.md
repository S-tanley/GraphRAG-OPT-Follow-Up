# Report：MoE plan Phase 0.5，检索时间线与搬运带宽（Q0）

*Bowen · 2026-10-17 · 对应 `developer-log/plan/2026-10-16-moe-retrieval-prefetch.md` §3、Phase 0.5*

## 一句话结论

**RoG 检索的耗时几乎全部花在"规划"这一次 LLM 生成上（约 0.6 秒）；规划结束、拿到 schema 之后，只要再过约 2 毫秒，prompt 就组装好了。** 所以"拿到 schema 之后、prefill 之前先 prefetch"这个窗口实际上不存在。唯一可观的窗口是"请求到达到规划结束"这约 0.6 秒，但在这段时间里只知道问题文本。另外，prefill 本来就要用到全部 expert，这段窗口按层顺序直接开始搬就行，**不需要任何检索语义**。所以检索信号的价值不在"单请求的提前 prefetch"，要转到另外两个方向：(1) decode 阶段的预测：这时 prefill 本身就要花好几秒，有充足的时间按检索信号提前搬运；(2) 多请求并发时，对队列的前瞻。

## 4. 结论与对 plan 的影响

1. **"拿到 schema 后提前 prefetch"不可行（Q0 未过关）。** 从 schema 已知到 prompt 就绪只有约 2 毫秒，几乎什么都搬不了。
2. **约 0.6 秒的"规划窗口"有用，但用不到检索语义。** 这段时间里只知道问题文本。而 prefill 反正要用到全部 expert，最好的做法就是按层顺序直接开始搬，任何"知道有请求要来"的系统都能做到，和 GraphRAG 无关。它可以作为一个工程优化（对 Mixtral 能把 TTFT 减少约 0.6 秒，约 20%），但不能作为研究贡献。
3. **检索信号真正能起作用的地方（plan 方向调整）：**
   - **decode 阶段的预测（D 问题）**：在 offload 场景下，prefill 本身要花 2–6 秒，schema 和候选实体在 prompt 就绪时就已知，有充足的时间按它们提前搬好 decode 会用到的 expert，时间完全够用。这部分取决于 Phase 2 测出的预测准确率（Q2、Q3）。
   - **多请求并发（Q4、Q5）**：请求在队列里等待时，它的检索已经完成，系统可以提前知道未来的需求，用来决定 expert 的常驻和换出，以及按亲和性组 batch。
   - **结合 KV 复用（S3）**：减少 prefill 需要计算的 token 后，如果 expert 不再全部被用到，P 问题才重新有选择的空间。
4. **一个工程上的细节**：如果规划器和阅读器是同一个 MoE 模型，规划这一步自己就会用到并搬入一批 expert，这些 expert 在后面的 prefill 中可以直接复用。在我们目前的设置下，规划器是独立的 RoG 7B 模型，这一点暂时用不上。
