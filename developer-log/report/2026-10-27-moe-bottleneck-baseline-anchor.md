# 总结：单用户 MoE offload 的瓶颈、基线能做到多少、anchor 能拿到多少

日期：2026-10-27
用途：回答导师的三个问题：
1. 在我们的场景下，系统的 bottleneck 在哪？
2. 已有的 baseline 能做到多少？
3. anchor 预测方法能拿到多少 benefit？

**这份报告没有新实验**，数字全部来自已有报告（见 §7）。配套 slides 是英文版。

---

## 0. 一页结论

| 问题 | 回答 | 关键数字 |
|---|---|---|
| **瓶颈在哪** | **从慢链路上读 expert。** 而且是**带宽受限**：每个 token 要读的字节太多，不是提前量不够 | Mac 实测：TPOT 168 ms 中约 85% 和读 expert 有关，不读时只要约 24–28 ms。完美预测、提前 8 层，停顿仍然 ≈ "读的时间 − 算的时间" |
| **基线能做到多少** | 最好的基线（校准 GATE + 按置信度预取）比"提前 1 层"降停顿 19–25%。固定取 8 个的预取在带宽受限时比不预取还慢 | 离完美预测还差 4–30%（缓存 25–50%）；完美预测本身也只比它好这么多 |
| **anchor 拿到多少** | **预测准确率在提前 ≥ 3 层时明显更高，但系统收益几乎为零** | 比校准 GATE 只多降停顿 0.1–4.4%（TPOT ≤ 2.2%）。加上"使用时顶替"后，模拟里多降 3–14%，原型上没有验证 |
| **对系统问题的含义** | 预测只能把读盘藏到计算后面。每个 token 读的时间本来就比算的时间长，所以预测再准也有下界。要减少读的字节，或者提高有效带宽 | "使用时顶替"（缺的 expert 换成缓存里的，改动 ≤ 10%）：Mac 实测 TPOT −46% / −58%，GSM8K 准确率没有掉 |

## 1. 场景和设置

- **场景**：个人工作站，单用户或低并发（B = 1–4，最多 8）。模型放不进显存 / 统一内存，expert 要 offload。
  - **Mac Studio M5 Max**：GLM-4.5-Air 4bit，expert 放在内置 SSD（峰值 7–9.6 GB/s）。
  - **单张 H200 + 主机内存**：expert 放锁页内存，经 PCIe 读（约 35–54 GB/s）。
- **模型**：
  - GLM-4.5-Air：45 个 MoE 层，128 选 8；
  - Qwen3-30B-A3B：48 层，128 选 8。
- **负载**：主要是 GLM 长推理 CoT（约 1,000 token / 请求，50 个请求，50,558 个 decode token）；另有 W1 短答案 CWQ。
- **两种测量**：
  - **模拟器** `tsim_mu.py`：用真实路由 trace 回放。计时参数来自微基准，Mac 部分按原型实测校准过，样本外误差 ≤ 16%。
  - **原型**：Mac `offload_engine.py` 和 H200 `hf_offload.py`，逐 token 和原生路径相同。
- **缓存大小**：用"能放下全部 expert 的百分之几"表示（25 / 50 / 75%）。

## 2. 问题一：瓶颈在哪

### 2.1 读一个 expert 比算一个 expert 慢得多

| 硬件 | 读一个 expert | 算一个 expert | 一层的计算（B = 1） |
|---|---|---|---|
| H200，PCIe，GLM bf16（34.6 MB） | 1.0 ms | 12.5 µs（**相差 80 倍**） | 约 0.31 ms |
| Mac SSD，GLM 4bit（约 10 MB） | 1.64 ms 等待 + 约 0.66 ms 主机开销（原型实测） | – | 约 0.79 ms |

每层只要缺一个 expert，读它的时间就是这一层计算时间的 2–3 倍。

### 2.2 Mac profiling：offload 的 decode 比全驻留慢 7–11 倍

设置：Qwen3-30B-A3B 4bit，前 3 层，缓存 50%，`outputs/moe_edge/profile/`。

| B | 全驻留（ms） | offload（ms） | 慢多少 | 等读盘的占比 | 有效读盘带宽 |
|---|---|---|---|---|---|
| 1 | 0.71 | 5.26 | 7.4× | 52%（另有约 34% 是启动开销） | 1.0 GB/s |
| 8 | 1.43 | 15.1 | 10.6× | 90% | 4.1 GB/s |
| 16 | 2.38 | 22.9 | 9.6× | 84% | 4.9 GB/s |
| 64 | 4.80 | 38.2 | 8.0× | 90% | 5.5 GB/s |

- 每次读的都是零碎的 2.65 MB 小块，有效带宽只有 1–5.5 GB/s，峰值约 9 GB/s。
- **batch 变大也分摊不掉**：不同 token 要的 expert 不一样，B 越大，要读的 expert 越多。

### 2.3 Mac 原型：GLM-4.5-Air 4bit，单用户，长推理

| 缓存 | TPOT | 每 token 读几次 | 等读盘 | 主机开销（估计） | 和读盘有关的占比 |
|---|---|---|---|---|---|
| 50% | 168 ms | 62.9 | 102 ms | 约 42 ms | **约 85%** |
| 75% | 66 ms | 18.2 | 30 ms | 约 12 ms | 约 64% |
| 不读（顶替吸收了全部缺失） | 24–28 ms | 0 | 0 | 0 | 0 |

主机开销 = 每次读 0.66 ms × 读的次数，这个系数来自模拟器校准（`mac_ssd_cal`）。

### 2.4 带宽受限，不是提前量受限

**完美预测**（oracle）下，提前不同层数的停顿（ms/token，GLM CoT，LRU，P3 参数）：

| 设置 | 提前 1 层 | 提前 4 层 | 提前 8 层 |
|---|---|---|---|
| Mac 25% | 126.4 | 125.3 | 125.2 |
| Mac 50% | 43.7 | 37.4 | 36.8 |
| Mac 75% | 8.9 | 3.6 | 3.1 |
| H200 25% | 93.3 | 93.1 | 93.1 |
| H200 50% | 37.3 | 35.6 | 35.4 |
| H200 75% | 9.4 | 6.9 | 6.2 |

- 缓存 25–50% 时，从提前 4 层加到 8 层几乎没有变化。
- 原因可以直接算出来。以 Mac 50% 为例：
  - 每个 token 要读 61 次 × 1.08 ms = **66 ms**；
  - 计算只有约 45 层 × 0.71 ms = **32 ms**；
  - 就算全部完美地藏到计算后面，也还要等 66 − 32 ≈ 34 ms。完美预测的实际值是 36.8 ms，基本就是这个下界。
- 只有缓存 75%（读的总量小于计算量）时，提前量才有意义，但这时停顿的绝对值只有几 ms。

### 2.5 低并发分摊不掉

Mac 原型，4 个请求并发，不顶替：
- 吞吐只比单用户高 21%（缓存 50%）和 1%（缓存 75%）；
- 每 token 的读次数和单用户几乎一样（65.4 对 62.9），因为 4 个请求要的 expert 很少重叠。

### 2.6 小结

> **停顿 ≈ max(0, 每 token 读的次数 × 每次读的时间 − 每 token 的计算时间) + 预测错的额外读**

所以只有三条路可以降低停顿：
1. **少读**：减少次数，或者每次读的字节更少。
2. **读得快**：提高有效带宽，比如把零碎的小块读合并。
3. **藏起来**：和计算重叠。这就是预测和预取做的事，但上限是"计算时间"那一项。

预测器只作用在第 3 条，以及"预测错的额外读"。

## 3. 问题二：基线能做到多少

### 3.1 比了哪些基线

| 我们的名字 | 做法 | 对应的已有工作 |
|---|---|---|
| 不预取 | 按需读 + LRU 缓存 | 通用 offload 缓存 |
| MoE-Infinity 式缓存（moeinf） | 按请求内的使用次数排优先级 | MoE-Infinity（作为缓存策略选项，每格取 LRU 和它中更好的） |
| 提前 1 层（la1） | 下一层的 gate 作用在当前 hidden state 上，固定取 8 个 | Mixtral-Offloading（2023-12，我们查到最早的免训练版本，ProMoE 称为 skip-gate）；Pre-gated MoE（ISCA'24）是要微调模型的版本 |
| GATE 多层 | 同上，提前 2–8 层，固定取 8 个 | HOBBIT（提前 ≤ 3 层）、AdapMoE（ICCAD'24，提前 2–3 层）。我们延伸到 8 层 |
| TOK+GATE 阈值 | token 频率 + GATE，按分数阈值取 | token 决定路由（OpenMoE 的发现） |
| **校准 GATE 阈值** | GATE 分数按校准表换成命中概率，超过阈值才读 | **我们加强过的基线** |
| 完美预测 | 真实路由 | 上界 |

还没有比的：ProMoE 训练的 MLP 预测器、FineMoE（代码已开源）。

### 3.2 结果

GLM CoT，50 个请求，decode 停顿（ms/token），每格都是各配置中的最优值（阶段 0）：

| 硬件 · 缓存 | 不预取 | 提前 1 层 | GATE 多层 | TOK+GATE 阈值 | **校准 GATE 阈值** | 完美预测 | 校准 GATE 离完美还差 |
|---|---|---|---|---|---|---|---|
| H200 · 25% | 144.5 | 170.1 | 168.3 | 139.7 | **137.2** | 131.1 | 4% |
| H200 · 50% | 61.0 | 71.4 | 70.7 | 57.2 | **56.7** | 47.9 | 16% |
| H200 · 75% | 16.3 | 17.3 | 15.9 | 13.8 | **14.0** | 6.4 | 54%（绝对值 7.6 ms） |
| Mac · 25% | 166.2 | 176.5 | 174.6 | 147.5 | **143.4** | 131.4 | 8% |
| Mac · 50% | 70.2 | 66.7 | 64.3 | 57.0 | **53.9** | 37.7 | 30% |
| Mac · 75% | 18.8 | 14.0 | 11.2 | 12.5 | **10.9** | 1.8 | 83%（绝对值 9.1 ms） |

**观察：**
1. **固定取 8 个的预取在带宽受限时有害**：H200 所有缓存、Mac 25%，"提前 1 层"都比不预取慢。不加阈值时，59–91% 的预取读没有被用到，既占带宽，又挤掉有用的 expert。
2. **按置信度只取有把握的 expert，是收益的主要来源**：比"提前 1 层"降 19–25%。这一点 GATE 自己就能做到，只要把它的分数校准成概率。
3. **不在测试集上挑参数也能拿到**：按排队负载自适应阈值，参数在 W1 上选，用到 CoT 上平均拿到事后最优的 85–99%（阶段 1.2）。
4. **完美预测的空间有限**：带宽受限的设置（25–50%）里，完美预测也只能再降 4–30%。这是任何预测器的上限，原因见 §2.4。

## 4. 问题三：anchor 能拿到多少

### 4.1 anchor 是什么

- 在第 l 层，用当前 token 已经算出的 router 打分，去历史 token 池里找最相似的 k 条记录（中心化余弦），让它们投票预测第 l+h 层的 expert。
- 每个 expert 的置信度 = 投票比例。
- 和 GATE 组合（AV+GATE）：投票比例 + 0.5 × GATE。

### 4.2 预测准确率：提前越多层，anchor 优势越大

GLM CoT，recall@8：

| 方法 | h=1 | h=2 | h=3 | h=4 | h=6 | h=8 |
|---|---|---|---|---|---|---|
| GATE | **.791** | .718 | .661 | .612 | .532 | .466 |
| TOK+GATE | .781 | .726 | .684 | .648 | .592 | .544 |
| anchor 单独（AV-logit-glob） | .660 | .653 | .645 | .637 | .624 | .610 |
| **anchor + GATE** | .778 | **.743** | **.715** | **.693** | **.655** | **.623** |

- **提前 1 层**：GATE 最好。
- **提前 ≥ 2 层**：anchor + GATE 最好。h=3 时高 5–6 pt，h=8 时比 GATE 高 16 pt。
- **anchor 单独几乎不随 h 衰减**：h=1 到 h=8 只掉 5 pt，GATE 掉 33 pt。
- **相似度高时更准**：只看相似度 ≥ 0.9 的 token（约 47%），anchor 在 h=3 时比 GATE 在同一批 token 上高 10–11 pt。
- W1 短答案上的规律相同。

### 4.3 系统收益：几乎没有

最好的 anchor 配置比**校准 GATE 阈值**多降多少停顿（负数 = anchor 更好）：

| 硬件 · 缓存 | 不顶替（阶段 0，每格事后最优） | 不顶替（阶段 1，自适应阈值） | 加上顶替 ≤ 10%（阶段 1，模拟） |
|---|---|---|---|
| H200 · 25% | −0.6% | −1.1% | −2.8% |
| H200 · 50% | −2.2% | −1.8% | −11.8% |
| H200 · 75% | −5.3% | −3.9% | −20.4%（0.7 对 0.8 ms） |
| Mac · 25% | −0.7% | −0.6% | −2.6% |
| Mac · 50% | −0.1% | +1.1% | −14.0% |
| Mac · 75% | −3.8% | +2.4% | −22.0%（0.5 对 0.6 ms） |

- **不顶替时**：anchor 和校准 GATE 几乎打平，TPOT 差 ≤ 2.2%。P3 里看到的 3–11%，是因为当时 GATE 还没有阈值，比较不公平。
- **加上顶替后**：缓存 50% 时 anchor 多降 12–14%。一个可能的解释：顶替只能换成已经读完的 expert，预取越准，剩下要换的越少。但这个结果只在模拟里出现，原型里用的是校准 GATE。
- **还没算的成本**：每个 token 每层都要在约 21 万条记录里找最近邻，实际要用近似搜索、缩小池子，准确率可能会掉。

### 4.4 预测下一个 token 的路由

GATE 只能在同一个 token 内往后看，anchor 可以预测下一个 token。这一点用在"按路由相似性组 batch"上（阶段 3）：
- recall@8：anchor .513，"沿用上一个 token" .342；
- anchor 能拿到"按真实路由组 batch"收益的 78–83%；
- 但组 batch 本身的收益就小：吞吐 +8–11%，p99 却高 40%。在 N ≤ 8 的低并发下也没有可挑的请求。arXiv 2608.07911 有几乎相同的负面结果。

### 4.5 为什么准确率更高、系统收益却很小

1. **带宽受限时提前量不值钱**（§2.4）。anchor 的强项正好是"提前很多层还准"，用不上。
2. **决定停顿的是最后一次预测准不准**。浪费的读几乎全部是"最后一次预测也错"，被早期预测修正掉的只占 0–4%。而在最后一两层，GATE 本来就很准（h=1 .79）。
3. **预测本身的上限就小**：连完美预测也只能再降 4–30%（§3.2）。
4. **已有工作**：FineMoE（EuroSys'26，已开源）也是"用前几层的 gate 概率去匹配历史轨迹"，只取最像的一条。anchor 能说的新意只剩"kNN 投票 + 每个 expert 的置信度"。

## 5. 对"系统层面要解决什么"的回答

- **问题**：在个人工作站上跑放不下的 MoE，decode 被"每个 token 要从慢链路（SSD / PCIe）搬的 expert 字节数"卡住。而且读得零碎，有效带宽只有峰值的 10–60%。
- **为什么预测不够**：每个 token 读的时间比算的时间长（Mac 50%：66 ms 对 32 ms），预测只能把读藏到计算后面，最多藏掉计算那么长。这就是完美预测的停顿下界。
- **真正能动这个瓶颈的**：减少读的字节，或者提高有效带宽。
  - 已有证据：**使用时顶替**。迟到的 expert 换成缓存里 router 分数最高的那个，全局改动 ≤ 10%。
    - Mac 单用户：TPOT 168 → 90 ms（缓存 50%，−46%）；66 → 28 ms（75%，−58%，完全不再读）。
    - Mac 4 并发：吞吐 ×1.65（50%）、×3.9（75%）。去掉读之后，计算可以被 batch 分摊。
    - 准确率：GLM GSM8K 10% 改动 .885 对 .890；Qwen3 thinking 10% .910 对 .900，没有系统性掉点（200 题，只能排除约 3 pt 以上的下降）。
    - 规则本身 DAOP（DATE'25）有；我们的部分是改动预算、长推理准确率、"缓存 ≥ 75% 时不再读"。
  - 预测（校准 GATE）作为补充：缓存 50% 时原型上再降 14–20%；缓存 75% 时反而有害（+23%）。
  - 还没做：合并读（提高有效带宽）、迟到的 expert 用低精度版本（每次读的字节更少）。
- **anchor 的定位**：不作为主贡献。保留两个可能有用的地方：顶替时的预测精度（§4.3 最后一列，待原型验证），以及多级存储（SSD → 内存 → 显存）里提前量真正成为瓶颈的情形。

## 6. 局限

1. 大部分基线和 anchor 的比较是**模拟**；原型只实现了校准 GATE 和顶替，没有实现 anchor。
2. 主负载只有 GLM CoT 一种；Mac 用的是 4bit 模型，它的路由和 bf16 重合 80–85%。
3. 阶段 0 每格取事后最优配置；阶段 1 的自适应阈值能拿到其中的 85–99%。
4. ProMoE 的 MLP 预测器和 FineMoE 还没有作为基线跑。
5. 顶替的改动预算目前是全局累积的，单个请求的改动率在 4.2–19.5% 之间，top-1 expert 也可能被换。修正和重测在 `plan/2026-10-27-subst-budget-plan.md`。
