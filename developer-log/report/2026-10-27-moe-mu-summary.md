# 总结：多用户 MoE offload 调度（阶段 0–4）

## 0. 一页结论

**问题**：expert 放不进 GPU / 统一内存时（offload 到 SSD 或主机内存），MoE decode 被"读 expert"卡住。plan 提出五个组件，想在单用户和多用户下降低这部分开销：
1. 相似性组 batch
2. anchor 多层预取
3. 使用时顶替（缓存感知路由）
4. 常驻 / 流动分区
5. 保护 / 冻结

**结果**：

| 组件 | 结论 | 关键证据 |
|---|---|---|
| **使用时顶替**（缺的 expert 换成缓存里分数最高的，改动 ≤ 10%） | **有效，而且是收益的主要来源** | 模拟：多用户吞吐 +50% 到 +800%；缓存 ≥ 75% 时完全不用再读。实测：Mac 单用户 TPOT −46%（缓存 50%）/ −58%（75%）；H200 吞吐 +26–46%。准确率：GLM 和 Qwen3 thinking 在 10% 以内都没有掉点 |
| **多层预取**（校准 GATE + 自适应阈值） | **只在低缓存时有用** | Mac 缓存 50%：吞吐 +15–24%（单用户、4 并发都成立）；缓存 75% 时反而变差 23%。模拟里大 batch（B ≥ 16）的 +73–82% 无法在原型上验证 |
| anchor（kNN 轨迹匹配）代替 GATE | **几乎没有额外价值** | 给 GATE 也加上校准阈值后，anchor 只再好 0.1–4.4% |
| 相似性组 batch | **只在 B 受限时有一点用** | 同一 B 下吞吐 +8–11%，但 p99 +40%。offload 时 B 越大越好，不限 B 时它没有用 |
| 常驻 / 流动分区 | **无效** | 单用户最好 −9.7%（判据 10%）；多用户 −1.3% 到 0 |
| 保护（C2）/ 冻结窗口 | **无效** | C2 的差别 ≤ 0.4%；冻结窗口能省的那部分浪费只占 0–4% |

**一句话**：在 offload 场景下，"把迟到的 expert 换成已在缓存里的、改动控制在 10% 以内"几乎包办了全部收益；预取只在缓存很小时有补充作用；其余组件可以不做。

## 1. 设定

- **模型**：
  - GLM-4.5-Air：45 个 MoE 层，128 expert，top-8，sigmoid + bias 路由；
  - Qwen3-30B-A3B：48 层，128 expert，top-8，softmax 路由。
- **负载**：
  - 主负载：GLM CoT（W2c，长推理，约 1000 token / 请求，200 个请求）；
  - 短答案：W1 CWQ；
  - 准确率：GSM8K（GLM；Qwen3 用 thinking 模式，约 1000 token）。
- **硬件**：
  - H200 PCIe：expert 放主机内存；
  - Mac M5 Max：GLM 4bit，expert 放内置 SSD；
  - 另有 H200 全驻留作对照。
- **模拟器** `tsim_mu.py`：同步 batch 模型，单用户（seq）和多用户（pool，N 个流、每步 B 个）。
  - 和 P3、Q1 的旧模拟器逐数一致（误差 1.8e-10）；20 个单元测试。
  - 计时参数先用微基准，后来按原型实测校准（§4）。
- **原则**：阈值等参数要么自适应，要么在校准集上选，不在测试集上挑。

## 2. 各组件的证据

### 2.1 使用时顶替（核心）

**规则**：一个 token 的 top-k 里，没在缓存里或还在读的 expert 叫"迟到"。迟到的按路由权重从小到大，换成缓存里该 token 没选、router 分数最高的 expert；全局改动率不超过预算；被换掉的不读。

**模拟（阶段 1、3）**：
- 单用户：改动 ≤ 10% 时，停顿比"提前 1 层"降 41–100%。
- 多用户（GLM CoT，N 64 / 128，B 16 / 32），相对"同步 + LFU"的吞吐：

  | 缓存 | 吞吐提升 | 说明 |
  |---|---|---|
  | 50% | +50–56% | |
  | 75% | +306–810% | 一次都不加载 |
  | 90% | +65–169% | 一次都不加载 |

  - 缓存 ≥ 75% 时，按校准频率选出的缓存集合 + 10% 预算就能吸收全部缺失，系统变成纯计算。用不泄漏的校准集预填也一样。

**准确率（阶段 2，真实模型）**：

| 模型 · 任务 | 改动率 | 准确率（基线） | 对变错 / 错变对 |
|---|---|---|---|
| GLM · GSM8K 200 题 | 2 / 5 / 10% | .920 / .900 / .885（.890） | 1/7、9/11、13/12 |
| Qwen3 · GSM8K thinking 200 题 | 5 / 10 / 15% | .895 / .910 / .865（.900） | 5/4、7/9、**14/7** |

- 10% 以内两个模型都没有系统性掉点。Qwen3 在 15% 时有下降趋势：差 −3.5 pt，95% 区间 [−8.0, +1.0]，还不显著。
- 换哪个 expert 很重要：GLM CoT 上均匀随机换时，答案相同的比例只有 38%；按规则换是 62%。
- 局限：200 题只能排除约 3 pt 以上的掉点；GLM 15–20% 的测量在等 GPU。

**原型实测（阶段 4）**：

| 机器 | 缓存 | 不顶替 | 顶替 5% | 顶替 10% |
|---|---|---|---|---|
| Mac 单用户（TPOT） | 50% | 168 ms | 130 ms | 90 ms（−46%） |
| Mac 单用户（TPOT） | 75% | 66 ms | 36 ms | 28 ms（−58%，0 次加载） |
| Mac 4 并发（吞吐） | 50% | 7.2 tok/s | 8.7 | 11.9（+65%） |
| Mac 4 并发（吞吐） | 75% | 15.4 tok/s | 37.9 | 59.8（3.9 倍） |
| H200 · Qwen3 B=16（吞吐） | 50% | 31.2 tok/s | 40.0 | 45.6（+46%） |
| H200 · Qwen3 B=16（吞吐） | 75% | 67.4 tok/s | 76.7 | 84.7（+26%） |

- 打补丁但不改动时，和原生路径逐 token 相同。模拟器、Mac、H200 三份实现在随机输入上逐步决定完全相同。
- **顶替让并发变得有用**：不顶替时，4 个请求的 expert 很少重叠，加载分摊不掉，4 并发几乎不比单用户快（+21% / +1%）；顶替去掉加载以后，计算可以分摊。

### 2.2 多层预取

- **预测器**：
  - 在第 l 层套用第 l+1…l+8 层的 router（GATE-h），按 margin 校准成命中概率，超过自适应阈值就预取。
  - recall@8：h=1 / 3 / 6 时 .80 / .68 / .55。Mac 4bit 和 H200 bf16 接近。
- **anchor vs GATE（阶段 0）**：给 GATE 也加上校准阈值后，anchor（kNN 投票）只再好 0.1–4.4%。所以原型用校准 GATE。是否继续做在线轨迹池（1.4），要等 v4 数据，现在倾向不做。
- **Mac 原型（阶段 4.2）**：参数在校准请求上用模拟器选（`p0.7:kl0.05`）。

  | | 不顶替 → + 预取 | 顶替 10% → + 预取 |
  |---|---|---|
  | 缓存 50% · 单用户 | 168 → 135 ms（−20%） | 93 → 80 ms（−14%） |
  | 缓存 50% · 4 并发 | 7.2 → 8.3 tok/s（+15%） | 11.8 → 14.3（+21%） |
  | 缓存 75% · 单用户 | 66 → 65 ms | 30 → 37 ms（**+23%**） |

  - 判据（预取 + 顶替比只做顶替再降 ≥ 25%）没有达到。
  - 缓存 75% 时预取有害：顶替已经吸收了缺失，预取读只增加开销；它唯一的作用是把改动率从 8.2% 降到 5.0%。
- **模拟里的大收益**：多用户 B=16–64、Mac 50% 时 +73–82%。只做顶替时读盘是"等待 + 主机开销"串行进行的，预取让加载通道在计算期间继续读。这个只在模拟里出现，原型最大只测到 B=4，没有看到"并发越多收益越大"的一致规律。

### 2.3 相似性组 batch（阶段 3）

- 下一 token 的 expert 预测：P-anchor recall@8 .51（上一 token .34），拿到"按真实路由挑"收益的 78–83%（判据 ≥ 75%，达到）。
- GPU 全驻留（H5：p99 ≤ +20% 时吞吐 ≥ +10%）：只在 N=200 时达到（+10.0% / +12.5%）；N ≤ 64 时 +6–8%。和 arXiv 2608.07911 的负面结果一致。
- offload（H6：相同 p99 下，全栈比"只做顶替"再高 ≥ 15%）：
  - 同一 B 下组 batch +8–11%，但 p99 +40%。
  - offload 时 B 越大，吞吐越高、p99 越低，所以不限 B 时最优点都是"B 最大 + 轮转"，组 batch 不起作用。只在 B 受限时有用。
  - 原参数下，H6 只在 Mac 50% 达到（同一 B 8/8，中位 +32%）。按原型校准后的参数，Mac 50% 达到得更充分（+84% 到 +93%，主要来自预取）；H200 50% 和所有 75–90% 的设置都没达到。

### 2.4 常驻 / 流动分区、保护、冻结

- 常驻 / 流动（阶段 1.1）：五种填法 × 各种 ρ，单用户最好比 ρ=0 再降 9.7%（判据 10%，没达到）。多用户 −1.3% 到 0。
- C2 保护（阶段 0.4、3.3）：差别 ≤ 0.4%，LRU / LFU 下这些 expert 本来就很少被换出。
- 冻结窗口 / 置信度累积（阶段 1.2）：浪费主要是"最终预测也错"，被早期预测修正的只占 0–4%，冻结能省的就这么多。实测也没有收益。
- 自适应阈值（阶段 1.2）：在 W1 上选，平均拿到"事后最优固定阈值"效果的 85–99%。最差设置只有 24–38%（Mac 75% + LRU），换成 CoT 校准子集后改善。

## 3. 原型

| | Mac（`experiments/moe_edge/`） | H200（`experiments/moe/hf_offload*.py`） |
|---|---|---|
| 模型 | GLM-4.5-Air 4bit（MLX） | Qwen3-30B-A3B bf16（transformers 5.2） |
| expert 存放 | 内置 SSD（preadv，F_NOCACHE） | 锁页主机内存（PCIe，旁路 stream） |
| 缓存 | 每层池，大小按校准频率分配 | 同左 |
| 顶替 | 有 | 有 |
| 多层预取 | 有（后台读线程，规则同模拟器） | 没有 |
| 并发 | 单用户、4 并发（BatchGenerator） | B=16 静态 batch |
| 和原生路径一致 | 逐 token 相同 | 逐 token 相同（grouped_mm） |
| 原型自身的开销 | 约 2% | **每步比全驻留多 22–90 ms** |

H200 原型的问题：每层要把路由同步到 CPU、做 Python 判断、启动许多小 kernel。我试过把判断搬到 GPU（4.2.6），但同一进程交替计时显示反而慢 7–8 ms。要可信地量化大 batch 收益，需要把路由、顶替、槽位映射融合成 GPU kernel，并配合 CUDA graph。按你的决定，这条线停在这里。

## 4. 模拟器可信度

- **回归**：P3、Q1 的数字逐数复现。
- **Mac 校准（4.1.3）**：
  - 原参数低估了每次读的代价：实测等待 1.64 ms（参数 1.15 ms），另有约 0.66 ms 的主机开销，TPOT 误差 −36% 到 +27%。
  - 只用不顶替的两组拟合后，样本外误差：只做顶替的四组 +2% / +6% / −4% / −16%；预取的四组 −0% / +3%（50%）、−5% 到 −37%（75%）。
  - 加载次数、改动率误差约 1%。
- **一个已知的建模缺口**：每次读的主机开销只有和计算重叠时才算数（50% 时被等待吸收，75% 时加到计算上）。模拟器现在只能在"只算需求读"和"所有读都算"之间二选一，所以 75% 时预取的代价被低估。
- **只在 B ≤ 4 验证过**。B=16–64 的多用户结论（特别是预取的大收益）仍是纯模拟。

## 5. 局限

1. **准确率**：样本量有限（200 题排除约 3 pt）；GLM 15–20%、CWQ、"按 token / 按层"的预算形式还没测（等 GPU0/1）；原型上的准确率不可比（CoT 截断）。
   - **改动预算的问题（2026-10-27 发现）**：现在的预算是全局、跨请求、跨时间累积的，从不清零，而且额度充足时连权重最大的 top-1 也会被换。Mac 75% 缓存、ρ = 10% 时，单个请求的改动率在 4.2–19.5% 之间，top-1 被换的占 8.9%，个别（token, 层）8 个全被换。阶段 2 的准确率是按"均匀改动、多为低权重"测的，覆盖不了这种情形。修正和重测见 `plan/2026-10-27-subst-budget-plan.md`。
2. **负载**：主要是 GLM CoT 一种。缓存是静态预填（顶替时几乎不再读，缓存不变），负载漂移时的表现没测。
3. **大 batch 只有模拟**；H200 原型受自身开销限制。
4. **共享集群**：主机负载会让分开测的同一配置差 30% 以上，所以 H200 的对比改用同一进程交替计时。

## 6. 建议

1. **主线收窄为"使用时顶替 + 改动预算"**，加上"低缓存时的校准 GATE 预取"作为可选项：
   - 适用于端侧和单卡 offload；
   - 在 Mac 上是现在就能落地的系统（缓存 75% 时 TPOT 降 58%、4 并发吞吐 3.9 倍），代码量小。
2. **新意的定位**：顶替规则本身 DAOP 已有。我们的贡献在于：
   - 改动预算与长推理准确率的系统测量；
   - "缓存 ≥ 75% 时顶替使 offload 不再加载"这一现象；
   - "顶替让小并发变得有用"的机制；
   - 模拟器与两台原型的逐项核对。
3. **不再投入**：常驻 / 流动分区、C2 / 冻结、anchor 在线池、相似性组 batch（除非场景里 B 明确受限）。
4. **还没做完的**：GLM 15–20% 和 CWQ 的准确率（等 GPU0/1）；Qwen3 安全改动率要更多题才能定到"掉 ≤ 1 pt"。
5. **下一步优先做的**：修正改动预算（按请求计、限制每层个数、保护 top 权重的 expert），并在真实的顶替决定下重测准确率（`plan/2026-10-27-subst-budget-plan.md`）。在此之前，"10% 以内不掉点"只对缓存 50%、改动均匀的情形成立。
6. **如果要讲多用户大 batch 的故事**，需要一个 GPU 原生的 offload 实现（融合 kernel + CUDA graph），工作量是周级。
