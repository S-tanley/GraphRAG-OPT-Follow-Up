机器：Mac Studio M5 Max（GLM-4.5-Air 4bit，expert 在内置 SSD）；masdar GPU2（Qwen3-30B-A3B bf16，expert 在锁页内存，PCIe）。

## 0. 结论

1. **顶替在两台真实机器上都有效，而且缓存 ≥ 75% 时同样"不再加载"。**

   | 机器 · 模型 · 缓存 | 不顶替 | 顶替 5% | 顶替 10% |
   |---|---|---|---|
   | Mac · GLM-4.5-Air 4bit · 单用户 · 50% | TPOT 168 ms | 130 ms（−23%） | 90 ms（−46%） |
   | Mac · 同上 · 75% | 66 ms | 36 ms（−45%） | 28 ms（−58%，0 次加载） |
   | H200 · Qwen3-30B-A3B bf16 · B=16 · 50% | 31.2 tok/s | 40.0（+28%） | 45.6（+46%） |
   | H200 · 同上 · 75% | 67.4 tok/s | 76.7（+14%） | 84.7（+26%，几乎不读） |

   - 补丁后不改动时，和原生路径逐 token 相同；补丁本身的开销约 2%（Mac）。
   - 三份顶替实现（模拟器、Mac、H200）在随机输入上的逐步决定完全相同。

2. **模拟器核对（4.1.3）：缓存行为完全对上，计时参数需要校准，校准后误差 ≤ 16%。**
   - 每 token 加载次数、改动率和实测相差约 1%。
   - 原 `mac_ssd` 参数低估了每次读的代价：实测等待 1.64 ms（参数 1.15 ms），另外每次读还有约 0.66 ms 的主机端开销。TPOT 误差 −36% 到 +27%。
   - 只用两组不顶替的运行拟合出 `mac_ssd_cal`，四组顶替的运行样本外预测误差 +2% / +6% / −4% / −16%。

3. **用校准参数重跑阶段 3 的 Mac 行：缓存 50% 时全栈收益比原来大得多，来源是多层预取。**
   - 全栈对"只做顶替"：同一 B 下 8/8 个设置达标，中位 +84% 到 +93%；不限 B 的前沿 +73% 到 +129%（原参数约 +15%）。
   - 原因：只做顶替时，每次读是"等待 + 主机开销"串行，加载通道只有 65% 的时间在忙；多层预取让它在主机工作和计算期间继续读。
   - 缓存 75–90% 的结论不变：没有加载，全栈无增益。
   - 注意：校准只在 B=1、无预取的条件下验证过。这个结果要靠在 Mac 原型里实现预取（4.2，你之前决定推迟）来确认。

4. **H200 原型受自身开销限制。** 不读盘时每步仍比全驻留多约 35–41 ms：每层要把路由同步到 CPU、做编号重映射和 Python 顶替判断。所以吞吐只到全驻留（129.7 tok/s）的 59–65%。
   - 这不影响"顶替有效"的结论，但 H200 上的绝对收益和模拟核对，要等把顶替判断移到 GPU 上之后才有意义。

5. **4 个请求并发（Mac）：不顶替时并发几乎没用，顶替让并发变得有用。**
   - 不顶替时，4 并发的吞吐比单用户只高 21%（缓存 50%）/ 1%（75%）。4 个随机请求的 expert 很少重叠，加载次数和请求数成正比，分摊不掉。
   - 顶替 10% 时，4 并发吞吐 11.9 tok/s（50%，+65%）/ 59.8 tok/s（75%，3.9 倍，完全不加载）。没有加载之后，计算可以被 batch 分摊（4 个 token 只花 1.9 倍的时间）。

## 1. 原型怎么做的

### 1.1 顶替规则（三份实现相同）

在 decode 时，一个 token 的 top-k 里"迟到"的 expert 被换掉：
- 迟到 = 不在该层的缓存池里，或者还在读；
- 按路由权重从小到大换，受改动预算限制（全局改动率，随机取整）；
- 换成池里已就绪、该 token 没选的、router selection 分数最高的那个（GLM：sigmoid + correction bias；Qwen3：softmax）；
- 按新集合用 router 的分数重算权重；
- 被换掉的 expert 不读。prefill 从不改动。

`test_subst_rule.py`：模拟器、Mac 原型、H200 原型三份实现，在 5 种预算 × 3 个随机种子下逐步决定完全相同。

### 1.2 Mac（`experiments/moe_edge/subst_offload.py`）

- 在 mlx-lm 的 GLM / Qwen3 MoE block 上打补丁：先调原生路由；有迟到的 expert 时按规则替换编号、重算权重；交给已有的 offload 引擎（`offload_engine.py`，expert 从内置 SSD 用 preadv 读进每层的缓存池）。
- 引擎的改动：每层槽数可以不同；`warm(counts)` 按校准频率预填；`ready_mask`。
- 池大小：按校准频率选全局前 C 个 expert，每层至少 16 个（`tsim_mu.layer_caps`），和模拟器的全局 LFU 对应。
- 负载：CoT CWQ 第 32–51 题；第 0–31 题的 Mac 轨迹做校准。上限 1024 token，LFU，每组 20 个请求连续跑。
- 4 并发：`subst_offload_batch.py`，mlx-lm 的 BatchGenerator（连续 batch，新请求在 decode 步之间逐个 prefill）。

### 1.3 H200（`experiments/moe/hf_offload.py`、`hf_offload_run.py`）

- transformers 5.2 的 MoE（GLM-4.5 / Qwen3）：expert 权重放锁页内存；每层一个 GPU 缓存池，experts 模块改为指向池，编号换成槽位号，模型自己的 experts 实现（grouped_mm）照常跑。
- 缺的 expert 在旁路 stream 上拷入；prefill 超过池大小时走全层暂存，再按 LFU 保留。
- 顶替：在路由处打补丁，按输入长度自动区分 prefill / decode。
- `test_hf_offload.py`：小随机模型上，grouped_mm 时 logits 和生成与原生完全相同；eager 时累加顺序变了，逐步喂 token 比较 logits，误差在 bf16 容差内。
- 负载：GSM8K thinking 第 50–113 题（前 50 题的轨迹做校准），B=16 静态 batch，上限 2048。

## 2. 结果

### 2.1 Mac 单用户（GLM-4.5-Air 4bit）

| 缓存 | 配置 | TPOT | 每 token 加载 | 停顿 / token | 迟到率 | 改动 |
|---|---|---|---|---|---|---|
| 50% | 原生（不打补丁，1 个请求） | 153 ms | – | – | – | – |
| 50% | 不顶替 | 168 ms | 62.9 | 102 ms | 17.5% | 0 |
| 50% | 顶替 5% | 130 ms | 47.6 | 77 ms | 18.2% | 5.0% |
| 50% | 顶替 10% | 90 ms | 31.4 | 50 ms | 18.7% | 10.0% |
| 75% | 原生（1 个请求） | 60 ms | – | – | – | – |
| 75% | 不顶替 | 66 ms | 18.2 | 30 ms | 5.1% | 0 |
| 75% | 顶替 5% | 36 ms | 4.1 | 7 ms | 6.1% | 5.0% |
| 75% | 顶替 10% | 28 ms | 0 | 0 | 8.2% | 8.2% |

- 同一个请求，原生 153 ms、补丁后不改动 156 ms：补丁开销约 2%。补丁后不改动和原生路径逐 token 相同。
- 准确率这里不可比：多数 CoT 写满 1024 token 被截断，Hit .10–.25，只有 20 题。准确率以阶段 2（H200 bf16）为准。

### 2.2 Mac 4 个请求并发（缓存 50%）

| 配置 | 吞吐 | token 间隔 p50 / p99 | 每 token decode 加载 | 改动 |
|---|---|---|---|---|
| 单用户不顶替（对照） | 5.95 tok/s | 168 ms | 62.9 | 0 |
| 4 并发不顶替 | 7.2 tok/s | 520 / 884 ms | 65.4 | 0 |
| 4 并发顶替 5% | 8.7 tok/s | 423 / 737 ms | 49.5 | 5.0% |
| 4 并发顶替 10% | 11.9 tok/s | 305 / 618 ms | 32.6 | 10.0% |
| 75% 单用户不顶替（对照） | 15.2 tok/s | 66 ms | 18.2 | 0 |
| 75% 4 并发不顶替 | 15.4 tok/s | 245 / 408 ms | 19.5 | 0 |
| 75% 4 并发顶替 5% | 37.9 tok/s | 77 / 240 ms | 5.3 | 5.0% |
| 75% 4 并发顶替 10% | 59.8 tok/s | 53 / 118 ms | 0 | 8.1% |

- **不顶替时，4 并发几乎没有吞吐收益**（50%：+21%；75%：+1%），每个请求却慢了 3–4 倍。原因是加载分摊不掉：4 个随机请求的 expert 很少重叠，每 token 的加载次数和单用户差不多（65.4 对 62.9，19.5 对 18.2）。75% 缓存不顶替时，一步 245 ms 里约 180 ms 是加载。
- **计算本身是能分摊的**：75% 顶替 10% 时完全不加载，4 并发一步 53 ms，单用户一步 28 ms，4 个 token 只花 1.9 倍的时间。
- 所以**顶替让并发变得有用**：去掉了分摊不掉的加载，剩下能分摊的计算。4 并发顶替 10% 的吞吐是不顶替的 1.65 倍（50%）/ 3.9 倍（75%），比单用户顶替 10% 高 7% / 68%（50% 时仍有 32.6 次 / token 的加载，分摊不掉）。
- 吞吐里包括了新请求的 prefill；token 间隔的 p99 主要来自 prefill。

## 3. 过程中的问题和修正

| 问题 | 处理 |
|---|---|
| 模拟器按层固定容量时，prefill（每层用到 105–128 个 expert）让缓存超容，之后顶替不再加载，缓存就一直比 C 大（模拟出的改动只有 2.2%） | 用完后按 LFU 裁回容量，和真实引擎的"暂存 + 保留"一致。全局缓存（阶段 1.3 的 seq、阶段 3 的 pool）没有超容，已核对 overflow 计数全为 0 |
| 主机开销最初只计了需求读，而且读的计数起点在顶替分支的 advance 之后，漏掉了大部分预取读 | 计数改为从每层开始；另加 `mac_ssd_cal_all`，框住两种假设 |
| 记录属性 `eng.rec` 和 Mac 引擎里已有的 `rec`（每个 expert 的字节数）重名 | 改名 `route_log` |
| transformers 5.2 的 Qwen3 router 返回的已经是 softmax 之后的概率，H200 补丁初版又做了一次 | 修正；小模型测试覆盖 |
| eager 实现下，换成槽位号后逐 token 生成和原生不同 | eager 按 expert 编号顺序累加，槽位号改变了累加顺序（bf16 舍入不同），不是逻辑错误；改为逐步喂 token 比较 logits。grouped_mm 下完全相同 |
| GPU 队列：计时任务每次都重新等 30 分钟 | 按你的规则改为每张卡只等一次，只有出现别人的进程才重新等（`gpu_queue.py` 按进程所有者区分，`--cleared` 保留状态） |

## 4. 局限

1. **准确率在原型上没有可比的测量**：Mac CoT 被截断；H200 只有 64 题。准确率以阶段 2 为准（GLM 10% 内、Qwen3 thinking 10% 内不掉；15% 时 Qwen3 有下降趋势）。
2. **校准只在 B=1、无预取的条件下验证过**；阶段 3 用的是 B=8–64 和预取。主机开销的来源没有查清。
3. **H200 原型的开销太大**，绝对收益偏低，也没做模拟核对。
4. **H200 只测了 Qwen3**；GLM bf16 需要锁约 200 GB 内存。
5. **静态缓存**：顶替时被换掉的 expert 不读，缓存因此几乎不变；负载漂移时可能变差，这里测不到。

## 6. 4.2：Mac 多层预取原型（2026-10-27 追加）

你的决定：做 4.2。预测器用在线可算的**校准 GATE**：
- 在第 l 层的 MoE 输入上，套用第 l+1…l+8 层的 router，得到前 16 个 expert；
- 按归一化 margin 查表，换成命中概率；
- 概率超过自适应阈值的交给后台读线程。规则和模拟器的 `prefetch_adv` / `lookahead` 一致：新预测替换旧预测、过期作废、不淘汰更早要用的、顶替时撤销排队中的读。

### 6.1 实现和检查

| 项 | 结果 |
|---|---|
| GATE-h 在线计算（预先堆叠各层 router 权重，每层一次批量算） | 前 200 次 GATE-1 和下一层原生 router 的 top-8 逐一相同；TPOT 没有可见的增加 |
| GATE-h recall@8（Mac 4bit） | h=1/3/6：.803 / .679 / .554（H200 bf16：.792 / .661 / .532） |
| 校准表（第 0–31 题，缓存 75%，不顶替） | 每个 h 最高桶的命中率：.997（h=1）到 .868（h=8） |
| 预取器单元测试（`test_prefetch.py`） | 5 项通过：排队顺序、撤销、过期、需求读接管、保护和钉住、读完自清 |
| 只预取不顶替时的生成 | 和原生路径逐 token 相同（50% / 75%）：预取只改时间，不改结果 |

### 6.2 参数选择（只用校准请求）

在第 0–31 题上用模拟器扫 τ0 × κ_log，两种校准参数都算，选中 `ah8:GATEs:m8:p0.7:kl0.05`。

单用户的模拟预测比阶段 3 的多用户小得多：
- 缓存 50% 时，顶替 + 预取比只做顶替降 10–19%；75% 时没有收益，甚至变差 21%。
- 原因：单用户时每层的计算短，能用来掩盖读盘的时间少。

所以计划里的判据（“再降 ≥ 25%”，取自多用户模拟的约 −40%）在单用户下不合适，已在 plan 里注明。

### 6.3 实测（第 32–51 题）

| 缓存 · 并发 | 不顶替 | 只预取 | 顶替 10% | 预取 + 顶替 10% |
|---|---|---|---|---|
| 50% · 单用户（TPOT） | 168 ms | 135 ms（−20%） | 93 ms | 80 ms（−14%） |
| 75% · 单用户（TPOT） | 66 ms | 65 ms（−2%） | 30 ms | 37 ms（**+23%**） |
| 50% · 4 并发（吞吐） | 7.2 tok/s | 8.3（+15%） | 11.8 | 14.3（+21%） |

- **缓存 50% 时，预取稳定带来 15–24% 的吞吐提升**，有没有顶替、单用户还是 4 并发都成立。实测落在模拟预测的区间里。
- **缓存 75% 时预取有害**：顶替已经吸收了全部缺失，预取读只增加开销（+23%，和“预取读也付主机开销”那种参数的预测 +21% 一致）。它唯一的作用是把改动率从 8.2% 降到 5.0%。所以预取只应在低缓存时打开。
- **判据（再降 ≥ 25%）没有达到**（单用户 −14%，4 并发 −22% 的 token 间隔）。
- **4 并发没有显示出“并发越多预取收益越大”**：只预取时 +15%（单用户 +24%），预取 + 顶替时 +21%（单用户 +16%）。阶段 3 模拟里 B=16–64 的 +73–82% 在 Mac 上无法验证。
- **模拟核对**（同一路由 + 同一预测回放，4.1.3 的做法；计时参数只用不顶替、不预取的两组拟合）：

  | 运行 | 实测 | 主机开销只算需求读 | 所有读都算 |
  |---|---|---|---|
  | 50% 预取 + 顶替 | 80 ms | 79（−0%） | 87（+10%） |
  | 50% 只预取 | 135 ms | 138（+3%） | 151（+12%） |
  | 75% 只做顶替 | 30 ms | 24（−22%） | 24（−22%） |
  | 75% 预取 + 顶替 | 37 ms | 24（−37%） | 30（−20%） |
  | 75% 只预取 | 65 ms | 57（−12%） | 61（−5%） |

  - 50% 时"只算需求读"几乎完全对上；75% 时"都算"更接近，但仍低估。
  - 解读：每次读的主机开销只有和计算重叠时才算数。50% 时主线程多在等读盘，预取读的开销被等待吸收；75% 时几乎不等，开销直接加到计算上。模拟器的两种算法是这个机制的两个极端。

### 6.4 对方向的意义

- 单用户和小并发下，顶替是主力（50% 缓存时 TPOT −45%），预取是锦上添花（再 −14–20%，只在低缓存时有用）。
- 预取的大收益只在模拟里的大 batch 出现。要验证，需要能跑大 batch 的平台（H200 上的 offload 原型，而它现在被自身的 Python 开销限制住了）。
