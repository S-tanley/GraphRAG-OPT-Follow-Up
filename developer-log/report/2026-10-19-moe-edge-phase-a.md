# Report：Mac 端侧 MoE 实验阶段 A（A 档三个模型，以及 GLM 4bit 的量化检查）

*Bowen · 2026-10-19 · 对应 `developer-log/plan/2026-10-18-moe-edge-mac-plan.md`（v2）*

> 状态：A 档三个模型（OLMoE、Qwen3-30B-A3B、DeepSeek-V2-Lite）的阶段 A 全部完成。B 档（H200 计划的四个大模型，4bit，真实 offload）在后台继续采集：GLM 已完成 W1，正在采 Wtrain。全部汇总表在 `outputs/moe_edge/phase_a/report_tables.md`。

## 一句话结论

在 Mac 上换成按时间推进的评估、更强的 token 基线、更多模型之后，结论和 H200 中期报告**方向一致，但更清楚了瓶颈在哪里**：

1. **完美的请求级预测有很大的空间。** 准入时就知道这个请求 decode 要用的 expert，短答案场景下 decode 停顿能减少 58–100%（缓存 ≥50% 时；缓存 25% 时是 25–76%）。
2. **检索信号只拿到其中很小一部分。** 准入时，检索预测比最强的 token 基线只多 0.2–2.1 个百分点的 recall；按时间模拟，decode 停顿只再少 1–19%，端到端时延的差别不到 1%。原因是 decode 的路由几乎由"生成了哪些 token"决定（只用答案的 token 查表，就能拿到上限的 80–98%），而检索只能给出候选，确定不了答案是哪一个。
3. **长 decode 上，请求级先验和分段先验都没用，甚至有害**；起作用的是时间局部性和提前一层的预测。
4. **按阶段、按段重组 batch 的空间本身就小**：完美分组下，短答案少 7–18% 的 expert 加载，长 decode 的分段重组只少 2–6%。
5. **与检索无关、但量很大的发现**：offload 时，prefill 阶段用抗扫描的缓存替换策略（按全局使用频率），首 token 延迟能减少 11–40%（缓存越大越明显）。

## 0. 本阶段做了什么

| 项目 | 内容 |
|---|---|
| 环境 | `.venv-mac`（MLX 0.32.4、mlx-lm 0.32.2）；硬件实测见 plan §1（内存 519 GB/s，内置 SSD 7–9.6 GB/s，外置 SSD 约 1.1 GB/s） |

| offload 引擎 | `offload_engine.py`：expert 导出到内置盘（`export_experts.py`），用 `preadv` + `F_NOCACHE` 直接读进缓存槽位，零拷贝。在 Qwen3-30B 上与原模型对比：贪心生成的 token 完全一致，logits 差值为 0 |
| 按时间推进的模拟器 | `tsim.py`（单用户 S1：prefill 流式加载、decode 逐层、三级优先级的加载队列、提前一层预取、准入时 / prefill 后 / 分段的先验）；`tsim_batch.py`（多请求 S2：continuous batching + 分段重组 + 缓存亲和调度）。计算时间用 MLX 实测值校准 |
| 新的预测器和基线 | prefill 后（T1）：CANDFIRST、FIRSTTOK（不用检索的对照）；准入时（T0）：KNN_R（检索特征的 kNN）和 **KNN_T（问题 token 的 kNN，更强的 token 基线）** |
| 数据 | A 档三个模型：W1（CWQ / WebQSP 各 500 题）、Wtrain 2000 题、Direct、chat 版 W2（200 题，最多 2048 个 token） |

**prompt 格式的两处调整：**

- Qwen3-30B 是带 thinking 的混合模型。在纯文本 few-shot 格式下，它会直接输出思考过程或格式碎片，CWQ 的 Hit 只有 0.20。所以改成把**完全相同的 few-shot 文本**放进 chat template，并关闭 thinking（标记为 `-cf`），Hit 回到 0.41。OLMoE 和 DeepSeek-V2-Lite 用纯文本格式正常。
- 纯文本格式下，小模型看到 few-shot 示例都是直接作答，就直接给答案，没有长推理。所以 W2 改用各模型的 chat template（Qwen3 开 thinking），标记为 W2c。

**没做的部分：**

- Wsyn / Wsyn-rand：改写表还在集群上，集群一直连不上。
- GLM bf16 trace 上的 FIRSTTOK 对照：需要集群上的 GLM Wtrain。

**发现：**

1. **完美的准入时预测空间很大**：短答案的 decode 停顿能减少 25–100%（缓存越大，比例越高）。而且准入时就知道（检索窗口里就能开始预取）比 prefill 之后才知道好得多：OLMoE 50% 缓存时是 −84% 对 −27%。这说明"提前量"确实是关键，验证了你之前的判断。
2. **但真实的检索预测只拿到 1–19%**，而且相对的是"用 token 先验"这个最强的非检索基线。
3. **端到端时延几乎不变（<1%）**：短答案的时延主要花在首 token 上（prefill 要扫一遍 expert），decode 一共只有几个 token。
4. **长 decode（W2c）上，请求级先验和分段先验都更差**：先验把缓存位置留给"整个请求平均会用"的 expert，挤掉了当前这一段真正要用的 expert；起作用的是时间局部性。
5. **prefill 用抗扫描的替换策略（全局频率），首 token 延迟减少 11–40%**（缓存越大越明显；DeepSeek-V2-Lite 75% 缓存时从 2551 ms 降到 1522 ms），和检索无关。代价是 prefill 结束时缓存里留的是全局热门的 expert，而不是这个请求自己的；缓存小的时候，decode 会因此略慢。这个取舍本身就是 E4（prefill 结束时保留什么）的内容。

**H3 判定：不成立**（门槛是比最强基线少 ≥20% 停顿，实际 1–19%）。**H4**：完美预测下的前 8 步停顿几乎可以消除，但检索预测只减少 1–19%，没有系统意义。

## 5. E5 初步：复用检索上下文的 KV

**用模拟器估算上限**（OLMoE，W1-CWQ，50% 缓存，最好的非检索策略；时间里扣掉了 0.6 秒的检索窗口）：

| prefill 时处理哪些 token | prefill 耗时 | 端到端 |
|---|---|---|
| 全部 | 768 ms | 852 ms |
| 去掉固定前缀（普通的前缀缓存） | 668 ms | 752 ms（−12%） |
| 只算问题 token（路径的 KV 也全部复用） | 511 ms | 613 ms（−28%） |

**但路径在不同请求之间的复用率很低**（按到达顺序统计）：

| | 路径：之前的请求里出现过 | 路径：之前的请求或 Wtrain | 三元组：之前的请求或 Wtrain |
|---|---|---|---|
| CWQ | 19.2% | 26.1% | 34.8% |
| WebQSP | 6.1% | 23.3% | 28.6% |

只能复用约 1/4 到 1/3 的路径时，剩下的路径照样会让 prefill 用到大部分 expert。所以 −28% 只是一个达不到的上限。真实系统积累的历史会更多，复用率可能更高，但目前的数据不支持把 E5 作为主线。

## 7. 为什么：瓶颈在"预测答案"

1. **decode 的路由由输出 token 决定。** 只用答案 token 查表，就能拿到重组上限的 80–98%。所以"预测 decode 用哪些 expert"几乎等价于"预测答案会写出哪些 token"。
2. **检索只缩小了答案的范围，没有确定答案。** 候选实体有好几个，相似问题的历史请求（KNN_T）也能提供差不多的信息，所以检索相对 token 基线的优势只剩 0.2–2.1 pt。
3. **短答案：时延的大头不在 decode。** prefill 的流式加载占了首 token 延迟的绝大部分，decode 只有几步。
4. **长 decode：要预测的是"下一段"，不是"整个请求"。** 整个请求的平均分布帮不上忙，有用的是时间局部性和提前一层的预测，而这些都和检索无关。

## 8. 局限

- 吞吐、时延是模拟值（计算时间用 MLX 实测校准）。B 档的 offload 引擎会给出真实测量，用来核对模拟。
- 4bit 量化改变了约 20% 的边界 expert（§1）。
- 采集都是 batch 1；多请求场景（S2）的路由用的是单独运行的 trace。
- 原型引擎的缓存是"每层固定槽位"，模拟器的缓存是"全局"，两者略有差别。
- Wsyn / Wsyn-rand 和 GLM bf16 的 FIRSTTOK 对照，要等集群恢复才能补。
