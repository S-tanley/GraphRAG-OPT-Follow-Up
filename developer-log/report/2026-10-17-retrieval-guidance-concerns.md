# 关于"用检索信息指导后续生成"的两个根本性疑问

*Bowen · 2026-10-17 · 整理自 2026-10-16、2026-10-17 的讨论，附上目前已有的证据*

这份文档记录我对整条研究线（proposal 的核心假设："检索暴露的语义和结构信息可以指导下游执行"）的两个疑问，以及在什么前提下这条线仍然可以做。这两个疑问直接决定 MoE plan（`developer-log/plan/2026-10-16-moe-retrieval-prefetch.md`）该往哪个方向走。

---

## 疑问 1：检索完成之后再用检索信息，和普通 prefill 有什么区别？

### 问题

如果等检索全部完成之后，才去考虑"拿到的信息能怎么指导后面的生成"，那这时候 prompt 已经确定了，和普通的 prefill 拿到 prompt 是同一时刻，**在时间上没有任何提前**。也就是说，我们只是"拿到了一个 prompt"，这和"这个 prompt 是不是检索来的"其实没有关系。任何针对 prompt 的优化，普通推理系统都可以做。

### 这条线仍然成立的两个前提

**前提 A：检索构造出的 prompt 带有独特的信息，比任意 prompt 更能指导生成。**

GraphRAG（或其他检索系统）产生的 prompt 和随便写的 prompt 不一样：它有明确的结构（实体、关系、路径、schema、候选答案集合），而且检索系统知道这些结构，不需要从文本里重新解析。如果只有这类结构信息才能更准地预测后续行为（例如 expert 的使用），那么"检索"就是不可替代的。

- 已有的支持证据：
  - GraphRAG prompt 的结构性和重复性很强：同一题内去重能省 55–69% 的路径 token，路径基本是一棵以 topic entity 为根的前缀树（实验 1、实验 2）。
  - proposal Fig. 7：relation schema 相同的题，expert 激活分布更相似（同组 cosine > 0.96，不同组约 0.85）；而检索打分、检索频次这类连续数值没有预测力。
- 主要威胁：**这些效果可能只是"相同的 token 被路由到相同的 expert"**。schema 相同的题，prompt 里有大量相同的关系名 token（关系 token 占路径 token 的约 40%）。如果真是这样，那么按 token 查表（任何 prompt 都适用）就能得到同样的效果，前提 A 就不成立。
- 怎么验证：把检索结构特征（schema、候选实体、路径拓扑）和"与检索无关的通用特征"（token 级的历史路由、prompt 本身观察到的分布）放在一起，比较预测准确率；同时专门控制 token 重叠（例如只用问题 token 或 decode token 来统计）。**只有在控制住 token 重叠之后，检索结构仍然带来额外的预测力，前提 A 才成立。**

**前提 B：在检索进行的同时，就能利用检索过程中产生的信息去指导后面的生成（prefetch 等），从而获得真正的时间提前。**

- 已有的反面证据（Phase 0.5，`2026-10-17-moe-phase0.5-timeline.md`）：在 RoG 式检索中，约 0.6 秒的检索时间几乎全部花在"规划"这一次 LLM 生成上；规划结束、拿到 schema 之后，只需约 2 毫秒 prompt 就组装好了。所以：
  - "拿到 schema 之后的窗口"约 2 毫秒，几乎什么都做不了；
  - "从请求到达开始的窗口"约 0.6 秒，但这段时间里只知道问题文本，不知道任何检索结构。
- 前提 B 可能成立的场景（需要另行验证）：
  - 检索本身更慢、而且分阶段产出信息：多跳的穷举式路径枚举（proposal 中 4 跳约 1.1 秒）、迭代式或 agent 式的多轮检索、远程向量库、重排序（reranker）；
  - 规划器和阅读器是同一个 MoE 模型时，规划这一步自己就会用到并搬入一批 expert，后续 prefill 可以直接复用；
  - 多请求并发时，请求在队列里等待的时间可以作为"检索之后、prefill 之前"的窗口（见下文）。

### 小结

| 前提 | 目前的证据 | 状态 |
|---|---|---|
| A：检索 prompt 的结构信息有独特的预测力 | Fig. 7 支持，但没有排除"token 重叠"这个更简单的解释 | **待验证**（MoE plan Phase 2 的 Q3） |
| B：检索进行中就能用上检索信息 | 在 RoG 式检索中，schema 之后的窗口约 2ms | **在当前设置下不成立**；只在检索更慢、分多阶段，或者多请求并发时才可能成立 |

另外还有一种不依赖"时间提前"的用法：**多请求并发时，对队列的前瞻。** 请求在排队时检索已经完成，系统可以在它进入 prefill 之前，就知道队列里接下来的请求会用到什么，用来决定资源的常驻和换出，以及请求的分组。这里的"提前"是相对于**其他请求**而言的，而不是相对于这个请求自己的 prefill。

## 疑问 2：expert offloading 的调度空间到底在哪里？

### 问题

expert offloading 看起来是最有希望的方向，但有两个问题：

**(a) prefill 阶段几乎所有 expert 都会被用到。** prefill 时几十到几百个 token 并行经过 FFN，各自选各自的 expert。即使每个 expert 分到的 token 数不同，几乎所有 expert 都会被用到，所以很难说在 loading / offloading 上能做什么有意义的调度。

- 数据：假设选择均匀独立，N 个 token 之后某个 expert 一次都没被选中的概率约为 (1 − k/E)^N。Mixtral（8 选 2）在 N=20 时约 0.3%；Qwen3（128 选 8）在 N=100 时约 0.2%。我们的 KGQA prompt 有 200–700 个 token，必然会用到全部 expert。
- 这时 prefill 的瓶颈就是"把不在显存里的 expert 全部搬一遍"：例如单卡上的 Qwen3-235B 每次 prefill 约要搬 340GB，按 54GB/s 计算约 6 秒。

**(b) decode 阶段可以调度，但这时检索信息的价值又被削弱了。**

- decode 时每个 token 每层只用 k 个 expert，预测和 prefetch 才有意义。但 KGQA 的输出很短（5–16 个 token），需要长输出的任务（思维链、reasoning 模型、多轮）才有足够的 decode 量。
- 更关键的是：**到 decode 的时候，prefill 已经做完了，prefill 自己观察到的 expert 使用情况（这个请求实际用了哪些 expert、用了多少）是一个更直接、很可能也更准的信号。** 如果 decode 的预测只需要 prefill 的信息就够了，那么检索信息就又没有用了。
  - 这里需要注意：prefill 信号"更准"目前还是一个假设。proposal Fig. 4 的 prefill–decode 相似度约 0.84，但它缺少跨请求的对照组，也受 decode 长度影响，不能直接说明"prefill 能准确预测 decode 的 top-k"。
  - 检索信息仍然可能有一点价值：它能在 prefill **开始之前**就给出 decode 的先验，可以趁 prefill 那几秒提前搬运。但这只有在它比"prefill 进行到一半时的观察"更准，或者更早可用时才有意义。这同样需要 Phase 2 的 Q3 来回答。

### 初步想法：逐层 prefill + attention 与 FFN 分离 + buffer（待细聊）

- **逐层 prefill**：prefill 按层推进，在算第 l 层时搬第 l+1 层的 expert，让搬运和计算流水起来。
- **attention 与 FFN 分离**：attention 和 expert 放在不同的执行单元上（例如不同的 GPU，或者 GPU 和 CPU / 近存计算单元），各自独立调度。
- **在 FFN 前加 buffer**：攒够足够多的 token（可以来自多个请求、多个 micro-batch）再让某个 expert 计算，让每次搬进来的 expert 服务更多 token，以此摊薄搬运代价。

和已有工作的关系（**未核实**，需要查新）：

- vLLM / SGLang 这类引擎在同一次迭代内，本来就把所有请求按层同步推进，MoE 层已经会把这一层的所有 token 按 expert 分组计算。所以"层内攒 token"已经存在，buffer 的新意要来自**跨迭代、跨请求**地攒。
- 吞吐优先的 offload（FlexGen、MoE-Lightning、Klotski 的"expert-aware multi-batch pipeline"）和 attention / FFN 分离部署（如 MegaScale-Infer）已经在用"攒更多 token 来摊薄 expert 代价"的思路。
- 可能的新角度：**利用检索信号主动决定把哪些请求、哪些 token 攒到一起**（按 expert 亲和性组 batch），而不是被动地等待。这又回到了疑问 1 里"并发时的前瞻"。

## 结论

两个疑问都切中要害。就目前的数据看：

- **前提 B 在 RoG 式检索下基本不成立**（Phase 0.5 已经测过）。
- **前提 A 是否成立，取决于能否排除"token 重叠"这一更简单的解释**，这是下一步分析最重要的一项。
- **expert offloading 的调度空间主要在 decode 和多请求并发**；prefill 阶段要么走"逐层流水 + attention / FFN 分离 + 跨请求攒 token"的系统设计路线，要么借助 KV 复用减少需要计算的 token。

在 V1、V2 有结论之前，不应该把"检索信息指导生成"作为论文的核心卖点。
