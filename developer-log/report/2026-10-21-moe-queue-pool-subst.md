# Report：Expert queue、多用户 decode 池、缓存感知路由（多用户 MoE offload）

日期：2026-10-21
plan：
- `archive/plan/2026-10-19-moe-expert-queue-plan.md`（Q0、Q1、Q3）
- `plan/2026-10-21-moe-affinity-decode-pool-plan.md`（A0）

机器：
- masdar H200：GPU0/1 用于微基准、准确率测试；CPU 用于 trace 统计和模拟。

数据：GLM-4.5-Air bf16 的 W2c CoT trace，200 个请求，每个约 1000 个 decode token（`traces_v3`）。

---

## 0. 结论

1. **原始的 expert queue 设计不成立。**
   - 原设计：每个请求独立推进，每个 expert 前面一个队列，攒够 token 再加载，用心跳统一推进。
   - 在 H200（PCIe）和 Mac（SSD）两种 offload 设置下，几乎所有配置都不如同步 batching（N=128、缓存 90%：147 对 291 tok/s，p99 1153 对 482 ms）。只有 N=16、缓存 75% 时略好（45 对 42 tok/s）。
   - 原因：同步时所有 token 同时到达同一层，缺的 expert 一次加载服务所有人，这本身就是最好的攒批。异步后需求在时间上被打散，每次加载服务的 token 更少。缓存大时，异步还带来大量小 batch 的 attention，GPU 上的固定开销成了瓶颈。
2. **同步框架下，"决定谁一起跑"有效，但收益温和。**
   - 方法：每步从 decode 池里按路由相似性挑请求，用上一个 token 的路由作预测，最多比轮转多等 2 步。
   - 结果：吞吐 +9% 到 +15%。用真实路由（上限）是 +13% 到 +18%；不限等待时 +18% 到 +26%，但 p99 涨 2–3 倍。
3. **最大的收益来自"缓存感知路由"；只要被改动的 expert 使用不超过约 10%，准确率基本不掉。**
   - 方法：decode 时只用常驻的 expert，缺的换成常驻里路由分数次高的。
   - 模拟：H200 PCIe，N=64，吞吐 ×3.7（缓存 90%，改动 1.2%）到 ×8.6（缓存 75%，改动 5.4%）。
   - 真实模型准确率：**判据应该是"被改动的比例"，不是"常驻比例"**。
     - 改动 ≤ 10%：两个模型、两类任务都基本不掉。例如 GLM 在 GSM8K 上常驻 75%（改动 8%）时 .910 → .905；Qwen3 常驻 50%（改动 9–13%）时也不掉。
     - 改动 ≥ 25%：明显下降。GLM 在 GSM8K 上常驻 50%（改动 26%）时掉到 .595，常驻 25%（改动 56%）时掉到 .295。Qwen3 常驻 25%（改动 43%）时掉 3.7 pt。
     - 同样的常驻比例，GLM 在长推理时用到的 expert 比 Qwen3 分散得多（常驻 50% 时改动 26% 对 12%），所以常驻比例要按模型和任务来定。
     - "换成次优 expert"始终比"直接丢弃"好（GSM8K、常驻 25%：Qwen3 −3.7 对 −31 pt；GLM .295 对 .180）。
4. **对后续方向的影响：**
   - expert queue 的价值不在"异步攒批"，而在"冷门 expert 不必等，用常驻的顶替"。
   - decode 池的相似性挑选可以和缓存感知路由叠加：挑选让一起跑的请求用到更集中的 expert，缓存感知路由处理剩下的冷门 expert。

## 1. H200 微基准（Q1 的时间参数）

脚本 `experiments/moe/queue_microbench.py`，GLM-4.5-Air 的形状（hidden 4096，expert 中间维 1408，96 个 query 头 / 8 个 KV 头），bf16，H200：

| 项 | 数值 |
|---|---|
| 一个 expert（34.6 MB）走 PCIe 从锁页内存读入 | 1.0 ms（35 GB/s）；一次读 16 个是 50 GB/s |
| 分组矩阵乘法（`torch._grouped_mm`），m 个 expert | ≈ 50 µs + 12.5 µs ×（m − 1），token 数在 1–64 / expert 之间几乎不影响 |
| 逐个 expert 做矩阵乘法（HF 的写法） | 每个 expert 约 45 µs，是分组的 3.6 倍 |
| 一层的 attention + 投影 + 路由（非融合实现） | B=1–16：140–170 µs；B=256、上下文 2k：1.05 ms |
| kernel 启动 / 路由结果同步到 CPU | 12.6 µs / 20 µs |

加载一个 expert 约是算一个 expert 的 80 倍，offload 下的 decode 完全受加载带宽限制。

## 2. Q0：能不能攒起来（只按步算）

脚本 `experiments/moe/queue_stats.py`。

- 设置：N 个请求同步 decode。不在常驻集合里的 expert（常驻集合按全局使用频率选）要加载。每层每个 expert 一个队列，攒够 n 个 token，或者最老的等满 w 步，才加载。
- 每层最热的 25% / 50% / 75% expert 分别承担 52% / 78% / 93% 的使用。

缓存 50% 时：

| N | 同步：每次加载服务的 token 数 | n=8，w=2 | n=16，w=2 |
|---|---|---|---|
| 64 | 2.4 | 6.0（×2.5） | 6.3（×2.6） |
| 200 | 5.9 | 10.4（×1.8） | 15.3（×2.6） |

- 加载次数能降到同步的 36–45%：**Q-H1 成立。**
- 但 n=8 时，40–90% 的（token, 层）至少有一个 expert 在排队，每层平均等 0.5–1.4 步。一个 token 要穿过 45 层，这是不可接受的。这就是 plan 里"一个 token 等它最慢的 expert"的问题。

## 3. Q1：按时间推进的模拟

脚本 `experiments/moe_edge/tsim_async.py`。

- 两种硬件：
  - `h200_pcie`：上面的微基准；
  - `mac_ssd`：GLM 4bit，从 SSD 读一个 expert 1.15 ms。
- 缓存：按使用频率淘汰（LFU）。最初用 LRU 时，同步模式每步按层顺序扫一遍，LRU 会把下一层要用的 expert 先踢掉，所以改为 LFU。
- 一开始先按使用频率把缓存填满，排除冷启动。
- 计入每次 attention、每次分组矩阵乘法、每次心跳的固定开销。
- 异步模式：加载通道空闲时，挑**当前**排队最长、且已达到阈值的 expert。

结果（`outputs/moe/q1_async.json`）：

| 设置 | 同步 | 同步 + 提前 1 层预取 | 异步队列（最好的阈值） |
|---|---|---|---|
| H200，N=64，缓存 50% | **27.3 tok/s** | 14.5 | 12.8 |
| H200，N=64，缓存 75% | **65.1** | 36.2 | 50.5 |
| H200，N=64，缓存 90% | **214** | 150 | 114 |
| H200，N=128，缓存 90% | **291**（p99 482 ms） | 193 | 147（p99 1153 ms） |
| Mac，N=64，缓存 75% | **49.5** | 31.4 | 36.9 |

- 只有 N=16、缓存 75% 时，异步略好：45.4 对 41.8 tok/s。
- 加载通道一直满载，所以阈值 n 和最长等待 W 都不起作用；expert 本来就在积压里排队。
- 提前 1 层预取在带宽受限时让加载量翻倍、吞吐减半，和 anchor P3 的发现一致。
- 异步模式的问题：
  - 缓存小时，需求被打散：每个 token 的加载次数比同步多一倍以上（N=64、缓存 50%：78 对 35）；
  - 缓存大时，GPU 被小 batch attention 的固定开销占满（GPU 忙碌 100%）。
- 局限：attention 的固定开销用的是非融合实现（约 140 µs），vLLM 的融合 kernel 会小不少。但"需求被打散"的问题和这个无关。

**Q-H3 不成立。**

## 4. 同步框架下的两个变体

### 4.1 按相似性挑请求（decode 池，A0 + 时间模拟）

**A0：不同 expert 数**（`experiments/moe/pool_bound.py`，每个请求从 decode 的随机位置开始）。每 token 每层平均用到的不同 expert 数，相对轮转（FCFS）：

| N | B | 真实路由，最多多等 2 / 4 步 / 不限 | 上一 token 预测，最多多等 2 / 4 步 / 不限 |
|---|---|---|---|
| 64 | 8 | −14 / −17 / −19% | −9 / −11 / −12% |
| 128 | 16 | −15 / −18 / −23% | −10 / −12 / −14% |
| 200 | 16 | −15 / −19 / −26% | −10 / −12 / −16% |
| 200 | 32 | −15 / −18 / −21% | −10 / −11 / −12% |

一开始所有请求从第 0 个 token 开始时，CoT 开头相同的模板文字会把收益放大；以上是改成随机起点之后的数字。

**时间模拟**（N=128，`outputs/moe/q1_pool.json`）：

| 设置 | 轮转 | 上一 token 预测（多等 ≤ 2 步） | 真实路由（多等 ≤ 2 步） |
|---|---|---|---|
| Mac，缓存 75%，B=32 | 37.3 tok/s | 43.0（+15%） | 44.0（+18%） |
| Mac，缓存 90%，B=32 | 89.7 | 98.2（+9%） | 101.8（+13%） |
| Mac，缓存 90%，B=16 | 66.4 | 72.3（+9%） | 75.7（+14%） |
| H200，缓存 90%，B=32 | 164.8 | 182.5（+11%） | 187.9（+14%） |

不限等待能到 +18% 到 +26%，但 p99 每 token 延迟会涨 2–3 倍。

### 4.2 冷门 expert 顶替（缓存感知路由）

**模拟**（`outputs/moe/q1_sub.json`）：本步需要某个缺失 expert 的 token 少于 n 个时不加载它。模拟里这些 token 直接跳过这个 expert，作为吞吐上的近似。H200，N=64：

| 缓存 | 同步 | n=2 | n=4 | n=8 | 被跳过的 expert 使用（n=4） |
|---|---|---|---|---|---|
| 90% | 214 tok/s | 479 | **789（×3.7）** | 805 | 1.2% |
| 75% | 65 | 133 | **562（×8.6）** | 893 | 5.4% |
| 50% | 27 | 42 | 139 | 1051 | 14% |

**真实模型准确率**（`experiments/moe/subst_accuracy.py`）：
- 常驻集合 = 每层在校准请求的 decode 中用得最多的 f 比例 expert。校准用 Wtrain / GSM8K 训练集，不用测试集。
- 只在 decode 时限制，prefill 不变。
- 两种处理：
  - **顶替**：非常驻 expert 的路由分数设为 −∞，重新从常驻里取 top-k；
  - **丢弃**：保留原 top-k，非常驻的权重置 0，剩下的重新归一。

| 模型 / 任务 | 完整 | f = 0.9 | f = 0.75 | f = 0.5 | f = 0.25 |
|---|---|---|---|---|---|
| Qwen3-30B-A3B / CWQ 300 题（Hit@1） | .470 | .470 / .470（0.0%） | .470 / .473（0.4%） | .463 / .463（9%） | – |
| GLM-4.5-Air / CWQ 300 题 | .487 | .487 / .487（0.5%） | .487 / .487（2.5%） | .470 / .460（9–10%） | – |
| Qwen3-30B-A3B / GSM8K 300 题（准确率） | .897 | .897 / .907（0.1%） | .917 / .897（1.5%） | .907 / .907（12–13%） | **.860** / .587（43–46%） |
| GLM-4.5-Air / GSM8K 200 题 | .910 | – | **.905** / .875（8%） | .595 / .525（26–28%） | .295 / .180（56–59%） |

（每格：顶替 / 丢弃；括号里是 decode 中被改动的 expert 使用比例。）

- 300 题的统计误差约 ±1.7–2.9 pt，常驻 ≥ 50% 时的差异基本都在误差内。
- 常驻 25% 时，近一半的 expert 使用被改动。顶替只掉 3.7 pt，丢弃掉 31 pt，所以**换成次优的常驻 expert 明显比直接丢掉好**。
- 注意：被改动的比例取决于任务。短答案和 GSM8K 的 decode 路由比 GLM 在 CWQ 上的长 CoT 更集中，模拟里同样缓存 50% 时，GLM CoT 有 21% 的使用不在常驻集合里。所以长 CoT 上的准确率还需要单独确认（§6）。

### 4.3 GLM-4.5-Air / GSM8K 的补充说明

- 第一次运行（生成上限 384）时，完整模型只有 .20。原因有两个：
  - GLM 写的是带 Markdown 的长篇分步解答，384 个 token 不够；
  - GLM 用 `<|user|>` 表示一轮结束，脚本只认 `<|endoftext|>`，答完后继续编下一轮，打分取到了编出来的数字。
- 修正后，结束符读取 generation_config 里的完整列表（`<|endoftext|>`、`<|user|>`、`<|observation|>`），生成上限改为 1024，跑 200 题，完整模型 .910。
- Qwen3 的结果不受影响：它的 `<|im_end|>` 当时单独处理过。GLM 在 CWQ 上的结果也不受影响：只取第一行，遇到换行就停。
- **结论**：GLM 在长推理时路由更分散，常驻 50% 已经有 26% 的使用要改动，准确率大幅下降；常驻 75%（改动 8%）是安全的。这说明需要按"被改动的比例"来设定缓存大小或顶替阈值，例如在线统计改动比例，超过约 10% 时就照常加载。

## 5. 讨论

- **Expert queue 原设想里真正有用的部分**是"冷门 expert 不让 token 等"。等待在异步推进下会被 45 层放大，在同步推进下又无从攒起；而缓存感知路由直接绕开了等待。这和 plan 里 Q3 的"超时后用常驻 expert 顶替"是同一个机制，只是不需要先等到超时。
- **和相关工作的关系**：缓存感知路由类似"cache-conditional experts"和 expert skipping / substitution 一类工作（端侧 MoE 推理）。本次结果的不同点是给出了多用户 offload 场景下的吞吐模拟，以及在长推理任务上的准确率。新颖性需要再查文献。
- **decode 池的相似性挑选**是正交的：它让同一批请求的 expert 需求更集中，缓存命中更高，需要顶替的更少。两者叠加的效果待测。
- **心跳**在这次的结果里没有用武之地：最好的配置都在同步框架下，心跳退化成每步一次。

## 6. 局限和下一步

1. **模拟里的顶替用的是"跳过"**，不是"换成次优 expert"。换成次优 expert 不增加加载，但可能要多算一个常驻 expert，吞吐上的差别很小。
2. **长 CoT 上的准确率**：GSM8K 的解答是 200–600 个 token。还需要在更长的推理（thinking 模式、1000+ token）上测，并做一个"改动比例上限"的自适应版本：例如每层只在本步被顶替的权重少于某个值时才顶替，否则照常加载。
3. **叠加实验**：decode 池挑选 + 缓存感知路由 + 按置信度预取（anchor P3）的组合，在同一个模拟器里跑吞吐 vs p99 曲线。
4. **原型**：
   - 缓存感知路由只需要改 router（加一个掩码），实现最简单；
   - 可以先在 Mac 的 offload 引擎或 H200 的 HF / vLLM 上做一个 PCIe offload 的原型，实测吞吐。
5. **心跳 / 异步**：如果之后换成融合的 attention kernel，固定开销大幅下降，可以重新评估异步方案在缓存大时的表现。不过"需求被打散"这一点不会变。
