# Report：MoE 实验 E0–E4 中期结果（GLM-4.5-Air 全流程；其余 3 个模型被 GPU 故障中断）

*Bowen · 2026-10-18 · 对应 `developer-log/plan/2026-10-18-moe-experiment-plan.md`*

## 一句话结论

**在 GLM-4.5-Air 上，四个假设都没有达到 plan 里定的门槛。**

- **检索信息确实有预测力，而且在统计上显著，但量很小。** 准入时，检索信号让 decode expert 的 recall@16 比最强的 token 基线高 1.8（CWQ）到 3.5（WebQSP）个百分点，门槛是 5。换成语义相同、token 不同的改写（Wsyn）之后，提升没有消失。
- **换算成系统收益更小，主要原因有两个：**
  - **W1（短答案）**：搬运量的 77–92% 来自 prefill 把几乎全部 expert 扫一遍，decode 只占 8–23%。即使是 Belady（知道未来全部访问的最优缓存），端到端也只能少搬 12–18%。
  - **W2（长思维链）**：decode 占大头，但 350 个 token 的 decode 会用到每层 93% 的 expert。决定性的是请求内的时间局部性，请求级先验（不管是检索的还是 token 的）反而有害。

剩下 3 个模型（Mixtral、Qwen3-235B、DeepSeek-V2.5）的采集，被 22:00 左右 GPU0/1 的硬件故障打断了。按 plan，H1 需要 4 个模型里至少 2 个成立，所以**现在还不能下最终结论**；但 GLM 的结果已经让整个方向的前景明显变差，建议和导师讨论（见 §7）。

## 2. E1：路由可预测性（H1）

设置：

- 查找表和学习式预测器只在 Wtrain 上建立：80% 用来建表（1600 题），20% 用来调组合权重（400 题），测试题不参与。
- 指标是 decode 每个 token、每层的 recall@B，B ∈ {8, 16, 32}，即 {k, 2k, 4k}。
- 显著性检验按请求做配对 bootstrap（2000 次）。
- 噪声上限约 97%。

| PREFILL − GLOBAL | −17.6 | −13.4 | −16.5 | +3.5 |

### 2.3 解读

1. **检索信号有预测力，但很小。** 准入时它比最强的 token 基线高 1.8–3.5 个百分点（WEB 的 schema 覆盖率是 0.77，CWQ 是 0.60，所以 WEB 更高）。所有置信区间都不跨 0，但都离 5 个百分点的门槛很远。
2. **提升不是由 token 重叠带来的。** 在 Wsyn 下，提升从 +1.8 变成 +2.2，没有下降（plan 的第二条判据要求"至少保留一半"，满足）。不过 Wsyn 里同一 schema 的请求仍然共享改写后的 token，更严格的 Wsyn-rand（每个请求随机选一种改写）还没跑，要等 GPU 恢复。
3. **decode 阶段一旦开始，检索信号就没有用了。** 提前一层的 gate 加上 TOKID 已经达到 0.87（@16），离噪声上限不远；加入检索信号只增加 ≤1 个百分点，在 W2 上甚至是负的。
4. **prefill 的观察对短答案的 decode 帮助很差**（比 GLOBAL 低 13–18 个百分点）：prompt 位置上的路由和 decode 位置上的路由差别很大。在 W2 上，PREFILL 反而比 GLOBAL 好 3.5 个百分点，因为长思维链在内容上更接近 prompt。
5. **decode 路由更多跟着主题实体走，而不是 schema**（CWQ 上的 decode 分布余弦相似度）：

   | | 同 schema、不同主题 | 不同 schema、同主题 | 同 schema、同主题 | 跨请求平均 |
   |---|---|---|---|---|
   | 余弦相似度 | 0.536 | 0.591 | 0.687 | 0.489 |

   WEB 上则是 schema 更重要（0.640 对 0.548）。

**H1 判定（GLM）：不成立**（门槛 5 个百分点，实际 1.8–3.5）。H1 需要 4 个模型中至少 2 个成立；还剩 3 个模型。

## 3. 模拟器设置（E2–E4）

- **数据**：E0 的真实路由 trace，加上 E1 导出的请求级预测分布。
- **硬件模型**：单卡 H200；路由 expert 缓存在显存中，容量为全部 expert 的 C ∈ {10%, 30%, 50%, 70%}，其余放在 pinned 主机内存（54 GB/s）；GLM 的一个 expert 是 34.6MB。
- **代价模型**：计算时间按解析的 roofline 估算（max(字节 / 4.8TB/s, FLOPs / 989TFLOPS) + 5µs）。原计划在两张卡空闲时实测单个 expert 的 roofline，因为一直有人共享、现在又出了故障，所以还没测。字节数和命中率不受这个影响，只有吞吐和延迟的绝对值受影响。

**本轮新增的策略：**

| 策略 | 做法 |
|---|---|
| **HYB:p** | MoE-Infinity 式的请求内使用次数，加上 λ × 预测的期望 decode 使用次数（k × 平均 decode 长度 × p） |
| **公平基线** | HYB:BASE_ADMIT、HYB:RPP（token 先验），用来和 HYB:OURS_ADMIT（检索先验）对比 |
| **SW:p**（E4） | prefill 扫描期间用稳定的全局分数（抗扫描抖动），到第一个 decode 步时改用 HYB:p 的分数重新排序 |
| **MIX\<a\>** | a × ORACLE + (1−a) × GLOBAL，用来画出"预测 recall 与少搬运量"之间的关系 |

所有"相对最好基线"的比较，基线都取所有不用检索信息的非 oracle 策略中最好的一个（LRU、LFU、MOEINF、PRED/HYB/SW 加 GLOBAL/RPP/BASE_ADMIT/PREFILL）。

- **H3 门槛是 20%，实际只有 4–8%：不成立。**
- 一个有意思的副产品：MoE-Infinity 加上 token 先验（HYB:BASE_ADMIT / HYB:RPP），本身就比 MoE-Infinity 少搬约 6–10%。这个收益与检索无关。
- **预测质量和收益之间的关系很陡**：recall@16 从 0.477（我们的）提到 0.505（MIX10），decode 搬运量就能多少约 15 个百分点。要达到 20% 的门槛，大约需要 recall@16 ≥ 0.50，也就是比 GLOBAL 高约 6 个百分点。现在的检索预测器离这个点只差约 3 个百分点。（注意：MIX 是把 oracle 和 GLOBAL 混合得到的，它"答对的地方"正好是最有用的那些 expert，所以这个曲线偏乐观。）
- 队列前瞻（Q=4）在所有配置中都比 Q=0 差或持平：一次只服务一个请求时，为后面的请求预留位置只会挤占当前请求。

### 4.2 加上 prefill 的端到端搬运量（W1）

| 负载 · 容量 | 最好的基线（总 GB/请求） | 其中 decode 占比 | 检索 | 完美的请求级预测（PRED / SW） | Belady |
|---|---|---|---|---|---|
| CWQ · 30% | 150.7（PRED:GLOBAL） | 15% | +1% | +16% / −0% | −13% |
| CWQ · 50% | 101.1 | 12% | +0% | +62% / −1% | −12% |
| WEB · 30% | 150.8 | 18% | +1% | +13% / −1% | −15% |
| WEB · 50% | 99.0 | 14% | +0% | +57% / −2% | −14% |

- **W1 的端到端搬运量里，prefill 扫描占 77–92%**（容量越大，decode 占比越小）。 最好的基线是用稳定的全局热度排序（PRED:GLOBAL 或 SW:GLOBAL），因为它在逐层扫描时不会把常用的 expert 冲掉。

## 5. E4：offload 的 prefill 结束时保留哪些 expert（H4）

指标：decode 前 8 步的未命中次数（每个请求，GLM 每层选 8 个、共 45 层，所以前 8 步最多访问 2880 次）。

| 负载 · 容量 | 最好的非检索基线 | 检索（最好的 OURS 策略） | 完美的请求级预测（PRED / HYB:ORACLE 中较好的） | Belady |
|---|---|---|---|---|
| CWQ · 10% | 768（PRED:BASE_ADMIT） | −4% | −24% | −48% |
| CWQ · 30% | 304（HYB:RPP） | **−7%** | −86% | −98% |
| CWQ · 50% | 138（HYB:RPP） | **−7%** | −90% | −95% |
| WEB · 30% | 329（HYB:BASE_ADMIT） | **−12%** | −83% | −97% |
| WEB · 50% | 144（HYB:RPP） | **−13%** | −90% | −93% |
| W2 · 30% | 957（MOEINF） | +44%（变差） | +22%（变差） | −99% |

- 保留策略本身的空间很大：完美的请求级预测能消除 80–90% 的前 8 步未命中。
- 但检索预测只拿到其中 7–13%。在 W2 上，请求级先验全部有害，连完美的请求级预测也比 MoE-Infinity 差 22%：长 decode 需要的是请求内的时间局部性，而不是整个请求的总体分布。
- 前 8 步的未命中对应的停顿约为 304 × 34.6MB / 54GB/s ≈ 0.19 秒/请求（CWQ，30%），而同一请求的 prefill 扫描本身要 128GB / 54GB/s ≈ 2.4 秒。省下 7% 的前 8 步未命中，大约等于端到端省 0.5%。
- **H4 判定：方向上成立（检索先验确实减少了前几步的等待），但量很小，没有系统意义。**

## 6. E2：准入时按亲和性组 batch（H2）

设置：

- **请求流**：泊松到达，速率为服务能力的 1.5 倍（队列持续存在，准入时总有选择余地）。
- **调度**：continuous batching，batch 上限 Bmax ∈ {8, 32}，缓存用 LRU。
- **准入策略**：FCFS，或者 AFF:p（选与当前 batch 预测分布最相似的等待请求），配合饥饿保护 τ（单位是步）。
- **分组准入**（MoE-Gen 式）：攒够 8 个空位再一起准入，让多个 prefill 共享一次扫描。

### 6.1 W1-CWQ，相对 FCFS（decode tok/s 的变化 / P99 延迟的变化）

| 容量 · Bmax | AFF:BASE_ADMIT | **AFF:OURS_ADMIT** | AFF:ORACLE |
|---|---|---|---|
| 30% · 8，τ=32 | −0% / +0% | +1% / +0% | +1% / +0% |
| 30% · 32，τ=32 | +8% / +20% | **+9% / +20%** | +14% / +26% |
| 50% · 32，τ=32 | −9% / +20% | +4% / +18% | −15% / +26% |
| 30% · 8，τ=∞（不设饥饿保护） | +4% / +132% | +4% / +122% | +10% / +95% |
| 50% · 8，τ=∞ | +5% / +130% | +4% / +121% | +42% / +93% |
| 30% · 32，τ=∞ | −5% / +61% | −7% / +53% | +18% / +57% |

- **整体吞吐（含 prefill）的变化都在 −6% 到 +11% 之间**，即使是 ORACLE、不设饥饿保护，也只有 +3% 到 +11%，而且 P99 延迟会翻倍。
- OURS 和 BASE 的整体吞吐基本一样（差 ≤2 个百分点）；decode tok/s 的差别在不同配置下方向不一（−6% 到 +13%），没有稳定的优势。
- **分组准入**（Bmax 32 时攒够 8 个空位）带来吞吐 +11%（7.20 → 8.00 tok/s），与使用哪种预测无关。这正是 MoE-Gen 已有的做法。
- **W2**：每个请求排队几千秒，饥饿保护一直触发，所有 AFF 策略和 FCFS 结果完全相同。不设饥饿保护时，AFF 也只有 0–8% 的变化，而 P99 延迟翻倍。原因是 batch 里长 decode 请求的 expert 并集几乎就是全部 expert，按相似度挑选也改变不了。

**H2 判定（GLM）：不成立。** 门槛是在相同 P99 下提高 15%；实际只有在 P99 翻倍的代价下，ORACLE 才能提高约 10%，检索预测是 0–4%。

## 7. 总结与建议

| 假设 | 门槛 | GLM 的结果 | 判定 |
|---|---|---|---|
| H1 可预测性 | 比最强的 token 基线高 ≥5 个百分点（4 个模型中至少 2 个）；Wsyn 下至少保留一半 | +1.8（CWQ）/ +3.5（WEB），显著；Wsyn 下 +2.2 | 不成立（GLM）；另外 3 个模型待测 |
| H2 亲和性准入 | 相同 P99 下 ≥15% | 0–4%（ORACLE 约 10%，且 P99 翻倍） | 不成立 |
| H3 前瞻式缓存 | 比最好的非 oracle 基线少搬 ≥20% | decode 少 4–8%，端到端约 0% | 不成立 |
| H4 prefill 后的保留 | （plan 中未定量） | 前 8 步未命中少 7–13%，约等于端到端 0.5% | 方向上成立，没有系统意义 |

**为什么不行：瓶颈在哪里，检索信号就不在哪里。**

- 短答案的 KGQA：瓶颈是 prefill 扫描，而 prefill 本来就要用全部 expert，用不着任何预测。
- 长答案：瓶颈是 decode，但 decode 会用到几乎所有 expert；能利用的是时间局部性（LRU、MoE-Infinity、提前一层 gate），这些都和检索无关。
- 检索信号能起作用的位置是"decode 开始前、请求级的 expert 子集"。这个位置在 W1 上只占 8–23% 的搬运量，而且检索信号在这里也只比 token 基线好 2–3 个百分点。

**建议**：

1. **等 GPU 恢复后，把剩下 3 个模型跑完。** 机器空闲时约需 1–2 天，可以确认 H1 是否在别的模型上也不成立。DeepSeek 和 Qwen3 都是从零训练、更细粒度的 MoE，是 H1 剩下的希望；Mixtral 是由 dense 改造的，预期更差。GLM 的模拟代码现在可以直接复用（`run_sim2.sh <model>`）。
2. **在剩下的模型结果出来之前，就可以先和导师讨论方向。** 如果 Qwen3 和 DeepSeek 也只有 2–3 个百分点，那么"检索信息指导 MoE 调度"作为论文主线就不成立了。可以考虑的转向：
   - **prefill 侧**：多个请求共享一次 expert 扫描（分组准入带来 +11%，但这正是 MoE-Gen 的思路，新意不足）；
   - **回到 attention 侧**：trie 结构的 KV 复用（之前的 exp0–exp4）。检索带来的结构性冗余在那里更直接。
   - 或者把"为什么检索信息帮不了 MoE offload"整理成一个负面结论，作为 proposal 里的一节。
3. 本轮得到的两个与检索无关、但可能有用的观察：
   - MoE-Infinity 加上 token 先验，decode 少搬约 6–10%；
   - 在短答案（W1）上，用全局热度做缓存替换，端到端比 MoE-Infinity 少搬 22–52%，比 LRU 少 29–68%（容量 30–70%），因为它在 prefill 逐层扫描时不会把常用的 expert 冲掉。但在长 decode（W2）上正好相反，MoE-Infinity 和 LRU 要好得多。这说明 offload 系统的缓存策略应该按阶段切换。这对系统实现有参考价值，但它不是"检索"的贡献。
