## 0. 三条线的结论汇总

| 来源 | 成立的 | 不成立 / 需要注意的 |
|---|---|---|
| **Anchor（P0–P3）** | 多层预测：anchor + GATE 在 h=2–8 都最好，anchor 几乎不随 h 衰减。按置信度只预取有把握的 expert 收益最大。同一目标层的预测要前后稳定 | 单用户系统收益只比最强基线好 3–11%；带宽受限时猜错的预取比不预取更糟（浪费 20–46%）；阈值是事后挑的 |
| **Expert queue（Q0、Q1）** | 同步 batching 本身就是最好的"攒批"；H200 微基准给出了可信的时间参数（加载 1 ms 对计算 12.5 µs） | 每个请求独立推进 + 每个 expert 排队：需求被打散，加载翻倍；缓存大时小 batch 的固定开销占满 GPU。带宽饱和时阈值和最长等待不起作用。多用户下，LRU 在"每步按层循环扫描"时会抖动 |
| **缓存感知路由（Q3）** | 缺的 expert 换成常驻的次优 expert：改动 ≤ 约 10% 时，Qwen3 / GLM、短答案 / 长推理都基本不掉；模拟吞吐 ×3.7（缓存 90%）到 ×8.6（缓存 75%）。换成次优始终好于直接丢弃 | GLM 长推理对改动更敏感（改动 26% 时掉 31 pt）；要按"改动比例"而不是"常驻比例"来控制 |
| **Decode 池（A0 + 时间模拟）** | 每步按路由相似性挑 batch：每 token 用到的不同 expert 少 12–27%（上限）；用上一 token 的路由预测，就能拿到其中约 60%；吞吐 +9% 到 +15%（最多比轮转多等 2 步） | 不限等待时 p99 涨 2–3 倍；B 大时并集接近饱和，空间变小 |

**由此确定的框架**：
- 留在**同步 batching** 框架内；
- 改的是四件事：
  - ① 谁一起跑（相似性组 batch）；
  - ② 提前加载什么（anchor 多层预取，只取有把握的）；
  - ③ 缺了怎么办（顶替，不等）；
  - ④ 缓存里放什么（常驻 + 流动）；
- **所有部分都以多用户为最终评估场景**。

## 1. 统一的系统流程

每个 decode 步：

```
(1) 预测   对池子里每个活跃请求，预测它下一个 token 在各层的 expert（anchor；退化时用上一 token 的路由）
(2) 组 batch   从 N 个请求中挑 B 个前进：预测的 expert 并集最小，且没有请求比轮转多等 k 步以上
(3) 逐层执行   到第 l 层：
      a. attention + 路由（整个 batch 一次）
      b. 多层预取：对 l+1..l+H 层，汇总 batch 内各请求的预测
         （置信度 = Σ 请求 × Σ 各次预测的加权置信度），超过自适应阈值且不在缓存里的发出加载；
         冻结窗口内不撤销；被预测到的 expert 受保护
      c. 使用：本层缺的 expert，在改动预算内换成已在缓存的次优 expert；超出预算的才按需加载
      d. 分组矩阵乘法（本层用到的所有 expert 一次算完）
(4) 更新   轨迹池写入新轨迹；常驻区按自己的周期更新；流动区按 LRU 换出
```

**两种硬件场景**：
- **GPU 全驻留**（H200 上 GLM-4.5-Air bf16 全部放在 GPU）：没有加载，(3b) 和 (3c) 不需要。收益只来自 (2)：一步里用到的不同 expert 越少，要读的权重越少，步越快。
- **Offload**（H200 走 PCIe、Mac 走 SSD）：全部组件都起作用。

## 2. 组件设计

### 2.1 预测器

- **多层预测（层内）**：anchor + GATE，第 l 层预测第 l+h 层。
  - 打分 = 投票比例 + β ×［在 GATE 集合中］；
  - 补采 GATE 的打分后，改为 + β × GATE 打分。
- **下一个 token 的预测（步间，组 batch 用）**，要比较的方法：
  - P-prev：上一个 token 的路由（A0 已有，约拿到上限的 60%）；
  - P-anchor：用上一个 token 各层的路由打分在池子里找相似记录，取它们"下一个 token"的路由投票；
  - P-mix：上两者加权。
- **置信度累积**：同一目标层的多次预测按 γ^(h−1) 加权累计。
- **GATE 打分**：重采 trace 时存 GATE-h 的前 16 个 expert 及其打分，使 GATE 也能加阈值，公平比较。

### 2.2 组 batch（相似性挑选）

- **贪心**：先放入强制前进的请求（已经比轮转多等了 k 步），再依次加入"让并集增加最少"的请求。
- **可变 B**：当某个请求加进来使并集增加超过阈值时就停止，B 可以小于上限。
- **公平**：k ∈ {1, 2, 4}，报告 p99 TPOT。

### 2.3 多层预取

- **发出规则**：累计置信度 ≥ τ，且不在缓存、不在队列中。
- **自适应阈值**：τ = τ0 + κ × 排队负载（排队中的 expert 数 / 每层能加载的数量），在 P3 的最优范围 0.5–1.1 内调。
- **队列顺序**：按目标层排序（越近越先），同一目标层内按置信度。
- **冻结窗口**：T − l ≤ d 时不撤销已发出的；新增只允许置信度 ≥ τ_high 的。
- **保护**：被任何尚未执行的目标层预测到的 expert，不论是新读入的还是本来在的，保护到该层执行完。
- **多用户汇总**：batch 内 r 个请求都预测某个 expert 时，置信度相加（需要它的请求越多越值得读）。

### 2.4 使用时顶替（缓存感知路由）

- 第 l 层缺失的 expert：
  - 在**改动预算**内，换成"已在缓存且路由分数最接近"的 expert；
  - 超出预算的才按需加载。
- **预算的形式**（要比较）：
  - 每 token 每层最多 b 个（b ∈ {0, 1, 2}）；
  - 全局改动率上限 ρ_c（2% / 5% / 10%），在线统计，超过就收紧；
  - 按层分配（对改动更敏感的层预算更小，用准确率实验校准）。
- 模拟器里要区分"换成次优 expert"（还要多算一个常驻 expert）和"跳过"（Q1 用的近似）。

### 2.5 缓存：常驻区 + 流动区

- 总容量 C = f × 全部（层, expert），常驻区占 ρ。
- **常驻区**：
  - 按以下方式填：全局频率 / 每层配额 / 负载类型 / 在线滑动平均 / anchor 预测需求；
  - 不参与 LRU 换出，按自己的周期更新。
- **流动区**：
  - 用 LRU，或 LRU + 保护；
  - Q1 里多用户 LRU 抖动的问题，靠常驻区放热门 expert 来避免：流动区只处理近期需求，不再承担整步的工作集。
- **扫描**：ρ ∈ {0, 0.25, 0.5, 0.75, 0.9}，f ∈ {25%, 50%, 75%, 90%}。
- 所有实验统一用这个定义，旧报告里的"缓存 X%"对应 ρ=0 或 ρ=1 的特例。

### 2.6 在线轨迹池

- **写入**：每个 decode token 写入（token id、低维路由打分、各层 expert）。
- **容量和淘汰**：总上限 + 每个 token id 的上限；按效用（被匹配次数 × 预测命中率，带衰减）淘汰；近重复记录合并。
- **匹配加速**：降到 32 / 64 维；按 token 分桶；全局用 IVF / PQ。
- **耗时**：在 Mac / H200 的 CPU 和 GPU 上实测，计入模拟；要求每层每 token 的匹配 < 每层计算时间的 20%。

## 3. 统一的评估设置

- **模拟器**：合并 `tsim_ahead.py`（单用户多层预取）和 `tsim_async.py` 的同步部分（多请求），写成一个 `tsim_mu.py`，单用户是 N = B = 1 的特例。
  - 时间参数：H200 PCIe 用实测微基准；H200 全驻留另加一套（每步时间 = 非 expert 部分 + 分组矩阵乘法按不同 expert 数计）；Mac 用 SSD 的参数。
  - **回归检查**：关掉新组件后，要复现 P3（单用户）和 Q1（同步多用户）的数字。
- **负载**：
  - GLM-4.5-Air bf16 W2c CoT 200 个请求（长 decode，主要负载）；
  - W1 CWQ 500 题（短答案对照）；
  - 补一组 Qwen3-30B-A3B 的长推理 trace（GSM8K 或 thinking 模式），检验结论能否跨模型。
- **准确率评估**：扩展 `subst_accuracy.py`：
  - 除了固定常驻集合，还支持"按模拟器给出的逐步缓存状态 / 改动分布"施加掩码；
  - 任务：CWQ（短）、GSM8K（中等长度），并补一个更长的推理任务（Qwen3 thinking 模式，1000+ token）。
- **指标**：
  - 单用户：每 token 停顿、TPOT、加载次数、浪费比例及来源、改动率、准确率；
  - 多用户：吞吐、p50 / p99 TPOT、每步每层不同 expert 数、GPU / 加载通道利用率。
- **基线**（同一缓存定义下）：
  - 同步 + LRU / LFU；
  - 同步 + 提前 1 层；
  - 同步 + GATE 多层（加阈值）；
  - 同步 + TOK+GATE（加阈值）；
  - 同步 + 只做缓存感知路由；
  - 完美预测（上限）；
  - 参考：原始异步队列方案（Q1 的数字）；
  - **0.1.3 补充的已有方案**（见 `report/2026-10-21-moe-mu-related.md` §3）：
    - Mira 式 HOT + STAGE 分层缓存（对照组件 4）：每 T 步按路由量最多换 s 个 HOT expert；STAGE 放 GATE-2 预测、目标层过后丢弃。在同样总槽数下和"常驻 ρ + LRU"比；
    - Cache-Prior（Skliar 等）的 logit 偏置路由（对照组件 3）：z′ = z + λ·Δ_avg·［已缓存］，保留原 top-J，扫 λ，在相同改动率下和"换成次优 + 改动预算"比。注意 DAOP 的顶替规则和我们的基本相同，组件 3 的新意只在多用户、改动预算和长推理准确率；
    - 组件 1 的对照检查：用 arXiv 2608.07911 的设置（N = 24、B = 8、最多等 4 步、上一 token 路由、贪心最小并集）在我们的 trace 上复现。它报告 miss 只降 4.6–4.8%（oracle 5.9–7.9%），阶段 3 必须正面回应。
- **参数选择**：阈值、κ、γ、预算等，要么自适应，要么在独立校准集上选，不在测试集上事后挑。

## 4. 实验阶段

### 阶段 0：基础（约 2 天）

- `tsim_mu.py`：合并模拟器，统一"常驻 + 流动"缓存定义，加入保护和浪费分解；回归检查 P3 / Q1。
- 重采 trace，存 GATE 打分：GLM W1 CWQ 500 + W2c CoT 50；Qwen3-30B 的长推理 trace。GPU 0–2 中空闲的卡，约 2 小时。
- **产出**：保护和浪费分解后的 P3 更新；"浪费来自早期预测被修正还是最终预测也错"的比例。

### 阶段 1：单用户 offload 的预取改进（约 5 天）

1. 常驻 / 流动分区：扫 ρ × f × 五种填法。
2. 预取机制：置信度累积、冻结窗口、自适应阈值、GATE 加阈值，逐项消融。
3. 使用时顶替：扫改动预算，报告停顿和改动率。
4. 在线轨迹池：容量、淘汰、匹配加速、实测耗时并计入模拟。

**判据**：
- **H1**：在不事后挑参数的前提下，相对"提前 1 层"停顿降 ≥ 30%，同时改动率 ≤ 10%（原 A3）；
- **H2**：浪费比例 ≤ 15%；
- **H3**：池子缩到 20% 时 recall 掉 ≤ 1 pt，匹配耗时 < 每层计算的 20%。

### 阶段 2：顶替的准确率（约 2–3 天，GPU）

- 把阶段 1 最好配置在模拟中的逐步顶替记录回放到真实模型（GLM、Qwen3），测 CWQ / GSM8K / 长推理的准确率。
- 对比按 token / 全局 / 按层的预算形式，找出准确率掉 ≤ 1 pt 时最大的改动率，分模型和任务。
- **判据 H4**：给出每个模型 / 任务的安全改动率；在该改动率下，阶段 1 的吞吐收益至少保留 80%。

### 阶段 3：多用户（约 4 天）

1. **下一 token 预测**（原 A1）：P-prev / P-anchor / P-mix 的 recall；接入 A0 的组 batch，看能拿到上限的多少。
2. **GPU 全驻留**：只做相似性组 batch，扫 N ∈ {32, 64, 128, 200}、B ∈ {8, 16, 32}、k；报告吞吐 vs p99。
3. **Offload 全栈**：逐项叠加，组成消融表（§5），扫 N、B、f、ρ。

**判据**：
- **H5**：GPU 全驻留时，相似性组 batch 在 p99 TPOT 增加 ≤ 20% 的前提下，吞吐 ≥ +10%；
- **H6**：offload 时，全栈在相同 p99 TPOT 下比"同步 + LFU + 只做缓存感知路由"的吞吐再高 ≥ 15%。

### 阶段 4：原型（约 1–2 周，按判据逐步推进）

1. **缓存感知路由**（最简单，只改 router 的掩码）：
   - Mac 的 `offload_engine.py`；
   - H200 的 HF offload（expert 放在锁页内存）。

   实测吞吐和准确率，核对模拟。
2. **加多层预取**：后台加载线程 + anchor 匹配线程。
3. **加相似性组 batch**：多请求调度器。可以先在 Mac 上用 4–8 个本地并发请求，再考虑在 vLLM 里改调度器（GPU 全驻留的场景）。

### 阶段 5：低优先级 / 备选

- **用融合 kernel 重新评估异步方案**：如果 attention 的固定开销降到几十微秒，缓存大时异步方案还输不输。
- **带宽富余时的攒批**：只在加载带宽不饱和的硬件上（例如 NVMe RAID、Grace-Hopper 的 C2C 互联）再评估 queue 的阈值和等待机制。
- **层内的 expert 队列**：仅当阶段 3 显示步间组 batch 之后仍有明显的冷门 expert 等待时考虑。

## 6. 风险

| 风险 | 应对 |
|---|---|
| 顶替的准确率依赖模型和任务（GLM 长推理敏感） | 阶段 2 按模型 / 任务校准安全改动率；运行时在线统计并收紧预算 |
| 多用户时预测并集变大，预取更容易饱和、浪费更多 | 按"需要它的请求数 × 置信度"排序；自适应阈值；组 batch 本身让并集更小 |
| 常驻区固定，长 decode 的时间局部性用不上 | 扫 ρ；常驻区用滑动平均或预测需求慢速更新 |
| 组 batch 让部分请求多等，尾延迟变差 | k 作为硬约束；报告吞吐 vs p99 的完整曲线 |
| 在线池的匹配和写入占 CPU，和调度、加载线程争资源 | 阶段 1 实测；只对部分层或部分 token 匹配 |
| 模拟器过于乐观 | 阶段 4 原型核对；先做最简单、收益最大的缓存感知路由 |
| 和已有工作重合（SwapMoE、AdapMoE、HOBBIT、ProMoE、MoE-Infinity、ExpertFlow 等） | 阶段 0 补查文献，把最接近的方案作为基线；突出多用户 + 组 batch + 改动预算的组合 |
