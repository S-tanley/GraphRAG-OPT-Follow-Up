## 0. 问题

### 0.1 现在的预算是怎么算的

三份实现完全相同：
- 模拟器 `tsim_mu.Subst`
- Mac 原型 `subst_offload.Subst`
- H200 原型 `hf_offload.Subst`

做法如下：
- 维护两个计数：`uses`（expert 使用总次数：每个 token 每过一层加 k）和 `changed`（已换掉的次数）。
- 某个 token 的某一层，按路由权重从小到大，把迟到的 expert（不在缓存里或还在读）换成缓存里分数最高的。最多换
  **min(迟到个数, max(0, ⌊ρ·uses + U⌋ − changed))** 个，U ~ [0, 1)。
- 计数在**每组配置开始时建一次，整组运行中从不清零**。

### 0.2 由此带来的三个性质

| 性质 | 含义 | 后果 |
|---|---|---|
| **跨请求、跨 token 共用一个池子** | 预算按全部请求的使用次数增长，谁迟到谁用 | 多请求并发时，路由"偏"的请求（常用不在缓存里的 expert）会用掉别的请求贡献的额度 |
| **跨时间累积，从不清零** | 没用完的额度一直留着，包括留给后面的请求 | 迟到少的阶段攒下额度，后面某个请求或某一段可以集中被改，局部改动率远超 ρ |
| **只规定顺序，不保护重要的 expert** | "权重从小到大"只在额度不够时起作用 | 额度充足时（缓存大），所有迟到的都被换掉，包括权重最大的 top-1，某一层 8 个 expert 可以全被换掉 |

### 0.3 已有的证据

Mac 单用户、GLM-4.5-Air 4bit、顶替 10%、CoT 20 个请求（`outputs/moe_edge/subst/p41_glm_f{0.5,0.75}_rate0.1/`）：

| | 缓存 50% | 缓存 75% |
|---|---|---|
| 迟到率 vs 预算 | 约 19% > 10%（额度一直不够） | 约 8% < 10%（额度一直在攒） |
| 每个（token, 层）换掉的个数 | 0：35%，1：52%，2：12%，≥ 3：1.4% | 0：57%，1：28%，2：10%，≥ 3：5%，最多 8 |
| 被换掉的是 top-1 的比例 | 3.8% | 8.9% |
| 一层里被换掉的路由权重之和：中位 / p90 / 最大 | 0.10 / 0.22 / 0.88 | 0.13 / 0.34 / 1.00 |
| 各请求的改动率 | 全部 10.0% | **4.2% – 19.5%** |

这还只是单用户（只有跨时间累积）。多用户时，同一步里的其他请求也会贡献额度，集中程度可能更高，但还没测。

### 0.4 为什么重要

- 准确率是按请求算的。阶段 2 的"10% 以内不掉点"（GLM GSM8K、Qwen3 thinking），用的是 emp 模式：
  - 每层的改动率均匀；
  - 换掉第几名，按缓存 50% 时的记录分布抽样（大多是低权重的）；
  - 每个请求被均匀地改。
- 所以那个结论**覆盖不了**两种情况：
  1. 缓存 ≥ 75% 时"所有迟到都换、包括 top-1"；
  2. 改动集中到少数请求上。
- H200 原型在真实决定下测过一次准确率（Qwen3，75% 缓存，.891 对 .875，64 题），但实际改动只有约 2%，说明不了问题。

## 1. 要回答的问题

- **Q1 集中程度**：在实际运行中，各请求的改动率、每个（token, 层）的改动个数、被换掉的名次分布是什么样？比较单用户、4 并发和多用户（N 64 / 128），以及缓存 50 / 75 / 90%。
- **Q2 准确率**：全局改动率相同时，"集中的、可能换掉 top-1 的改动"是否比"均匀的、只换低权重的改动"更伤准确率？
- **Q3 预算形式**：哪种预算形式能把单个请求的风险限制住，同时吞吐损失最小？

## 2. 候选的预算形式

三份实现都要支持，语义完全一致（扩展 `test_subst_rule.py` 核对）：

| 编号 | 形式 | 规则 | spec（建议） |
|---|---|---|---|
| B0 | 现状 | 全局、累积、不清零 | `rate:ρ` |
| B1 | 按请求 | 每个请求一套 `uses` / `changed`，请求开始时清零；多用户时每个流各自一套 | `req:ρ` |
| B2 | 按请求 + 每层上限 | B1，且每个（token, 层）最多换 b 个 | `req:ρ:tok:b` |
| B3 | 按请求 + 保护重要 expert | B1，且路由权重排前 r 名（或权重 > w0）的 expert 永不换，迟到了就读 | `req:ρ:keep:r` |
| B4 | 限制累积 | 全局，但额度最多攒 c 个 token 的量：changed ≥ ρ·uses − c·L·k·ρ | `rate:ρ:bank:c` |

另外报告 B2 + B3 的组合。参数先取 b = 2、r = 1 或 2、c = 1，Phase B 再扫。

## 3. 实验

### Phase A：测集中程度（CPU，约半天）

- 三份 `Subst` 都加按请求的统计：每个请求的 `uses` / `changed`；每个（token, 层）改动个数的直方图；被换掉的名次（按路由权重）直方图；被换掉的权重之和的分布。
  - 汇总：各请求改动率的 p50 / p90 / max，top-1 / top-2 被换的比例。
- 数据来源：
  - 模拟器 pool 模式（GLM CoT，同 `p33d` 的非泄漏设置：N 64 / 128，B 16 / 32，缓存 50 / 75 / 90%，H200 / Mac 参数）；
  - seq 模式（单用户）；
  - Mac 原型已有的轨迹（单用户）可直接统计。Mac 4 并发要补存轨迹（`subst_offload_batch.py` 加记录）。
- 产出：`report/2026-10-xx-subst-budget-A.md` 的表；回答 Q1。

### Phase B：吞吐代价（CPU 模拟 + Mac 原型，约 1 天）

- 模拟器：B0–B4 × ρ ∈ {5, 10, 15%} × 缓存 50 / 75 / 90% × 单用户 / pool（N 64 / 128，B 16 / 32）× `mac_ssd_cal` / `h200_pcie`。报告吞吐（或 TPOT）相对 B0 的比值，以及 Phase A 的集中程度指标。
- Mac 原型：选 2–3 种形式，单用户和 4 并发，缓存 50 / 75%，实测 TPOT / 吞吐，并用模拟器核对（同 4.1.3）。
- 产出：吞吐代价表；回答 Q3 的"成本"一半。

### Phase C：真实决定下的准确率（GPU，需要你确认 GPU 时间）

- **方法**：不用 emp 抽样，改为"在线模拟缓存"。在全驻留的真实模型上生成，同时维护一个模拟的缓存：
  - 每层的池大小按校准频率分配，预填，LFU；不预取时加载是同步的，所以"迟到" = 不在缓存里。
  - 每步按所选预算形式实时做顶替决定，再施加到路由上。
  - 这样准确率对应的就是实际系统会做的决定，包括集中和 top-1 被换的情况。
  - 实现：扩展 `subst_replay.py` 增加 `cache` 模式。
- **对照**：同一全局改动率下，emp 均匀模式（阶段 2 的做法）。
- **任务**：
  - GLM-4.5-Air GSM8K 200 题（thinking 关）；
  - Qwen3-30B-A3B GSM8K thinking 200 题（第 50–249 题，前 50 题是校准用的轨迹）；
  - 可选：GLM CoT（Hit 太低，只看"答案相同"的比例）。
- **配置**：缓存 50% / 75% × {B0, B1, B2 + B3} × ρ = 10%（加一组 15%），加不顶替的基线。
- **分析**：逐题配对（`subst_flips.py`）；把每个请求的实际改动率和"对变错"关联起来，看改得多的请求是否更容易错。
- **GPU 估计**：Qwen3 每组约 25–50 分钟（含顶替判断的 CPU 开销），GLM 每组约 10–20 分钟（两张卡）；合计约 6–10 小时。**开始前问你。**
- 产出：回答 Q2 和 Q3 的"收益"一半。

## 4. 判据

- **H-A**：B0 下，至少有一种设置出现单请求改动率 > 1.5ρ，或 top-1 被换的比例 > 5%。现有数据（Mac 75%：19.5%，8.9%）已经倾向成立，Phase A 补齐多用户。
- **H-B**：存在一种形式（B1–B4 或组合），满足 §3 Phase D 的三条标准。
- **H-C**：同一全局改动率下，B0 的"集中改动"比 emp 均匀改动的对变错更多（配对差 ≥ 2 pt，或改动率高的请求明显更容易对变错）。不成立也是有用的结论：说明集中本身不伤准确率。

## 5. 风险

| 风险 | 应对 |
|---|---|
| 200 题分辨不出 1–2 pt 的差别 | 用"对变错"与单请求改动率的关联，比只看总准确率更灵敏；必要时扩到 500 题（再问你） |
| 按请求的预算让多用户的吞吐明显下降（不能借额度） | B4（限制累积）是折中；Phase B 量化 |
| 保护 top-r 后，缓存 ≥ 75% 时"不再加载"的现象消失 | 这正是要量化的取舍：吞吐 vs 风险。Phase B 报告加载次数 |
| "在线模拟缓存"忽略了预取的时间（预取在路上也算迟到） | Phase C 只测不预取的配置，此时同步加载与模拟完全一致；预取的情况另外说明 |
