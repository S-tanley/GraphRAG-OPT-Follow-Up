## 0. 现在在哪里

| 已有结果 | 数字 |
|---|---|
| 预测准确率（P2） | anchor + GATE 在 h=2–8 都最好；h=3 时比 GATE 高 5.8 pt，h=8 高 16–17 pt；anchor 单独几乎不随 h 衰减 |

**P3 留下的问题**：
- 缓存内容完全由 prefill 遗留和动态换出决定，没有结构；
- 被预测到、但已在缓存里的 expert 没有保护；
- 新预测完全覆盖旧预测，临近目标层时还在来回改；
- 预取没赶上时只能等；
- 池子是离线、静态、未优化的，匹配耗时也没算；
- 阈值是事后挑的；
- GATE 没存分数；
- 三份报告的"缓存 X%"定义不一致；
- 只做了单用户。

## 1. 这一轮要做的改动

| 编号 | 来源 | 改动 |
|---|---|---|
| **C1** | 想法 1 | 缓存分成**常驻区**（按历史 / 预测信息填，较少变动）和**流动区**（按需加载和换出），扫描两者的比例和常驻区的填法 |
| **C2** | 想法 2 | **保护被预测到的常驻 expert**：已在缓存、且被某个尚未执行的目标层预测到的 expert，保护到该层算完 |
| **C3** | 想法 3 | **冻结窗口**：离目标层 ≤ d 层时，已发出或已读入的预取不再撤销；新出现的 expert 只在置信度很高时才追加 |
| **C4** | 想法 3 | **使用时顶替**：到第 l 层发现要用的 expert 不在（预取没赶上），换成常驻 / 已在的、路由分数最接近的 expert，不等待；设改动预算 |
| **C5** | 想法 4 | **在线轨迹池**：decode 和 prefill 持续写入新轨迹；按效用（被匹配并命中的次数）淘汰；限制容量；匹配要加速并计入耗时 |
| **C6** | P3 报告 §5 | 自适应阈值（按加载队列的拥挤程度调）；采集 GATE 打分并给 GATE 也加阈值（公平性）；测匹配开销 |
| **C7** | 讨论 | **多次预测的置信度累积**：同一目标层的 H 次预测加权累计，越近权重越大 |
| **C8** | 讨论 | **浪费分解统计**：浪费的加载来自"早期预测被修正"还是"最终预测也错了" |
| **C9** | 讨论 | 统一三份报告的缓存定义：以后都用 C1 的"常驻 + 流动"表述 |
| **C10** | 讨论 | **多用户**：batch decode、decode 池按相似性挑请求、缓存感知路由，三者和 anchor 预取叠加 |

## 2. 设计细节

### 2.1 缓存分区（C1、C2、C9）

- 总容量 C（占全部（层, expert）的比例 f），分成**常驻区** R = ρ·C 和**流动区** D = (1−ρ)·C。
- **常驻区的填法**（要比较的选项）：

  | 选项 | 内容 | 更新频率 |
  |---|---|---|
  | R-glob | 校准集上全局使用频率最高的（层, expert） | 固定 |
  | R-layer | 每层各取频率最高的若干个（层间配额，按每层的缺失代价分配） | 固定 |
  | R-work | 当前负载类型（短答案 / CoT）的频率 | 按负载切换 |
  | R-ema | 在线指数滑动平均的使用频率 | 每 N 个 token 刷新一次，换入换出一小部分 |
  | R-pred | 由 anchor 池在当前一批请求上的预测需求决定 | 每个请求或每段 |

- **流动区**：存放预取和按需加载的 expert，用 LRU 或 MoE-Infinity 式换出。被保护的 expert（C2：被预测、目标层未执行）不换出。流动区满且只剩受保护的 expert 时，放弃新的低置信度预取。
- **常驻区不参与换出**，只按上表各自的更新频率替换。
- **扫描**：
  - ρ ∈ {0, 0.25, 0.5, 0.75, 0.9}（ρ=0 就是 P3 的纯动态缓存）；
  - f ∈ {25%, 50%, 75%}；
  - 上面五种填法。
- **参考**：用户提到"有一篇论文是常驻 + 流动"。候选包括 SwapMoE、AdapMoE、HOBBIT、MoE-Infinity、ProMoE 中的相关设计，需要先查清楚出处，作为基线（`待办`）。

### 2.2 预测、预取和顶替（C3、C4、C6、C7、C8）

在第 l 层，对目标层 T = l+h（h = 1..H）：

1. **累积置信度**（C7）：每个 expert e 的置信度 = Σ_h w(h) × score_h(e)，其中 w 随 h 减小而增大（例如 w(h) = γ^(h−1)），每次新预测都更新。这里的 score 用 AVG 的打分（投票比例 + 0.5 × [在 GATE 集合中]），GATE 有分数后也可换成 GATE 的打分。
2. **发出规则**：置信度 ≥ 阈值 τ、不在缓存、也不在队列里的，发出预取（按目标层排序的队列）。
3. **自适应阈值**（C6）：τ 是加载队列预计等待时间的函数。例如 τ = τ0 + κ × (排队 expert 数 / 每层可加载数)，在 P3 的最优阈值范围（0.5–1.1）内调。
4. **冻结窗口**（C3）：T − l ≤ d 时：
   - 已发出或已读入的不撤销；
   - 新出现的 expert 只有在置信度 ≥ τ_high 时才追加；
   - d 扫描 {0, 1, 2, 3}，d=0 就是 P3 的"完全覆盖"。
5. **保护**（C2）：被任何未执行的目标层预测到的 expert，不论是新读入的还是本来就在的，都保护到该层执行完。
6. **使用时顶替**（C4）：第 l 层执行时，缺失的 expert：
   - 若缺失数 ≤ 本层的改动预算 b，换成**已在缓存**的 expert 中路由分数最接近的，不等待；
   - 否则照常按需加载。
   - b 按 token 计，例如每 token 每层最多换 1 个；也可以设整体改动率上限，例如 5% / 10%，依据准确率实验"≤ 约 10% 安全"的结论。
   - 统计实际改动率。
7. **浪费分解**（C8）：每次浪费的加载记录：来自第几次预测（h）、后来是否被更新的预测撤掉、是否是最终预测也错了。

### 2.3 在线轨迹池（C5）

- **写入**：decode（以及可选的 prefill）每完成一个 token，把（token id，各层路由打分的低维表示，各层的 expert 选择）写入池子。
- **容量**：总上限 P_max（例如 1 万、5 万、20 万）；每个 token id 设上限 M。
- **淘汰**：按效用分数（被选为前 m 近邻的次数 × 这些匹配后来预测命中的比例，随时间衰减），低分先淘汰；新写入的记录有一段保护期。
- **去重 / 聚类**：同一 token id 下非常相似的记录（余弦 > 0.98）合并为一条，并累计它们的投票分布。
- **冷启动**：开始时只用离线池（Wtrain），在线写入逐步替换；比较"只离线 / 只在线 / 混合"。
- **匹配加速**：
  - 128 维路由打分降到 32 / 64 维（PCA 或随机投影）；
  - 只在同 token id 的桶里精确搜索（候选少时退回全局）；
  - 全局搜索用 IVF 或 PQ（faiss）。
- **匹配耗时**：在 Mac（CPU / GPU）和 H200（CPU / GPU）上实测每层每 token 的匹配时间，要求 < 每层计算时间的 20%（Mac 约 0.1 ms，H200 约 0.02 ms）。把这个耗时计入模拟器。
- **验证"池子大部分没用"**：统计每条记录被匹配的次数分布，找出用 10% / 20% 的池子能保留多少准确率。

## 3. 实验步骤

### S0：基础修正和补数据（约 1 天，CPU，另需约 1 小时 GPU）

- 模拟器 `tsim_ahead.py` 加入 C2（保护被预测的常驻 expert）和 C8（浪费分解），用 P3 的设置重跑，看各自带来多少变化。
- 统一缓存定义（C9）：模拟器支持常驻区 + 流动区；ρ=0 时结果和 P3 一致（回归检查）。
- **补采 GATE 的打分**（C6）：`collect_traces_v2.py` 加存 GATE-h 的前 16 个 expert 及其分数；用 GPU0/1 重采 W1 CWQ 500 题 + W2c CoT 前 50 个请求，约 1 小时。
- **产出**：P3 结果在保护和浪费分解下的更新版本；"浪费来自哪里"的比例。

### S1：常驻 / 流动分区（约 1 天，CPU）

- 扫描 ρ × f × 五种常驻区填法，叠加 P3 最好的预取策略（AVG + 阈值）和最强基线（不预取、提前 1 层、GATE 多层、TOK+GATE 加阈值）。
- 负载：W2c CoT 50 个请求（主要），W1 CWQ 500 题（对照）。
- 硬件：Mac 4bit SSD、H200 bf16 PCIe。
- **判据 V1**：存在 ρ > 0 的配置，比 P3 最好的纯动态配置再降 ≥ 10% 的停顿。

### S2：预测和预取机制（约 1.5 天，CPU）

- 在 S1 最好的分区上，依次加入：
  - 累积置信度（γ ∈ {0.5, 0.7, 1.0}）；
  - 冻结窗口（d ∈ {0, 1, 2, 3}）；
  - 自适应阈值（κ 扫描）；
  - GATE 加阈值（S0 补的打分）。
- 做消融，每一项单独去掉，看贡献。
- **判据 V2**：
  - 不依赖事后挑阈值，自适应阈值能拿到"事后最优阈值"效果的 ≥ 80%；
  - 浪费比例降到 ≤ 15%。

### S3：使用时顶替（约 1.5 天，模拟 + GPU 准确率）

- **模拟**：S2 的配置 + C4，扫描改动预算（每 token 每层 0 / 1 / 2 个，或整体 2% / 5% / 10%），报告停顿、TPOT 和实际改动率。
- **准确率**：把模拟里实际发生的"顶替事件分布"（哪些层、哪些 expert、多少比例）施加到真实模型上，测 GLM-4.5-Air 和 Qwen3-30B 在 CWQ 和 GSM8K 上的准确率。实现上用 `subst_accuracy.py` 的路由补丁，但掩码不再是静态常驻集合，而是模拟器给出的逐步缓存状态，或者按模拟器统计出的每层改动率随机施加。
- **判据 V3**：改动率 ≤ 10% 时，准确率下降 ≤ 1 pt；相对"提前 1 层"，停顿降 ≥ 30%（也就是原 A3 的判据）。

### S4：在线轨迹池（约 2 天，CPU + 实测匹配耗时）

- 实现 C5：写入、容量、效用淘汰、去重、匹配加速。
- 离线评估 recall@k vs 池容量（1 万 / 5 万 / 20 万）和淘汰策略；在线 vs 离线 vs 混合。
- 在 Mac 和 H200 上实测匹配耗时：numpy 精确、按 token 分桶、faiss IVF / PQ，各在 CPU / GPU 上。
- 把匹配耗时和在线池接入模拟器，重跑 S2 / S3 的最佳配置。
- **判据 V4**：
  - 池容量缩小到 20% 时，recall 的下降 ≤ 1 pt；
  - 每层匹配耗时 < 每层计算时间的 20%，计入后系统收益保留 ≥ 80%。

### S5：多用户（约 2–3 天，CPU；可选 GPU 原型）

- 把单用户的 `tsim_ahead.py` 和多请求的 `tsim_async.py`（同步框架）合并成一个多用户模拟器：
  - batch 内各请求的预测并起来作为目标层的预取集合，置信度按"需要它的请求数 × 各自的置信度"汇总；
  - 常驻 / 流动分区、保护、冻结窗口、顶替都在 batch 层面生效；
  - 叠加 decode 池的相似性挑选（A0：每步挑 B 个路由相近的请求）。
- 扫描 N ∈ {16, 64, 128}、B ∈ {8, 16, 32}、缓存 50% / 75% / 90%。报告吞吐 vs p99 TPOT 曲线。
- **对照**：
  - 同步 batching + LRU / LFU；
  - 同步 + 提前 1 层；
  - 同步 + 缓存感知路由（不预取）；
  - 逐项叠加：相似性挑选 → anchor 预取 → 顶替。
- **判据 V5**：在相同 p99 TPOT 下，吞吐比"同步 + LFU + 缓存感知路由"再高 ≥ 15%。

### S6：原型（S3 或 S5 的判据成立时再做，约 3–5 天）

- Mac：在 `offload_engine.py` 上加入常驻 / 流动分区、anchor 预测线程（在线池 + 匹配）、多层预取队列和使用时顶替；单用户和 4–8 个本地并发请求，实测 TPOT 和准确率。
- H200：PCIe offload 的 HF 或 vLLM 原型（可选）。

## 4. 指标

- **单用户**：每 token 停顿、TPOT、每 token 加载次数、浪费比例及其分解、实际改动率、准确率（CWQ Hit@1、GSM8K）、匹配耗时。
- **多用户**：吞吐、p50 / p99 TPOT、GPU / 加载通道利用率、batch 内每层不同 expert 数。
- **基线**统一为：不预取、提前 1 层、GATE 多层（加阈值）、TOK+GATE（加阈值）、完美预测（上限），在同一缓存定义下。所有阈值或参数要么自适应，要么在独立的校准集上选定，不在测试集上事后挑。

## 5. 风险

| 风险 | 应对 |
|---|---|
| 常驻区固定后，长 decode 的时间局部性用不上（P3 中长 decode 时 LRU 最好） | R-ema 和 R-pred 让常驻区缓慢更新；扫描 ρ，找到常驻和流动的平衡点 |
| 冻结窗口使错误预测无法纠正，浪费上升 | 窗口内仍允许高置信度追加；用浪费分解（C8）监控 |
| 顶替的准确率依赖任务（GLM 长推理对改动更敏感） | 设改动预算，并按模型 / 任务校准；S3 用模拟器给出的真实顶替分布测准确率 |
| 在线池写入和匹配本身吃 CPU，和检索、调度争资源 | S4 实测；必要时只对部分层或部分 token 做匹配 |
| 多用户时 batch 的预测并集变大，预取更容易饱和 | 按"需要它的请求数 × 置信度"排序，配合自适应阈值；decode 池的相似性挑选让并集更小 |
| 模拟器和真实系统的差距 | S6 原型核对 |
