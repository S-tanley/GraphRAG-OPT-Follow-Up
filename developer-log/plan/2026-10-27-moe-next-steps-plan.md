## 0. 现在的定位

**场景**：个人工作站，单用户或低并发（N ≤ 8，主要看 B = 1 和 B = 4），模型放不进快内存，expert 要 offload。两类硬件：
- Mac（统一内存 + 内置 SSD）；
- 单张 GPU + 主机内存（PCIe）。

**瓶颈**：
> 停顿 ≈ max(0, 每 token 读的次数 × 每次读的时间 − 每 token 的计算时间) + 预测错的额外读

- 缓存 25–50% 时，读的总时间大于计算，完美预测也越不过这个下界。
- 降停顿只有三条路：
  1. **少读**：读的次数更少，或者每次读的字节更少；
  2. **读得快**：提高有效带宽，降低每次读的固定开销；
  3. **藏起来**：和计算重叠，也就是预测 + 预取。

**已知的结论**：

| 杠杆 | 已有的做法 | 状态 |
|---|---|---|
| 少读（次数） | 使用时顶替，改动 ≤ 10% | 有效。Mac TPOT −46% / −58%。准确率没掉，但只在"按统计随机扰动"下测过，不是真实系统的决定（§D11）；预算形式也有问题（§D1） |
| 少读（字节） | – | 没做（§D4） |
| 读得快 | – | 没做。Mac 有效带宽只有峰值的 10–60%，每次读另有约 0.66 ms 主机开销（§D3） |
| 藏起来 | 校准 GATE + 自适应阈值 | 只在缓存 ≤ 50% 时有用（Mac 原型 −14–20%），75% 时有害 |
| 预测器本身 | anchor（kNN 轨迹匹配） | 不顶替时比校准 GATE 只好 0.1–4.4%；加顶替后模拟里多降 3–14%。但池子的内存和搜索时间都没算（§D10），不作为主线 |

**数据的局限**：系统结果几乎都来自同一个数据集 CWQ，一种不开 CoT（W1，约 5.6 token / 请求），一种开 CoT（W2c，约 1,000 token / 请求）；GSM8K 主要用来测准确率。已经看到负载会改变最佳策略（短答案上 MoE-Infinity 式淘汰好得多，长推理上 LRU 更好）。只用一种负载，很容易过拟合（§D9）。

**论文的思路（2026-10-28 和导师讨论后）**：以**预测**为主线，讲清它的 limitation，再引出另外两条线，形成一个因果链：
1. **刻画**：offload 时 decode 被读 expert 卡住；已有方法都靠预测提前读。
2. **预测**：把预测做到最好（多层、校准、按负载自适应；和 FineMoE / ProMoE 同条件比）。
3. **limitation**：带宽受限时预测有算得出来的下界（停顿 ≥ 读的总时间 − 计算时间），提前多层、更准也越不过去（§D13）。
4. **少读 + 读得快**：用预测去决定"不读谁"（顶替，§D1 / D2 / D12）和"怎么读"（并行、合并读取，§D3），把系统从带宽受限推进到延迟受限的区域。
5. **深层预测重新变得关键**：在延迟受限的区域（单次读很慢、但能同时读很多），能否提前很多层、甚至提前一个 token 准确预测，直接决定性能；这是 anchor 最可能明显赢的地方（§D13 A6）。

原来的"按硬件、模型、负载动态选策略"（§D6）在这个 story 里变成支撑的一部分（自适应），不再是主线。

## 2. 各方向

### D1 顶替的改动预算（原 `subst-budget-plan` 的全部内容）

#### D1.0 问题

**现在的预算怎么算**。三份实现完全相同（模拟器 `tsim_mu.Subst`、Mac 原型 `subst_offload.Subst`、H200 原型 `hf_offload.Subst`）：
- 维护两个计数：`uses`（expert 使用总次数：每个 token 每过一层加 k）和 `changed`（已换掉的次数）。
- 某个 token 的某一层，按路由权重从小到大，把迟到的 expert（不在缓存里或还在读）换成缓存里分数最高的。最多换 **min(迟到个数, max(0, ⌊ρ·uses + U⌋ − changed))** 个，U ~ [0, 1)。
- 计数在**每组配置开始时建一次，整组运行中从不清零**。

**由此带来的三个性质**：

| 性质 | 含义 | 后果 |
|---|---|---|
| **跨请求、跨 token 共用一个池子** | 预算按全部请求的使用次数增长，谁迟到谁用 | 多请求并发时，路由"偏"的请求（常用不在缓存里的 expert）会用掉别的请求贡献的额度 |
| **跨时间累积，从不清零** | 没用完的额度一直留着，包括留给后面的请求 | 迟到少的阶段攒下额度，后面某个请求或某一段可以集中被改，局部改动率远超 ρ |
| **只规定顺序，不保护重要的 expert** | "权重从小到大"只在额度不够时起作用 | 额度充足时（缓存大），所有迟到的都被换掉，包括权重最大的 top-1，某一层 8 个 expert 可以全被换掉 |

**已有的证据**。Mac 单用户、GLM-4.5-Air 4bit、顶替 10%、CoT 20 个请求（`outputs/moe_edge/subst/p41_glm_f{0.5,0.75}_rate0.1/`）：

| | 缓存 50% | 缓存 75% |
|---|---|---|
| 迟到率 vs 预算 | 约 19% > 10%（额度一直不够） | 约 8% < 10%（额度一直在攒） |
| 每个（token, 层）换掉的个数 | 0：35%，1：52%，2：12%，≥ 3：1.4% | 0：57%，1：28%，2：10%，≥ 3：5%，最多 8 |
| 被换掉的是 top-1 的比例 | 3.8% | 8.9% |
| 一层里被换掉的路由权重之和：中位 / p90 / 最大 | 0.10 / 0.22 / 0.88 | 0.13 / 0.34 / 1.00 |
| 各请求的改动率 | 全部 10.0% | **4.2% – 19.5%** |

这还只是单用户（只有跨时间累积）。多用户时，同一步里的其他请求也会贡献额度，集中程度可能更高，但还没测。

**为什么重要**：
- 准确率是按请求算的。阶段 2 的"10% 以内不掉点"（GLM GSM8K、Qwen3 thinking），用的是 emp 模式：每层的改动率均匀；换掉第几名，按缓存 50% 时的记录分布抽样（大多是低权重的）；每个请求被均匀地改。
- 所以那个结论**覆盖不了**两种情况：(1) 缓存 ≥ 75% 时"所有迟到都换、包括 top-1"；(2) 改动集中到少数请求上。
- H200 原型在真实决定下测过一次准确率（Qwen3，75% 缓存，.891 对 .875，64 题），但实际改动只有约 2%，说明不了问题。

#### D1.1 要回答的问题

- **Q1 集中程度**：实际运行中，各请求的改动率、每个（token, 层）的改动个数、被换掉的名次分布是什么样？比较单用户、4 并发和多用户（N 64 / 128），以及缓存 50 / 75 / 90%。按现在的低并发定位，**单用户和 4 并发优先**，N 64 / 128 作为补充。
- **Q2 准确率**：全局改动率相同时，"集中的、可能换掉 top-1 的改动"是否比"均匀的、只换低权重的改动"更伤准确率？
- **Q3 预算形式**：哪种预算形式能把单个请求的风险限制住，同时吞吐损失最小？

#### D1.2 候选的预算形式

三份实现都要支持，语义完全一致（扩展 `test_subst_rule.py` 核对）：

| 编号 | 形式 | 规则 | spec（建议） |
|---|---|---|---|
| B0 | 现状 | 全局、累积、不清零 | `rate:ρ` |
| B1 | 按请求 | 每个请求一套 `uses` / `changed`，请求开始时清零；多用户时每个流各自一套 | `req:ρ` |
| B2 | 按请求 + 每层上限 | B1，且每个（token, 层）最多换 b 个 | `req:ρ:tok:b` |
| B3 | 按请求 + 保护重要 expert | B1，且路由权重排前 r 名（或权重 > w0）的 expert 永不换，迟到了就读 | `req:ρ:keep:r` |
| B4 | 限制累积 | 全局，但额度最多攒 c 个 token 的量：changed ≥ ρ·uses − c·L·k·ρ | `rate:ρ:bank:c` |

另外报告 B2 + B3 的组合。参数先取 b = 2、r = 1 或 2、c = 1，Phase B 再扫。B3 的 `keep:r` 也是 D2 要用的。

**Phase C：真实决定下的准确率**（GPU，开始前问）

> 测量框架和对照方法统一放在 §D11（这里用的是 D11 的 L1 层级）。D1 Phase C 是 D11 的第一部分，只做选预算形式需要的那几组。

#### D1.4 判据

- **H-A**：B0 下，至少有一种设置出现单请求改动率 > 1.5ρ，或 top-1 被换的比例 > 5%。现有数据（Mac 75%：19.5%，8.9%）已经倾向成立，Phase A 补齐 4 并发和多用户。
- **H-B**：存在一种形式（B1–B4 或组合），满足 Phase D 的三条标准。
- **H-C**：同一全局改动率下，B0 的"集中改动"比 emp 均匀改动的对变错更多（配对差 ≥ 2 pt，或改动率高的请求明显更容易对变错）。不成立也是有用的结论：说明集中本身不伤准确率。

| 风险 | 应对 |

### D2 预取和顶替的联动（2026-10-27 新增）

#### D2.0 现在的规则（模拟器 `tsim_mu.py` 和 Mac 原型 `prefetch.py` 一致）

- **每层都重新预测**：在第 n 层，对 n+1 … n+8 每层各出一个新预测，替换这一层之前的预测（`Engine.lookahead`）。
- **一条读取通道**：需求读最优先，预取按目标层由近到远排队。
- **预测变了时**：

  | 情况 | 处理 |
  |---|---|
  | 被去掉的 expert 还在排队、没开始读 | 撤销 |
  | 正在读 | 读完（不能中途打断） |
  | 已经读完 | 留在缓存，在目标层跑完前不换出；不会重读，也不会退回 |
  | 新加的 expert 不在缓存里 | 只要过阈值就按目标层排进队列 |

- **目标层执行时**（打开顶替）：没在缓存、或还没读完的 expert 算迟到（`Subst.apply`，`slack` 默认 0），在预算内从权重最小的开始换成缓存里分数最高的；被换掉的若还在排队就撤销，正在读的继续读完（这部分白读）。
- 带宽紧时队列很长（缓存 25% 时排队约等于 16–32 层的读取时间，50% 时 4–16 层），远处目标层的预测在被读到之前会被改好几次，实际读出去的多是离目标层很近时的预测。

#### D2.1 和阶段 1.2 的"冻结窗口"的区别

阶段 1.2 的冻结窗口（`:d<d>:x<τ_high>`）在离目标层 ≤ d 层时做两件事：
1. **已排队的一个都不撤销**；
2. 新加的必须置信度 ≥ τ_high。

而且是**在没有顶替的情况下**测的，结果更慢 1–15%，主要是第 1 条造成的：近处的预测更准，本该撤掉的错误读被强制读完。

**这次的想法正好相反**：
- 撤销规则不变：没读的照常按新预测改；
- 已读完的不管；
- 离目标层很近时才冒出来的新 expert，除非很有把握，否则不读，留给顶替；
- 但顶替不能换掉太重要的 expert（权重 top-r），那些迟到了必须读。

所以阶段 1.2 的"冻结有害"不适用于这个想法，需要单独测。

#### D2.2 为什么可能有用

- 离目标层只剩 1–2 层才冒出来的 expert 大多来不及读完。在 Mac 上读一个约要 1.6 ms 等待 + 0.66 ms 主机开销，而算一层只要 0.79 ms，到时候它还是迟到，要么被顶替，要么让计算干等。
- 阶段 0：只在提前 1 层时才排进队列的读浪费率最高（15–66%）。
- 不读它们，带宽能留给更有把握的预取和需求读。

**代价**：少读的这些 expert 更可能迟到，会多用顶替额度；额度用完后剩下的只能现读。本质是**拿改动额度换带宽**：额度宽松时（缓存 75%）大概率划算，额度紧时（缓存 25%、ρ 5%）可能变差。

#### D2.3 变体

| 编号 | 预取侧 | 顶替侧 | spec（建议） |
|---|---|---|---|
| V0 | 现在的最终配置：校准 GATE 自适应 + LRU（`ah8:GATEs:m8:p0.7:kl0.05`，或 CoT 子集选的） | B0 或 B1 | – |
| V1 | 离目标层 ≤ d 层（d = 1, 2）时，**不在上一次预测里的新 expert** 需要置信度 ≥ τ_high 才排队（τ_high ∈ {0.9, 0.95, 0.99, ∞}；∞ = 晚到的一律不读）；撤销规则不变 | 同 V0 | `:lg<d>:x<τ_high>` |
| V2 | 同 V1 | 加 B3 `keep:r`（r = 1, 2）：权重 top-r 的迟到 expert 不换，必须读 | V1 + `keep:r` |
| V3 | 同 V1 | V2 + 在途等待：迟到 expert 若正在读、且 ≤ s 内就绪，就等它而不换（s = 0、0.25、0.5 × 单次读时间） | V2 + `slack<us>` |

- `:lg` 是新选项，旧的 `:d` 保持不变（可复现阶段 1.2）。
- `slack` 在 `Subst` 里已有，先核对它的语义是否就是"在途且 s 内就绪就等"。

#### D2.4 实验

- **模拟器**（CPU，约半天）：
  - seq（单用户）+ pool（N = B = 4）；
  - `mac_ssd_cal`、`mac_ssd_cal_all`（框住主机开销的两种算法）、`h200_pcie`；
  - 缓存 25 / 50 / 75%；ρ 5 / 10%；
  - GLM CoT 前 50 个请求测试，第 51–72 个请求选参数（不泄漏）。
- **指标**：TPOT / 停顿、每 token 读几次、预取浪费、白读的在途读、全局和单请求改动率（p90 / max）、top-1 被换的比例。
- **Mac 原型**（如果模拟里有收益）：在 `prefetch.py` + `subst_offload.py` 实现最好的变体，单用户和 4 并发、缓存 50 / 75%，实测并用模拟器核对。

#### D2.5 判据

- **H-D2**：存在一个变体，在改动率不高于 V0 时 TPOT 再降 ≥ 5%；或者 TPOT 相同时，单请求最大改动率或 top-1 被换比例明显更低（例如 top-1 被换降到 ≤ 1%）。
- 如果只在缓存 75% 时成立，也是有用的结论：可以作为 D6 策略选择里的一条规则。

### D3 读得快：主机开销和有效带宽（候选）

**动机**：
- Mac 原型缓存 50% 时，每 token 约 102 ms 等读盘 + 约 42 ms 主机开销（每次读约 0.66 ms，来源不明）。
- profiling 里有效读盘带宽只有 1–5.5 GB/s，峰值约 9 GB/s，原因是读得零碎。

**步骤**：
- **D3.1 主机开销**（约半天）：profile `offload_engine.py` 每次读的路径：Python 处理、`preadv` 系统调用、统一内存争用。试着把一层的缺失合成一次 `preadv`（多个 iovec）、把发起读的逻辑移到原生线程。目标：每次读的主机开销 ≤ 0.1 ms。按校准参数估算，缓存 50% 时 TPOT 可降约 20%。
- **D3.2 存储微基准**（约 1 天）：单个 expert 的读 vs n 个并发读（队列深度 1 / 2 / 4 / 8 / 16 / 32）vs 一次连续读 n 个，**同时测吞吐（GB/s）和单次延迟**。四种链路：Mac 内置 SSD；masdar 的 NVMe RAID（`/data`，服务器上把 expert 放在 SSD 的场景）；H200 的 PCIe 5 多 stream；nobel A100 的 PCIe 4 多 stream（S3）。结果同时给 D13 的 A6 当真实参数。
- **D3.3 按共现安排位置**（约 1 天）：用 trace 统计同一层"常一起缺"的 expert，把它们在盘上排在一起；模拟每层缺失里能合并成连续读的比例，再实测。
- **D3.4** 把"按一次读多少字节算时间"的代价模型加进模拟器，估算 TPOT。

**判据**：主机开销 ≤ 0.1 ms / 次，或一层缺失集合的有效带宽 ≥ 2 倍现状。

H200 上对应的是每次拷贝的固定开销（原型里约 0.18 ms / 次），要等 D8。

### D6 按硬件、模型、负载自动选策略（论文主线候选，待导师确认）

**动机**：已有数据显示，最佳策略随设置翻转（目前只在 CWQ 上看到，D9 要在多负载上确认）：
- 预取：Mac 缓存 50% 时 +15–24%，75% 时 +23% 停顿；
- 淘汰策略：短答案和长推理上 LRU / MoE-Infinity 式谁好正好相反；
- 固定阈值：跑到缓存 75% 时会差 20–29%；
- 顶替：缓存 ≥ 75% 时可以完全不读，50% 时只能顶掉一部分。

**步骤**：
- **D6.1 代价模型**：用停顿公式，输入硬件参数（单次读时间、主机开销、每层计算随 B 的变化）和模型 / 负载统计（各缓存大小下的缺失率，从校准 trace 得到），预测每种策略组合的 TPOT。
- **D6.2 选择规则**：是否预取、阈值参数、顶替的 ρ（由准确率预算给定）、淘汰策略。可以是规则，也可以是在线用代价模型搜索。
- **D6.3 评估**：在各个（硬件、模型、负载、缓存、B）上，和"每个设置事后挑最优的配置"以及几组固定配置比。判据：离每个设置的最优 ≤ 5%，而任何一组固定配置都至少在一个设置上差 ≥ 15%。另做"留一个负载"的检验（见 D9）：选择器没见过的负载上也要达到判据。
- **D6.4 通用性**：用 D9 的多负载、多模型数据，加上 D3 / D4 做出来的杠杆。
- **D6.5 负载漂移**：负载在运行中切换时（D9 的负载切换实验），选择器能否在线调整（重新校准阈值、更新缓存），以及要多久。

### D9 多负载、多模型的 trace 和刻画（2026-10-27 新增，D6 的基础）

**为什么**：

- **GLM-4.5-Air 在三个场景都有**：同一个模型在三种硬件上比，最能说明"硬件不同，最佳策略不同"。

**gpt-oss-120b 的注意事项**：
- MXFP4 是它的原生精度，Mac 上的路由就是参考路由，没有 4bit 和 bf16 路由不一致的问题。
- 它的 expert 有 bias、激活函数带截断，attention 有 sink 和滑动窗口。`collect_traces_mlx.py`、`collect_traces_v2.py` 的钩子和 `offload_engine.py` 的 expert 导出格式要先核对。
- A100 不支持 MXFP4 的原生计算。transformers 在 A100 上可能会反量化成 bf16（约 230 GB，四张卡才放得下）；vLLM 在 Ampere 上有 MXFP4 的 kernel。先确认能用哪种方式加载和采 trace。

**Mixtral-8×7B**：bf16 约 94 GB，一张 A100 放不下，采 trace 要两张卡；采集脚本已经处理过 Mixtral 的 BOS 偏移。

**nobel（A100）的注意事项**：
- GPU 由你每次指定（2026-10-28 晚上是 0–3，都在 NUMA 节点 0，CPU 线程绑在 0–15、64–79）。
- 没有 NVLink，多卡之间走 PCIe，采大模型 trace 会比 masdar 慢。
- 存储是机械硬盘上的 ZFS（NVMe 只作读缓存），第一次加载大模型慢。
- 机器是共用的（有别人跑 CPU 密集任务），计时类实验要等机器空闲，并在结果里注明。
- 没有 FP8 硬件支持：Qwen3-235B FP8 只在 H200 上采。

**大模型采 trace 的注意事项**（10-18 的 GPU 事故就是加载 Mixtral-8×22B 时发生的）：
- 只能用 GPU 0–2（3 × 143 GB）：Qwen3-235B FP8 放两张卡。
- 严格遵守 GPU 规则：每卡至少留 15 GB；一个进程只加载一次；不用 expandable_segments；尽量在 NVLink 组内；先用小样本试。
- 要先确认 transformers 5.2 对这些模型 FP8 权重的支持，必要时用 vLLM 加钩子采集。

**模拟器参数**：每个（场景, 模型）都要在对应硬件上测微基准（单个 expert 的读取时间、每层计算时间随 B 的变化），新建参数，不能沿用 GLM-4.5-Air 在 H200 上的。Mac 的参数要按原型实测校准（像 `mac_ssd_cal` 那样）。

- Mac 的 4bit 模型路由和 bf16 只重合 80–85%，Mac 原型在每个负载上用少量请求补实测。

**trace 格式**：和 v4 相同（路由、路由权重、router 打分、GATE-h 前 16 的 fp32 打分，h = 1–8），所有已有的模拟器、预测器、顶替代码都能直接用。

**刻画**（CPU），每个（模型, 负载）报告：
- decode 长度分布；
- 各缓存大小、各淘汰策略（LRU / LFU / MoE-Infinity 式）下的缺失率；
- 时间局部性：同一个 expert 两次使用之间隔了多少 token；
- expert 使用的集中程度：最热的 25% expert 占多少使用；
- GATE-h 的 recall 随 h 的变化；校准表能否跨负载迁移（ECE）；
- **跨负载的缓存迁移**：用负载 A 的统计预填缓存去跑负载 B，缺失率比用 B 自己的统计高多少。

**关键实验在各负载上重跑**（模拟器）：
- 阶段 0 式的基线表（不预取 / 提前 1 层 / 校准 GATE / 完美预测）；
- 顶替（D1 选定的预算形式）；
- D2 的最好变体。

看最佳策略在哪些维度上随负载翻转，这就是 D6 的输入。

**防止过拟合的评估方法**：
- 参数一律在校准集上选，测试集只测一次；
- **留一个负载**：用其余负载选参数，在留出的负载上测，看能拿到该负载事后最优的多少。

**负载切换**：把不同负载的请求按段混在一个流里，看缓存预填和阈值校准在负载变化时是否需要在线更新、要多久才能适应。这是"动态"系统必须回答的问题。

**判据**：
- **H-D9a**：至少有一个策略维度（是否预取、淘汰策略、顶替预算、阈值）的最佳选择在不同负载之间翻转，而且用错的代价 ≥ 10%。成立 → D6 有充分的动机；不成立 → 一组固定配置就够了，D6 的论点要改。
- **H-D9b**：顶替在改动 ≤ 10% 时，在所有有标准答案的负载上都没有显著掉点。用 §D11 的方法测（真实决定 + 自然波动对照）。

**GPU 估计**：
- 小模型和 GLM-4.5-Air：每个（模型, 负载）约 1–2 小时；
- Qwen3-235B：每个（模型, 负载）约 2–4 小时（两张卡）；

全部约 30–50 小时，分批采，每批开始前问。建议先采 Qwen3-235B FP8（两张卡就够）。

### D10 anchor 的真实成本（2026-10-27 新增，决定 anchor 去留）

#### D10.0 为什么

- 到目前为止，anchor 的所有比较都假设**池子不占内存、搜索不花时间**。模拟器没算，原型也没实现（阶段 1.4 和判据 H3 一直推迟）。
- 现在的池子（`anchor_dump.py`）：
  - 每个历史 token、每一层存 128 维 router 打分（`S`），以及之后各层的路由（`R`）；
  - 在第 l 层，用当前 token 第 l 层的打分（中心化后的 cosine）在**整个池子**里精确地找最近的 8 个，加权投票预测 l+1 … l+8 层。
- **按 CoT 实验的池子粗算**：
  - 约 21.4 万个 token × 45 层 × 128 × fp16 ≈ **2.5 GB**，路由另约 80 MB；
  - Mac 上这 2.5 GB 本来能多放约 250 个 expert（约 10 MB 一个），相当于缓存少了约 4 个百分点，在缓存 50% 附近可能比 anchor 省下的约 3 ms / token 还贵；
  - 每个 token 每层的暴力搜索约 21.4 万 × 128 ≈ 2,700 万次乘加，和 Mac 上一层的计算（约 0.79 ms）同一量级。
- 加顶替后 anchor 在模拟里比校准 GATE 多降 3–14%（缓存 50%、LRU），这是它唯一像样的收益。如果搜索太慢或池子太大，这点收益会被吃掉，anchor 就不能直接用。

#### D10.1 要回答的问题

- **Q1 内存**：各种压缩后池子多大；Mac 上占掉多少缓存，H200 上能不能放在主机内存里。
- **Q2 搜索时间**：每层每 token 一次 kNN，在 Mac（CPU 的 Accelerate、MLX GPU、faiss CPU）和 H200（torch GPU、faiss GPU）上各要多少 µs；B = 1 和 B = 4 时各是多少。
- **Q3 压缩和近似后预测还准不准**：recall@8（h = 1–8）和组合后的 AVG / AVGs 比全池精确搜索掉多少。
- **Q4 关键路径**：搜索能不能和计算、读盘重叠（放到另一个 CPU 线程上异步跑）。异步时代价是预测晚到（相当于少提前一层），还会和每次读的主机开销（约 0.66 ms，也在 CPU 上）抢 CPU。
- **Q5 扣掉成本后还剩多少**：把内存和时间都算进去，anchor 在它最可能赢的条件下（顶替 10%、缓存 50%、LRU，以及 D2 的最好变体）还比校准 GATE 好多少。
- **Q6 池子从哪来**：真实部署时没有现成的同负载历史。冷启动（从空池开始，只加自己生成过的 token）多久能追上；换负载时池子是否失效（依赖 D9）。

#### D10.2 压缩和近似的选项

| 维度 | 选项 |
|---|---|
| 池子大小 | 全池；随机抽样 50 / 20 / 5%；去掉近似重复的记录；**聚类成原型**（每层 k-means 成 C = 1k / 4k / 16k 个中心，每个中心存它覆盖的记录在后面各层的路由分布，搜索变成找最近的中心）；FineMoE 式只存 1000 条 |
| 精度 | fp16 → int8 → 二值（符号哈希） |
| 维度 | 128 → PCA 降到 32 / 16；或只存每层打分最高的 16 个（稀疏） |
| 搜索范围 | 全池；先按 token id 分桶再找（`-tok` / `-hier`，以前略差，但便宜得多） |
| 搜索方法 | 暴力矩阵乘；faiss IVF / IVF-PQ / HNSW；找最近的原型 |
| 运行位置 | 同步（加在每层的关键路径上）；异步（另一个线程，结果晚一层到） |
| 只在部分层做 | 例如每 2–4 层搜一次，其余层沿用最近一次的近邻 |

#### D10.3 实验

- **离线质量**（CPU，约半天）：各压缩 / 近似组合的 recall@8，与全池精确搜索对比；用 GLM CoT（v4）和 W1，同 `anchor_dump.py` 的口径。
- **微基准**（Mac + H200，约半天）：每种组合的每次查询延迟（B = 1、4）和内存。
  - Mac：CPU Accelerate、MLX GPU、faiss CPU；
  - H200：torch GPU、faiss GPU。
  - H200 的 GPU 计时要等卡空闲（`gpu_queue.py`），开始前问。
- **模拟器加成本**（CPU，约 1 天）：`tsim_mu.py` 增加两项：
  1. 池子内存折算成 expert 个数，从缓存容量里扣掉（Mac；H200 放主机内存时不扣，放 GPU 时扣）；
  2. 搜索时间：同步时加到每层时间上；异步时预测在"当前层开始 + 搜索时间"之后才能发出。

  然后在 seq 和 pool（N = B = 4）× `mac_ssd_cal` / `h200_pcie` × 缓存 25 / 50 / 75% × {不顶替，顶替 10%，D2 最好变体} 下，比较各个可行的 anchor 配置和校准 GATE。
- **冷启动和换负载**：池子从空开始，只加入本请求和之前请求生成的 token，recall 随历史长度的曲线；用负载 A 的池子跑负载 B（依赖 D9）。
- **Mac 原型**（只有 H-D10b 成立才做）：在 `prefetch.py` 里实现最好的 anchor 配置，和校准 GATE 实测对比。

#### D10.4 判据

- **H-D10a（可行性，原 H3 的扩展）**：存在一种配置同时满足：
  - h = 2–4 的 recall@8 比全池精确搜索掉 ≤ 1 pt；
  - 每次查询 ≤ 每层计算的 20%（Mac ≤ 约 160 µs，H200 ≤ 约 60 µs），或者异步运行时晚到一层的损失 ≤ 1 pt；
  - 内存 ≤ 全部 expert 字节数的 1%（GLM 4bit 约 560 MB）。
- **H-D10b（值不值）**：扣掉内存和时间后，至少在"顶替 10%、缓存 50%"下，anchor+GATE 的 TPOT 比校准 GATE 低 ≥ 3%。
- 任何一条不成立：anchor 从系统里去掉，结论写成"把基线校准公平、并算上成本后，轨迹匹配类预测（FineMoE / anchor）不值得"，和 D5.1 一起作为论文里的分析。

### D11 真实决定下的准确率（多负载、多模型；2026-10-27 新增）

#### D11.0 为什么

阶段 2 的准确率是**真模型、真打分，但顶替决定是模拟出来的**：
- **回放**模拟器的记录：生成一分叉，记录就对不上，实际改动率只有 0.44–0.60%；
- **按统计随机施加（emp）**：只匹配模拟器记录的统计分布，和缓存状态无关。统计来自缓存 50%（覆盖不了 75% 时 top-1 被换 8.9% 的情况）；每个请求被均匀地改（真实系统里单请求 4.2–19.5%）；Qwen3 还借用了 GLM 的排名分布。

真实决定下测过的只有原型，而且样本太少：
- H200 Qwen3 64 题：缓存 50%、顶替 10% 时 .844 对 .875，分不清；
- Mac CoT 20 题：多数被截断，不可比。

另外两个问题：
- 只有 GSM8K 和 CWQ 两个任务；
- 小改动时准确率常比不改动略高（GLM 2%：.920 对 .890，对变错 / 错变对 1 / 7）。这更像"扰动让模型重新走了一遍、多抽了一次"，说明拿单次 greedy 当基准时，自然波动不可忽略。

所以"改动 ≤ 10% 不掉点"目前只是"按统计随机扰动时不掉点"，不能当作真实系统的结论。

#### D11.1 三个真实程度

| 层级 | 做法 | 决定是否真实 | 时间 | 成本 |
|---|---|---|---|---|
| **L1** 在线模拟缓存（同步加载） | 全驻留模型生成。每一步用模型自己当时的真实路由，驱动一个按真实规则运作的缓存（每层池大小按校准频率、预填、LFU / LRU）；迟到 = 不在缓存里；按预算形式实时决定，再施加到路由上 | 是（不预取时和真实系统完全一致） | 不需要 | GPU 全速，加每层的判断开销 |
| **L2** L1 + 虚拟时钟 | 再按硬件参数跑一个 `tsim_mu.Engine` 的虚拟时间：预取、读取顺序、在途的读都按模拟器的规则算，"迟到"的判断和模拟器一致 | 是（包括预取、D2 的变体） | 虚拟 | 比 L1 稍慢 |
| **L3** 原型端到端 | 直接在 Mac / H200 原型上生成 | 是 | 真实 | 慢（Mac 每 token 30–170 ms） |

L1 / L2 是主力；L3 用来抽查：同样的题，原型的准确率要落在 L1 / L2 的置信区间里。准确率和速度无关，所以 H200 原型的开销问题不影响用它测准确率。

#### D11.4 对照和统计

### D12 顶替规则：对比、"读还是换"的统一决策、改进（2026-10-28 新增）

#### D12.0 为什么

- 顶替是吞吐提升最大的来源（单用户 Mac TPOT −46% / −58%；多用户模拟 +50% 到 +810%），而且并发越高收益越大。
- 但**规则本身不新**：DAOP（DATE'25）几乎一样；"保护前几名"Cache-Prior 已有；SMoE / MoE-CORE 用分数窗口控制。我们**从没在同样的改动率下和它们比过**。
- 高并发时决策单位应该变：同一个 expert 被 batch 里很多 token 需要时，读一次就能分摊；只被一两个 token 需要时最不划算，应优先交给顶替。Q1 的粗糙版本（被少于 4 个 token 需要的缺失直接跳过）在 N = 64 时让吞吐从 65 / 214 升到 562 / 789 tok/s（缓存 75 / 90%），但那是跳过，准确率代价更大。

#### D12.1 和已有规则同条件对比

- 放进同一个框架（`tsim_mu.Subst`、D11 的 L1 测量框架），各自扫参数：
  - DAOP：低分的缺失换成驻留的下一个最高分，不设预算；
  - SMoE / MoE-CORE：分数窗口 α；
  - Cache-Prior：缓存 expert 的 logit 加 λ·Δ_avg，前 J 名永远保留；
  - BuddyMoE：离线按共现找伙伴，每 token 最多换 3–4 个；
  - 直接跳过（Not All Experts 式）；
  - 我们的：B0 / D1 选出的预算形式。
- 画"改动率 → 对变错"和"读取次数（或吞吐）→ 对变错"两条前沿，比较谁在前沿上。准确率按 D11 的方法测。

#### D12.2 "读还是换"的统一规则（用户 2026-10-28 的想法）

**预计需求**：对目标层的每个 expert e，D_e = 这一步 batch 里所有 token 用到它的概率之和，也就是预计有几个 token 要用它。
- 同一步内往后看几层：用校准 GATE 的命中概率直接相加，不需要 anchor；
- 跨步（下一步的头几层，以及挑 batch）：用 P-anchor 的下一 token 预测；
- 可以再乘上路由权重或"可替代性"（见 D12.4），让重要的、难替代的排前面。

**预取**：
- 队列按（目标层，D_e 从大到小）排，需求高的先读；
- D_e ≥ θ(排队负载) 才读，θ 随读取通道的拥堵程度升高，沿用现有的 τ0 + κ·log2(1 + 负载) 形式；
- 读取空闲时，需求低的也读；拥堵时不读，交给顶替。

**执行到这一层时**，对每个缺失的 expert，看实际有几个 token 要用它（c_e）：
- c_e ≥ c\*(负载)，或者它是某个 token 的 top-r → 现读；
- 否则，对这几个 token 在各自请求的预算内顶替；
- 某个请求快用完额度（D1 的 B1）→ 它的缺失改为现读，避免改动集中到少数"路由偏"的请求上。

**和已有方向的关系**：
- B = 1 时退化成 D2：晚出现的、没把握的交给顶替；
- 可选叠加按相似度组 batch（P-anchor），让需求更集中，但要付出 p99 的代价（阶段 3：p99 +40%）。

#### D12.3 实验

- **模拟器**：
  - seq，以及 pool：N ∈ {4, 16, 64}，B ∈ {4, 16, 32}；
  - 缓存 50 / 75 / 90%；`mac_ssd_cal` / `h200_pcie`；
  - 对比：只顶替（B0 / B1）、D2 最好变体、D12.2 规则、D12.2 + 组 batch。
- **指标**：吞吐、p99 TPOT、每 token 读几次、全局和单请求改动率（p90 / max）、top-1 被换比例。
- 选出的配置用 D11 测准确率。
- 多用户要用校准 GATE，需要带 GATE 打分的 v4 CoT 200 个请求的 trace（阶段 3 没采到，只能用 anchor+GATE）。这部分并入 D9 的采集。

#### D12.4 其他改进候选（先在模拟里看改动率和读取次数，再用 D11 测准确率）

1. **按"可替代性"做缓存和预取**：一个 expert 的缓存价值 = 被用到的概率 × 缺失代价，其中缺失代价 = min(读的时间, 换掉造成的质量损失)。缓存里有好替身的 expert 缺了代价小，可以优先淘汰、晚一点读。这把缓存、预取、顶替连成一个决策。
2. **按权重算预算**：预算限制"被换掉的路由权重之和"，而不是个数（换 top-1 和换第 8 名的风险不同）。
3. **按敏感度分配额度**：层和 token 对改动的敏感程度不同（参考 AdapMoE 的 Fisher 敏感度），额度集中给不敏感的地方。
4. **按功能相似性挑替身**：离线算 expert 之间输出的相似度，挑功能最接近的，而不是 router 分数次高的。
5. **按请求的反馈预算**：每个请求累计被换掉的权重，接近上限就停止顶替、改为现读。

#### D12.4b 预测器 × 顶替的矩阵（2026-10-28 新增）

**问题**：anchor 和顶替结合起来，是不是比其他预测器和顶替结合起来更好？

**已有的数据**（阶段 1，GLM CoT，单用户，LRU，全局预算，停顿 ms/token，`outputs/moe/mu/p13/p13_tables.md`）：

| 设置 | 顶替 | 不预取 | 校准 GATE | anchor+GATE | anchor 比校准 GATE |
|---|---|---|---|---|---|
| Mac 50% | 不顶替 | 70.2 | 53.6 | 54.3 | +1% |

- 加上顶替后，预测更值钱了：Mac 50% 不顶替时 anchor 比校准 GATE 慢 0.7 ms，顶替 10% 时快 2.9 ms。猜测的机制：顶替额度有限，预测越准、迟到的越少，额度能盖住的比例越大。这和 §0 story 的第 4 → 5 步方向一致。
- 但结论还很弱：
  - 只在 LRU 下成立（MoE-Infinity 式缓存下 anchor 略差：Mac 50% 26.5 对 26.0）；
  - 只在缓存 50% 时明显，换成 TPOT 只有约 5–8%；
  - 只和校准 GATE 比过，没有"完美预测 + 顶替"的上界；
  - 没算 anchor 的成本（D10）；
  - 只有一种负载、单用户、旧的全局预算；
  - 准确率没比：两边改动率都是 10%，但被换掉的是哪些 expert（top-1 被换多少）可能不同。

### D13 预测收益的机制分析（2026-10-28 新增）

#### D13.0 为什么

导师的问题：anchor 能预测更多层、准确率更高，为什么 performance gain 这么小？现有的解释：
- **提前量没用**：带宽受限时读取通道几乎一直满，早知道也没法早读。Mac 缓存 50% 时，每 token 读约 69.7 ms、算 35.7 ms，下界约 34.0 ms，完美预测实际 37.1 ms；完美预测下提前 4 层和 8 层几乎一样（37.4 对 36.8）。
- **远处的高准确率用不上**：每层都重新预测，远处目标层的读在队列里等着，轮到时已被近处的新预测替换。实际执行的读多来自 h ≤ 2 的预测，而这个距离上 GATE 和 anchor 一样准（h = 1：.791 对 .778）。
- **准确率的空间已被阈值吃掉**：校准 GATE 加阈值后白读只剩约 10%（Mac 50%：每 token 68.0 对完美的 60.6 次）。anchor 没缩小这个差距（53.9 对 53.7 ms）。
- **衡量指标可能不对**：决定停顿的是"对缓存里缺的那些 expert"预测得准不准，而不是整体 recall@8。命中一个本来就在缓存里的 expert，对停顿没有帮助。这个还没测过。

这些目前只是推理加上一两个数字，而且只在 GLM、CWQ CoT 上。要成为论文里"预测的 limitation"一节，需要直接的测量，并且在多负载、多模型、多种硬件比例下都成立。

#### D13.1 分析内容

| 编号 | 分析 | 要说明什么 |
|---|---|---|
| A1 | **读取通道的忙碌率和排队长度**：按时间记录通道是否在读、排队中的读有多少（折算成"几层的读取时间"） | 带宽受限的设置里通道几乎一直满，提前量没有空闲可以利用 |
| A2 | **实际执行的读来自哪个 h**：每次真正开始执行的预取读，记下当时让它留在队列里的最新预测是提前几层的；以及读完到被用到之间隔了多久（实际用到的提前量） | 远处的预测几乎没有被执行，anchor 在 h = 6–8 的优势没机会用上 |
| A3 | **缺失上的 recall**：只看在当前缓存下会缺失的 expert，比较各预测器在各个 h 上的 recall；再看它和停顿的相关性，是否比整体 recall@8 更能解释停顿 | 衡量预测的正确指标；anchor 在"缺失"上是否真的更准 |
| A4 | **硬件比例扫描**：单次读取时间 ×{0.25, 0.5, 1, 2}、计算速度 ×{0.5, 1, 2}、读取通道数 {1, 2, 4}，再配合不同缓存大小。定义 R = 每 token 读的总时间 ÷ 每 token 的计算时间，画各预测器相对校准 GATE、以及完美预测相对校准 GATE 的收益随 R 的变化 | 找出"预测（和提前量）什么时候值钱"的分界线，指出 anchor 真正适用的硬件条件 |
| A5 | **差距分解**：校准 GATE 和完美预测之间的停顿差，分成白读的（读了没用）、该读没读的（缺失时还没排进队列）、排了但来不及的（排了队但用到时还没读完） | 剩下的空间在哪一块，预测还能改进什么 |
| **A6** | **延迟受限区域**：把读取的"单次延迟 L"和"同时能读几个 Q"分开（现在两者绑在一起：一次只读一个）。扫 L（相当于 1–16 层，乃至超过一个 token 的计算时间）× Q（1–32）× 缓存；再用 D3.2 测到的真实 L、Q（Mac SSD、NVMe RAID、H200 PCIe）定位真实硬件落在哪。比较 anchor（含 D10 的压缩版本，以及用 P-anchor 跨 token 提前读下一个 token 的头几层）、校准 GATE、FineMoE、完美预测，报告停顿和 TPOT。另外把顶替（D1）和并行读（D3）加上去，看系统是否真的从带宽受限移到延迟受限、深层预测的价值是否随之上升 | story 第 5 步：深层预测在什么硬件条件下重新变得关键；anchor 能否在那里明显赢 |

**预测器**：GATE、校准 GATE、TOK+GATE、anchor（AV、AVG / AVGs，以及 D10 选出的压缩配置）、FineMoE（D5.1）、ProMoE MLP（D5.2，有的话）、完美预测。

**范围**：
- 试跑：现有 GLM 的 CWQ CoT（v4）和 W1，用来开发脚本和模拟器计量；
- 正式：D9 的全部负载 × 全部模型；
- 硬件参数：`mac_ssd_cal`、`h200_pcie`，加上 A4 的扫描；
- 缓存 25 / 50 / 75 / 90%；单用户为主，pool（N = B = 4）补一组。

**需要的模拟器改动**：
- 通道忙碌和排队长度的时间线；
- 每次执行的读对应的 h、实际提前量；
- 缺失集合的记录；
- 硬件参数的缩放；
- **多个读取通道**（现在只有一个）；
- **延迟和并发分开**：每次读有延迟 L，最多 Q 个同时在读（A6）；
- **跨 token 预取**：在当前 token 的最后几层，用 P-anchor 预测并提前读下一个 token 头几层的 expert（A6）。

#### D13.2 判据

- **H-D13a（解释成立）**：在 R > 1（读比算长）的设置里，所有负载、模型上：
  - 通道忙碌率 ≥ 85%；
  - ≥ 80% 的已执行预取读来自 h ≤ 2 的预测；
  - anchor 相对校准 GATE 的停顿收益 ≤ 5%。
- **H-D13b（找到预测有用的区域）**：存在 R < 1 或多通道的设置，在那里 anchor（或任何更强的预测器）相对校准 GATE 的收益 ≥ 10%。给出这个区域对应的硬件条件（读取带宽、计算速度、缓存大小）。
- **H-D13c（指标）**：缺失上的 recall 和停顿的相关性，明显高于整体 recall@8。
- **H-D13d（延迟受限区域）**：在 A6 的扫描里，存在一个区域，anchor 比最好的 baseline（校准 GATE、FineMoE 中较好的）停顿低 ≥ 20%、TPOT 低 ≥ 10%；并且这个区域能对应到真实硬件（D3.2 测到的 L、Q），或者是加上顶替和并行读之后系统会进入的区域。不成立 → 结论写成"即使在延迟受限区域，轨迹匹配也不值得"。
