# Plan：多用户 decode 池——按路由相似性组 batch（anchor × expert queue）

*Bowen · 2026-10-21 · 状态：A0 完成（见 §5），A1 待做*

来源：讨论中提出，所有想法最终都面向多用户。现有两个 plan 都偏单用户或单步视角：
- `2026-10-19-moe-trajectory-anchor-plan.md`：P3 只做了单用户（batch = 1）；
- `2026-10-19-moe-expert-queue-plan.md`：还没开始。

这份 plan 把两者合并到"一个 decode 请求池、batch 大小可变"的场景里。

---

## 0. 想法

- **场景**：decode 池里有 N 个活跃请求（N 大于每步实际跑的 batch B，或者 B 可变）。每一步决定**让哪些请求前进**。
- **开销**：一层的开销主要取决于本步 batch 在这一层用到的**不同 expert 数** U_l，也就是各请求所选 expert 的并集。
  - GPU 全驻留（H200 上的 GLM-4.5-Air bf16）：decode 受显存带宽限制，读的权重 ∝ U_l。
  - offload（Mac，或 H200 走 PCIe）：要加载的 expert ∝ U_l 中不在缓存里的部分。
- **做法**：让"下一个 token 大概率走相同 expert"的请求一起跑，U_l 变小，单位时间产出的 token 更多。没被选上的请求等一步。用心跳（最长跳过 k 步）保证公平。

三个粒度，同一个目标：

| 粒度 | 决策 | 需要的预测 |
|---|---|---|
| 步级（选 batch） | 这一步让池中哪些请求前进；B 可变 | 在这一步开始前，预测每个请求下一个 token 在各层的 expert（用上一个 token 的轨迹、anchor） |
| 层级（expert queue） | 每个 expert 攒到阈值或到心跳才加载 / 计算 | 多层提前预测：各 expert 接下来会排进多少 token |
| 预取 / 缓存 | 按全池的预测需求预取、常驻 | P3 的预测器，按全池汇总 |

和之前结果的关系：
- 阶段 A 的"分段重组"上限只有 2–6%（长 decode）。但那是**固定分组**。
- 这里是**每步从更大的池子里动态挑**，并允许等待，空间可能更大，也可能一样小。所以 A0 先用真实路由算上限，作为是否继续的判断依据。

---

## 1. 假设

| 编号 | 假设 | 判据 |
|---|---|---|
| M1（上限） | 用真实路由、池子 N ≥ 4B 时，按相似性每步挑 batch，每个 token 的平均不同 expert 数比 FCFS（所有请求齐步前进）少 | ≥ 20%，且每个请求最多被跳过的步数 ≤ k（k = 2–4） |
| M2（可预测） | 用预测的路由（上一个 token / anchor）挑 batch，能拿到上限的大部分 | ≥ 50% 的 M1 收益 |
| M3（系统） | 在相同的 p99 每 token 延迟下，吞吐提高 | GPU 全驻留 ≥ 15%；offload ≥ 25% |
| M4（结合 queue） | 层级 expert queue（攒批 + 心跳）在步级挑选之上还有额外收益 | 再 ≥ 10% |

## 2. 实验步骤

### A0：上限（CPU，用现有 trace，约半天）

- 数据：GLM-4.5-Air bf16 W2c CoT 200 个请求（每个约 1000 个 decode token，`traces_v3`）；W1 短答案作对照。
- 把每个请求看作池中的一条"token 流"。每步从池中选 B 个请求前进，记录各层的 U_l。
- 策略：
  - FCFS / round-robin（基线）；
  - 贪心相似性挑选（真实路由，上限）；
  - 贪心 + 最长等待约束 k。
- 扫描 N ∈ {32, 64, 128, 200}，B ∈ {4, 8, 16, 32}，k ∈ {1, 2, 4, ∞}。
- 指标：每个 token 的 Σ_l U_l；最长 / p99 等待步数。

### A1：可预测性（CPU，约半天）

- 下一个 token 第 l 层的 expert，在这一步开始前用以下方法预测：
  1. 上一个 token 在第 l 层的 expert（时间局部性）；
  2. anchor：用上一个 token 的状态（各层 router 打分）在池子里找相似记录，取它们"下一个 token"的轨迹；
  3. 上一个 token 的轨迹 + 前几步的累计频率。
- 指标：每层的 recall@k；再用预测的路由跑 A0 的挑选，看实际 U_l。

### A2：时间模拟（约 1–2 天）

- 扩展 `tsim_batch.py`，或新写 `tsim_pool.py`：
  - GPU 全驻留：每层时间 = (非 expert 权重 + U_l × expert 大小) / 显存带宽 + 计算；
  - offload：P3 的加载模型（缓存 + 加载队列 + 预取）。
- 请求按 Poisson 到达，decode 长度取自 trace。指标：吞吐 vs p99 每 token 延迟曲线。
- 对比：FCFS continuous batching、按相似性挑选（预测）、按相似性挑选（真实路由），以及再叠加 P3 的预取。

### A3：层级 expert queue（和 queue plan 的 Q1 合做，约 2 天）

- 事件驱动模拟：token 在每层按 expert 排队；队列达到阈值或心跳到时才加载并计算。
- 测：在步级挑选之上，层级攒批的额外收益，以及心跳间隔对延迟的影响。

### A4：原型（只在 M3 成立时做）

- H200：在 vLLM 的 scheduler 里改"选谁进这一步"（步级挑选，不改 kernel）。
- Mac：在 offload 引擎上实现多请求版本。

## 3. 风险

| 风险 | 应对 |
|---|---|
| B 大时并集接近全部 expert（GLM top-8 / 128，B = 32 时每层约 100 个），挑选空间小 | 重点看中小 B 和 offload 场景；A0 会直接给出这个曲线 |
| 下一个 token 的路由事先难以预测（只有上一个 token 的信息） | A1 先量化；不行就退到层级粒度（A3），用层内的多层提前预测 |
| 跳过请求导致尾延迟变差 | 心跳 k 作为硬约束；报吞吐 vs p99 的完整曲线 |
| 和"按请求分组"的旧结论重复 | 明确对比固定分组（阶段 A）和每步动态挑选 |

## 5. A0 结果（2026-10-21）

- 数据：GLM-4.5-Air bf16 W2c CoT 200 个请求（`traces_v3`）。每个请求从其 decode 的随机位置开始（前一半中的随机点），模拟 continuous batching 中新旧请求混在一起的情况。
- 每种设置跑 400 步。指标是每个 token 每层平均用到的不同 expert 数，相对 FCFS（按等待时间轮转）的变化。
- k 表示"比轮转最多多等几步"，k=∞ 表示不限制。

| N | B | FCFS | 真实路由 k=0/1/2/4/∞ | 上一 token 预测 k=0/1/2/4/∞ | p99 等待步数（FCFS → 真实路由 k=∞） |
|---|---|---|---|---|---|
| 32 | 8 | 5.82 | −0 / −10 / −12 / −13 / −13% | −1 / −6 / −7 / −7 / −8% | 3 → 9 |
| 64 | 8 | 5.85 | −1 / −10 / −14 / −17 / −19% | −1 / −7 / −9 / −11 / −12% | 7 → 18 |
| 128 | 8 | 5.83 | −2 / −10 / −12 / −17 / −24% | −2 / −6 / −8 / −11 / −15% | 15 → 35 |
| 128 | 16 | 4.41 | −1 / −11 / −15 / −18 / −23% | −1 / −8 / −10 / −12 / −14% | 7 → 24 |
| 200 | 8 | 5.82 | −4 / −9 / −12 / −16 / −27% | −2 / −5 / −7 / −11 / −16% | 24 → 55 |
| 200 | 16 | 4.41 | −7 / −12 / −15 / −19 / −26% | −4 / −8 / −10 / −12 / −16% | 12 → 37 |
| 200 | 32 | 2.94 | −9 / −13 / −15 / −18 / −21% | −6 / −9 / −10 / −11 / −12% | 6 → 24 |

完整表在 `outputs/moe/pool_bound_cot_off.json`。

判定：
- **M1**：k ≤ 4 时，真实路由的上限是 −12% 到 −19%。不限等待时，大池子（N ≥ 128）能到 −21% 到 −27%。≥ 20% 只在大池子、放宽等待时成立。
- **M2**：只用"上一个 token 的路由"做预测，就能拿到上限的约 55–65%（k=4 时 −7% 到 −12%）。下一步看 anchor 能否更接近上限（A1）。
- **池子越大、B 越小，空间越大**；B = 32 时，并集本来就接近饱和。

注意：
- 一开始所有请求都从第 0 个 token 开始，结果被 CoT 开头相同的模板文字放大了。修正为随机起点后，FCFS 的数字不再随 N 变化，以上是修正后的结果。
- 这里只算了"不同 expert 数"，还没换算成时间（A2）。
