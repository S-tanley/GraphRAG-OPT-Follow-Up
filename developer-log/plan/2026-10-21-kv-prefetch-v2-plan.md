### 已知

| 结论 | 证据 |
|---|---|
| 服务器 + 小模型时，KG 4 跳检索远长于 prefill（检索占 78–94%），能省的绝对时间少 | K0 |
| 端侧（Mac）+ KG 4 跳是五五开的场景（检索占 39–57%），而且检索期间 GPU 空闲 | K0v2 §3.8 |
| 生成侧上限：段落 / 路径 KV 都就绪 + question 提前 prefill 时，首 token 延迟可省 60–92%（服务器）；端侧绝对节省更大 | K0v2 §3.3、§3.8 |
| 多用户时，只"边检索边预算"收益 5–15%；加上跨请求复用（命中 35%）收益 22–85%，越接近饱和越大，吞吐也能提高 | 调研报告 §4 |
| 服务器上普通文本 RAG 做推测式预算会变差（p50 +16% 到 +20%） | 调研报告 §4 |
| KG 片段的跨请求复用：CWQ 路径 35–52%、三元组 59–63%；WebQSP 路径 13–17%、三元组 20–25% | K0 |

### 定位（和已有工作的区别）

已有系统都在**排好序的文档列表**上做推测式 prefill：RAGCache、HedraRAG、AquaPipe、Stream2LLM。图 RAG 的 KV 复用（SubGCache、DepCache、MetaKV）都在检索结束之后。GLM Graph-CoT 服务把图检索和 decode 做了流水，但不在检索期间预算路径 KV。

我们做：
1. **路径 trie 的增量预算**：图遍历逐条产出路径时，按前缀增量计算 KV。在 trie mask（M2）下，每条路径的 KV 只取决于自己的前缀，剪枝、重排后已算好的 KV 依然有效；Stream2LLM 是前缀语义，前面一变后面全部作废。**代价**：我们 10-15 的实验显示，免训练的 M2 相对完整 prefill 掉 2–7 pt（GraphRAG-Opt 的 reuse-all，即完全独立编码的 M1，掉 4–12 pt）；在 M2 下做 LoRA 后差距只有 −0.6 到 −1.0 且不显著。所以"剪枝后仍可用"要么接受 LoRA，要么靠重算补准确率（见 R1）。
2. **多用户共享**：同一主题实体或实体对的遍历只做一次，分发给所有订阅它的请求；路径 KV 进入跨请求的池子（GPU / 内存 / SSD 分层）。
3. **只填空闲的调度**：推测工作是最低优先级、可抢占的，用"预计省下的 prefill × 存活概率 − 对其他请求的干扰"来决定是否接纳；报告浪费比例和对其他请求 TPOT / p99 的影响。已有工作都没有报告这些。
4. **两个落点**：端侧统一内存（CPU 遍历 + GPU 预算，不需要 PCIe 搬运）；服务器大模型（prefill 重，接近饱和时复用的价值最大）。

和 GraphRAG-Opt 的关系：
- GraphRAG-Opt 本身是完全独立编码（reuse-all = M1）；trie mask（M2）、文本 trie（T）和 LoRA-M2 是我们 10-15 的 follow-up 实验（`report/2026-10-15-exp2/3/4`）。其中 M2 / LoRA-M2 是"路径 KV 在剪枝后依然可用"的前提，T 不掉点，但属于前缀语义；
- 批内"同一实体对只搜一次" → 扩展为跨用户、流式的共享遍历。

## 2. 实验步骤

### R0：检索实现诊断（约 1 天，CPU）——决定定位是否成立

调研指出：我们的 Python BFS 4 跳平均 1.2 s，但 C++ 的 PathEnum 在 10^6–10^7 条边的图上典型查询只要毫秒级。必须先弄清楚检索时间里有多少是实现开销。

- 给 RoG BFS 和 GraphRAG-Opt 的 JbiDFS 加计时：每秒产出路径数、第一条路径的时间、第一批 10 / 50 条路径的时间、遍历过的节点和边数。
- 实现一个优化版本作对照：先用 BFS 算到源点和终点的距离做剪枝（PathEnum 的 IDX-DFS 思路），C++ 或 numba，同样 cap 50、跳数 3 / 4。
- 统计优化前后，检索时间的分布（p50 / p90 / p99）和"检索时间 ≥ prefill 时间"的请求占比（分服务器 / Mac、8B / 70B）。
- **顺带核对** GraphRAG-Opt `retrieval.py` 中的两处疑点：
  - 冗余率统计恒为 0；
  - `pair_to_graph` 被后面问题的子图覆盖。

  确认它们是否影响论文结果。
- **分支**：
  - 优化后检索窗口仍然普遍存在 → 按原定位继续；
  - 只剩尾部查询 → 定位改为"尾部查询 + 路径数上限 + 按得分流式产出"，重点转向多用户共享（V-H3），因为它不依赖检索窗口的长短。

### R1：路径 KV 拼接的准确率（K2，约 3–4 天，GPU 0–2 中空闲的卡 + Mac）

调研指出，没有工作在不训练的情况下验证过 10–30 token 的短单位，所以这一步是方法能否成立的关键。

- **KV 的结构：四条路线并排比较（核心对比）**。共同的设定：路径 KV 都在检索期间提前算好，检索结束后拼接，再 prefill 末尾的问题；以完整 prefill（M0）为对照。
  - **路线 0：GraphRAG-Opt 本身（M1）**：以单条路径为单位，每条路径各自独立算 KV（互相看不到，也不共享前缀），检索结束后直接拼接。10-15 实验在 cap 8 下掉 4–12 pt。这里在新设置（cap 50、3/4 跳、Qwen3）下重测，同时测它加上重算（不看问题的 CacheBlend 式，以及按问题选）能补回多少。它也是和 GraphRAG-Opt 论文直接对比的基线；
  - **路线 1：LoRA-M2**：trie mask + LoRA。10-15 实验已打平（−0.6 到 −1.0，不显著），但需要训练。这里在新设置下复现，并确认它的 KV 能在检索期间预算；
  - **路线 2：免训练 M2 + 按问题选 token 重算**：trie mask，不训练。10-15 实验掉 2–7 pt；10-16 只重算箭头没补回来。这次试按问题选 15–30% 的 token 重算（ProphetKV / FusionRAG 式）；
  - **路线 3：T + 前缀语义**：trie 写成文本，普通 causal，不掉点（10-15 已验证）。按 DFS 产出顺序流式算 KV；检索结束时，从第一个改动位置往后要重算。这里测在真实的剪枝 / 排序下，提前算的 KV 能保留多少。
- **复用单位**（主要在路线 1 / 2 下比较；路线 0 固定为单条路径）：
  - 单条三元组；
  - 整条路径（一行，20–60 token）；
  - 顶点块（主题实体 + 一跳邻居的所有边，≥ 100 token）；
  - trie 前缀（共享前缀精确复用，只在分叉处独立）。
- **位置**：存 RoPE 前的 key，拼接时统一旋转（KVLink 的做法）；位置连续编号。
- **注意力汇聚的修补**：
  - 每段前加共享前缀或哑 token，算完后丢掉它们的 KV（APE / LegoLink-0 的做法）；
  - 对照：不修补、重算每段开头若干 token。
- **重算**（用于路线 0 和路线 2；10-16 的箭头重算没补回来，这次试按问题选的）：
  - 不重算；
  - CacheBlend 式（不看问题）15%；
  - **按问题选** 15 / 20 / 30%（ProphetKV / FusionRAG 式，用提前 prefill 的问题 query 打分）。
- **prompt 格式**：
  - question 在后（原格式）；
  - "[系统 + 问题] → 路径 KV → [重复问题]"（推荐）；
  - question 只在前。
- **数据和模型**：CWQ、WebQSP（cap 50，3 / 4 跳），各 500 题；Qwen3-8B、Qwen3-30B-A3B（H200 用 HF；Mac 用 MLX 复核一组）。对照组是完整 prefill。
- **产出**：四条路线的对比表（准确率、需不需要训练、检索结束后还要算的 token 比例、剪枝 / 重排后保留的 KV 比例）；准确率 vs 重算比例曲线，按单位 / 修补方式 / 格式分开；选定后续使用的配置。

### R2：单请求流水原型（端侧优先，约 3 天，Mac）

- **结构**：
  - CPU 线程跑路径枚举（R0 的优化版本），路径按得分（关系路径似然，或简单的长度 / 度数启发式）或 DFS 顺序流式产出；
  - GPU（MLX）按 trie 增量 prefill 路径 / 前缀，写入 KV 池；
  - 检索结束后按 R1 选定的方式拼接 + 重算，prefill 末尾的问题，开始 decode。
- **对比**：
  - 检索完整段 prefill；
  - 检索完用 R1 的拼接（没有重叠，等于 CacheBlend 式的事后复用）；
  - 流水（本方法）；
  - 流水 + 只预算得分前 K 条路径。
- **指标**：首 token 延迟（p50 / p90）、准确率、浪费的预算（算了但被剪掉的路径），以及 CPU 遍历和 GPU prefill 在统一内存带宽上的相互影响。
- **判据**：V-H2。

### R3：多用户模拟升级（约 2 天，CPU）

在 `mu_sim.py` 的基础上加入：
- **路径 KV 池**：容量、换出策略（LRU / 按热度）、分层（GPU / 内存 / SSD）和加载时间。服务器内存 → GPU 约 50 GB/s，SSD 约 3–7 GB/s；Mac 是统一内存，内存层不需要加载。8B 的 KV 每 token 约 144 KB。
- **共享遍历**：同一（主题实体, 答案实体, 跳数）在一个时间窗口内只遍历一次，路径同时发给所有订阅的请求；减少 CPU 工作量，也让 KV 池更早命中。
- **到达顺序**：随机、按主题实体聚集（Zipf，模拟热门实体）、按 CWQ / WebQSP 的真实分布。
- **接纳策略**：按"预计省下的 prefill × 存活概率 − 干扰"决定是否预算；路径数上限；只预算得分前 K 条。
- **拼接代价**：用 R1 测得的重算比例。
- **新指标**：浪费比例、池命中率、其他请求的 TPOT / p99、CPU 遍历利用率。
- **场景**：KG 4 跳（以及 3 跳），服务器 8B / 70B 和 Mac 8B / 30B-A3B；负载从低到饱和。
- **产出**：明确判断 V-H3 在哪些设置下可能成立，指导 R4 的取舍。

### R4：多用户原型（约 5 天）

- **端侧（Mac）**：
  - 4–8 个本地并发请求（例如多个 agent 子查询，或同一用户的多个问题）；
  - 共享遍历线程池 + 路径 KV 池（统一内存）+ MLX 上的低优先级预算队列；
  - 实测 TTFT、吞吐、干扰。
- **服务器（H200）**：在 vLLM 上加一个低优先级预算队列，参考 InferCept 的"用空闲算力分块计算"；路径 KV 池放内存，通过 LMCache 或自写的加载。用 70B（TP=2，GPU 0–2 中空闲的两张）测负载曲线。
- **基线**：
  - vLLM 前缀缓存；
  - SubGCache 式（按簇共享子图 KV，检索后）；
  - Stream2LLM 式（前缀语义的流式 prefill）；
  - CacheBlend 式（检索后复用）。
- **判据**：V-H3、V-H4。

## 3. 指标和基线（统一）

- **延迟**：首 token 延迟 p50 / p90 / p99、端到端延迟、TPOT（自己的和同时运行的其他请求的）。
- **效率**：吞吐（请求/秒）、GPU 利用率、CPU 遍历利用率、浪费的预算 token 占比、KV 池命中率、加载带宽。
- **准确率**：CWQ / WebQSP Hit@1、F1；改格式或拼接后相对完整 prefill 的变化。
- **基线**：
  - 完整 prefill；
  - GraphRAG-Opt（逐条路径独立 KV + 拼接，即路线 0）；
  - vLLM 前缀缓存；
  - CacheBlend 式事后复用；
  - SubGCache；
  - Stream2LLM 式流式 prefill；
  - RAGCache 式推测（文本场景）。

## 4. 风险

| 风险 | 应对 |
|---|---|
| 优化后检索时间大幅缩短，窗口消失 | R0 先测；转向尾部查询和多用户共享（V-H3 不依赖窗口长短） |

| 推测预算干扰其他请求（Stream2LLM 观察到 p99 恶化） | 最低优先级 + 每轮预算上限 + 接纳策略；R3 / R4 报告干扰 |
| 复用率取决于数据和到达顺序 | R3 扫到达顺序；报告 WebQSP（低复用）和 CWQ（高复用）两端 |
| 端侧 CPU 遍历和 GPU prefill 争统一内存带宽 | R2 实测 |
| 和 Stream2LLM / GLM / SubGCache 的区分被质疑 | 实验里直接跑它们的思路作为基线，突出 trie mask 语义（剪枝不作废，代价是需要 LoRA 或重算）和跨用户共享 |
