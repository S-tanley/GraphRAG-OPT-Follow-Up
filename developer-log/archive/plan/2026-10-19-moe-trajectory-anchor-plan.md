# Plan：用历史路由轨迹做多层提前预测（Anchor Pool），再加 expert 替换

*Bowen · 2026-10-19 · 状态：计划阶段*

依据：

- `report/2026-10-19-moe-edge-phase-a.md`：在线预测很准，但提前量只有一层；请求级预测提前量长，但不准。
- 本次讨论中提出的想法：按 token 维护历史路由轨迹池，用当前层的相似度匹配历史轨迹，延续它去预测后面几层；预测出现小错误时，用已经在内存里的 expert 替换。

---

## 0. 动机：准确率和提前量之间的矛盾

阶段 A 的结果可以归结为一张表（recall@2k，A 档三个模型的短答案负载）：

| 信号 | 什么时候能拿到 | 准确率 | 提前量 |
|---|---|---|---|
| 请求级预测（检索或问题文字） | prefill 前 | .54–.75（完美的请求级预测上限 .86–.94） | 整个请求 |
| 当前输入 token 查表 | decode 每一步开始时 | .70–.83 | 一步之内；越往后的层越不准 |
| 提前一层的 gate | 上一层算完时 | .81–.84 | **一层**（Mac 上约 0.2–0.6 ms） |
| 上面两个组合 | – | .89–.93 | 一层 |

在 Mac 上，从内置盘读一个 expert 约 1 ms，decode 每层平均缺 1–3 个。**要把加载藏住，大约需要提前 2–6 层知道要用哪些 expert**（§4.1 会精确地算出来）。现有方法里，没有一个能同时做到"准"和"提前 2 层以上"。

**想法**：同一个 token 后面几层走的 expert 不一样，是因为上下文让它的 hidden state 偏离了。但路由只由每一层的输入决定，所以**如果当前层的状态和历史上某一次很像，后面几层大概率也会沿着那次的轨迹走**。为每个 token 维护一个历史轨迹池（anchor pool），在第 l 层找到相似的历史，就可以延续它的轨迹，预测第 l+1 到 l+h 层。

偶尔猜错时，如果猜错的 expert 和真正该选的 expert 分数相差不大，就直接用已经在内存里的那个（expert 替换），不再等待加载。

## 1. 相关工作，以及我们和它们的区别

| 类别 | 工作 | 做法 | 和本计划的区别 |
|---|---|---|---|
| 提前多层的 gate | HOBBIT | 把当前 gate 的输入直接送进后面 p 层的 gate；Mixtral 上提前 1 层约 96%，提前 2–3 层约 90% | 不用历史，只用当前 hidden state。我们把它作为主要基线，也可以和它组合 |
| 训练式预测器 | Pre-gated MoE、ProMoE、AdapMoE | 训练一个小网络，从当前 hidden state 预测后面层的 expert | 需要训练，且没有利用"同一个 token 的历史"。作为基线（§3.3 的 LEARN） |
| 历史匹配 | MoE-Infinity | 请求级：用历史请求的激活矩阵匹配当前请求 | 粒度是请求，不是 token 加层 |
| 路径查表 | EdgeMoE | 用前 2 层的 expert ID 查表预测下一层（命中 87%） | 只预测下一层，不按 token，不延续多层 |
| 跨上下文复用 | KVComm | 维护 anchor 池，估计 KV 在不同上下文下的偏差 | 思路相同（anchor + 相似度），我们用在路由轨迹上 |
| expert 替换 | Cache-Conditional Experts（Qualcomm） | 分数接近时偏向已缓存的 expert；未命中减少 >50%，困惑度 +0.1–3% | 我们只在"预测错了、而且是近似平局"时替换，并在 KGQA 的准确率上评估 |

需要补做的文献检查：SiDA（用离线哈希预测 expert）、ExpertFlow 的 token 级路由路径预测、Fiddler / kTransformers 里的预测部分，确认"按 token 的轨迹池 + 多层延续"没有被做过。

| 编号 | 假设 | 判据 |
|---|---|---|
| **A1 可匹配** | 大部分 decode token，在池子里能找到当前层相似度足够高的历史 | 在设定的阈值下，覆盖率 ≥ 50% |

## 3. 方法设计

### 3.1 轨迹池（anchor pool）

- **键**：token ID。每个 token 一个池子。
- **池中的每条记录**：这个 token 某一次出现时的完整路由轨迹（每层选中的 k 个 expert），加上用来比较相似度的"状态描述"（见 §3.2）。
- **来源**：Wtrain 的 decode（离线建池），加上运行时已经完成的请求（在线追加）。
- **容量**：每个 token 最多 M 条（M ∈ {16, 64, 256}），超出时淘汰最旧的或最少被匹配到的。记录总内存和匹配耗时。
- **冷启动**：池子里没有这个 token，或者找不到足够相似的记录时，退回到"按 token 查表 + 提前一层 gate"。

### 3.2 怎么比较相似度（三档，从便宜到准）

| 档 | 状态描述 | 维度 | 代价 | 需要的数据 |
|---|---|---|---|---|
| S-route | 最近 w 层（w ∈ {1, 2, 3}）选中的 expert 集合，用重合度比较 | 离散 | 可以哈希，O(1) | **现有 trace 就有** |
| S-logit | 第 l 层（以及 l−1 层）router 的 logits，用余弦相似度比较 | E（64–160） | 小；路由本来就要算这些 logits | 需要重新采：在采集器里加存每层 logits |
| S-hidden | 第 l 层 MoE 输入 hidden state 的低维随机投影（64 或 128 维） | 64–128 | 小 | 需要重新采：加存投影 |

router 的 logits 本身就是 hidden state 的一个 E 维投影，而且是"对路由最相关"的投影，所以 S-logit 很可能已经足够。S-hidden 用来确认"信息有没有在投影里丢掉"。

### 3.3 预测方法（都输出第 l+h 层每个 expert 的分数）

| 名称 | 做法 | 类别 |
|---|---|---|
| TOKID | 只按 token 查表，不看上下文 | 基线 |
| GATE-h（HOBBIT 式） | 把第 l 层 MoE 的输入送进第 l+h 层的 gate | 主要基线 |
| PATH（EdgeMoE 式） | 用前 2 层的 expert ID 查表，只能提前 1 层；扩展到 h 层时逐层递推 | 基线 |
| LEARN（ProMoE 式） | 在 Wtrain 上训练一个小 MLP：输入第 l 层的 logits 或投影，输出第 l+h 层的 expert | 基线 |
| **ANCHOR-1** | 在池子里找最相似的 1 条历史，直接用它第 l+h 层的 expert | 我们的 |
| **ANCHOR-vote** | 取相似度最高的 m 条（m = 4–16），按相似度加权投票 | 我们的 |
| **ANCHOR+GATE** | ANCHOR 的分数和 GATE-h 的分数加权组合；匹配不上时只用 GATE-h | 我们的 |

每个预测还要输出一个**置信度**（最高的相似度、投票的集中程度），用于"只在置信度高时预取"。

### 3.4 预取策略（用在模拟器和原型里）

- 在第 l 层，对 h ∈ {1, …, H} 层之后的预测按置信度排序发出预取；提前越多层的预取优先级越低，近的先加载。
- 和缓存替换策略配合：预取进来的 expert 分数要高于"这一步用不到的"常驻 expert，才允许替换。
- 扫描 H ∈ {1, 2, 3, 4, 6, 8}，以及置信度阈值。

### 3.5 expert 替换（A4）

规则（只在 decode 时用，prefill 不变）：

1. 第 l 层的 gate 算完后，如果它选中的某个 expert e 不在内存里、而且加载来不及完成，就去找一个**在内存里**、分数和 e 相差小于 δ 的 expert e′；
2. 用 e′ 代替 e，路由权重仍用原来的分数（或者重新归一化，两种都测）；
3. **分数最高的那一个（top-1）永远不替换**；DeepSeek 和 GLM 这类有共享 expert 的模型，共享 expert 不受影响；
4. 扫描 δ，同时记录"实际触发了几次替换"。

对照组：
- 不替换，等待加载；
- Cache-Conditional Experts 的原始做法：所有 token、所有层都给已缓存的 expert 加分；
- 随机替换（同样的替换次数），用来证明"挑近似平局"是有意义的。

## 4. 实验步骤

### P0：离线可行性（用现有 trace，CPU，约 1 天）

- 用 S-route（最近 w 层的 expert 重合度）实现 ANCHOR-1 和 ANCHOR-vote。池子用 Wtrain 的 decode 轨迹；W2c 的池子用其他请求的轨迹（留一法）。
- 模型：A 档三个，加上 B1（GLM 4bit）。负载：W1-CWQ、W1-WEB、W2c。
- **输出**：
  - 覆盖率随阈值的变化（A1）；
  - h = 1, 2, 3, 4, 6, 8 时的 recall@k 和 recall@2k，对比 TOKID，以及 trace 里已有的提前一层 gate（A2 的初步结果）；
  - 匹配上和匹配不上的 token 分别统计。
- **算出"需要提前几层"**：用 tsim 的硬件参数，把"提前 h 层、准确率 p 的预测"代入，扫出 decode 停顿随 h 和 p 的变化，得到一张"要达到某个停顿减少比例，需要多少 h、多少 p"的图。
- **继续 / 停止**：如果 S-route 在 h = 2–3 时比 TOKID 高不了多少，而且覆盖率 < 30%，就先做 P1 看看 S-logit 能不能救；如果 S-logit 也不行，停止。

### P1：采集 router logits 和 hidden state 投影（约半天）

- 扩展 `collect_traces_mlx.py`：每个 decode token、每层存 router logits（fp16），以及 MoE 输入的 64 维随机投影（固定随机矩阵，fp16）。
- 存储量：OLMoE 每 token 约 2KB + 2KB；Qwen3-30B 约 12KB + 6KB。W1 加 Wtrain 加 W2c 一共几 GB 以内。
- 同时把 **GATE-h（HOBBIT 式）** 直接算出来存下：在第 l 层把 MoE 输入送进第 l+1 … l+H 层的 gate。这个必须在运行时算，事后补不了。
- 模型：A 档三个（都能整个放进内存，很快）。B1（GLM 4bit）用 offload 引擎采，在 B 档队列之后。

### P2：离线比较全部预测方法（约 1–2 天）

- §3.3 的所有方法 × §3.2 的三档相似度 × h = 1…8。
- LEARN 在 Wtrain 上训练，在测试集上评估。
- **成本**：每个 token 每次匹配的耗时（池子用 numpy 或 MLX 实现）、池子总内存，要求匹配耗时 < 每层计算时间的 20%。
- **输出**：准确率 vs 提前量的曲线（每个方法一条）；覆盖率 vs 阈值；A2 的判定。

### P3：系统模拟（约 1 天）

- 扩展 `tsim.py`：让 decode 支持"提前 h 层、带置信度"的预取（§3.4）。预测来自 P2 存下的结果。
- **对比**：
  - 提前一层 + MoE-Infinity 式缓存（目前最强的基线）；
  - GATE-H（HOBBIT 式多层）；
  - ANCHOR+GATE；
  - 完美的提前 H 层预测（上限）。
- 扫描：缓存 25%、50%、75%，H，置信度阈值。负载：W1 和 W2c（长 decode 才是这个方向最可能见效的地方）。
- **指标**：decode 停顿、每 token 延迟、预取浪费的字节、SSD 带宽利用率。
- A3 判定。

### P4：expert 替换的准确率实验（真实运行，约 1–2 天）

- 在 MLX 里实现 §3.5 的替换规则。缓存状态来自真实运行（A 档用模拟的缓存容量，B1 用 offload 引擎的真实缓存）。
- 扫描 δ，测 W1-CWQ、W1-WEB 的 Hit@1 / F1，以及 W2c 最终答案的准确率；同时记录触发了多少次替换、消除了多少停顿。
- 和 P3 结合：替换只用来处理"预测错了、来不及加载"的那部分。
- A4 判定。

### P5：原型实测（B1 GLM-4.5-Air 4bit，约 2 天）

- 在 `offload_engine.py` 里加入：轨迹池、提前 H 层的预取线程、替换规则。
- 测单用户的每 token 延迟、首 token 延迟、答案准确率；对比 mmap 基线、LRU、MoE-Infinity 式加提前一层。
- 用实测核对 P3 的模拟。

## 5. 和检索的关系（A5）

这个方向本身是通用的 MoE offload 优化，不依赖检索。和 GraphRAG 的联系在于：

- KGQA 的答案主要是实体名，同一个实体在不同请求之间反复出现；检索结果在 prefill 前就给出了候选实体。所以可以在 prefill 时，**把候选实体那些 token 的历史轨迹先放进池子、甚至提前预取**。
- 检验方法：比较 W1（实体答案）和 W2c（长推理文本）的覆盖率和准确率；再比较"用候选实体预先装池"和"不预先装池"。

如果 A5 不成立，这个工作就作为一般的 MoE offload 方法来写，检索只是其中一个应用场景。

## 6. 风险

| 风险 | 应对 |
|---|---|
| 覆盖率低：很多 token 在历史里出现太少 | 匹配不上时退回 GATE-h / TOKID；报告分开统计；考虑按"token 加上前一个 token"建池等更细或更粗的键 |
| 用路由集合比较相似度太粗 | P1 改用 logits / hidden 投影 |
| 匹配本身太慢，吃掉了省下的时间 | S-route 用哈希；S-logit 用小维度余弦加每个 token 的池子上限；在 P2 里测耗时 |
| 4bit 量化让路由更"抖"（§1 里约 20% 的边界 expert 会变） | 同时在 bf16 的 A 档模型（OLMoE、DeepSeek-V2-Lite）上做；替换规则正好能消化边界抖动 |
| 替换对 KGQA 准确率的影响比通用测评大（答案是实体名，一个 token 错就整体错） | 只在近似平局时替换，永不替换 top-1；准确率是主要判据之一 |
| B 档采集占着 GPU | P0 只用 CPU；P1 采 A 档时先暂停 B 档，或者把 B 档的采集量按之前的建议缩减 |
