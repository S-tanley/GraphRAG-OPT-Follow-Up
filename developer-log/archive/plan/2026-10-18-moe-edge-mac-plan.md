## 0. v2 改了什么、为什么

v1 根据 H200 中期报告得出"检索信号对 decode 没多大用"，于是把重点转到了 prefill 侧。讨论后发现，那份报告的分析有几处跑偏了，v2 改正如下：

| v1 / 中期报告的问题 | v2 的修正 |
|---|---|
| 只用"搬运了多少字节"来评估，没有模拟预取的提前量，也没有模拟加载和计算的重叠 | 所有调度实验改用**按时间推进的模拟**，指标是停顿时间、首 token 延迟、每 token 延迟、吞吐。请求级预测的价值主要在于"更早知道"，必须在时间维度上评估 |
| 把整个请求的 expert 并集当成 decode 的特征（W2 的并集是 93%），据此认为"decode 没有调度空间" | decode 是逐个 token 自回归生成的，每一步用的 expert 都不一样。**一段长 decode 可以看成很多段短 decode**，每一段的分布都不同，可以分段组 batch，再结合 continuous batching |
| 先按 schema 分组，再看组内 decode 是否相似 | 先按**实际 decode 的相似度**定出分组（目标），再找准入时或 prefill 后能拿到的信号去逼近它（要学的映射） |
| 把 prefill 和 decode 当成同一个 batch | 两个阶段的 expert 分布不同，**分开组 batch**：prefill 后重组 decode batch，decode 过程中再分段重组 |
| W2 的生成上限是 384，大部分思维链被截断 | 生成上限提高到 2048（B 档大模型用 1024），让答案能完整生成 |
| 去掉了 E2（亲和性组 batch），理由是端侧只有一个请求 | 增加一个"本机作为小型服务器"的多请求场景（S2），E2 保留并扩展 |

**v2 的依据：讨论中用 H200 上 GLM 的 trace 补做的两项分析**（脚本：`experiments/moe/regroup_bound.py`、`regroup_pred.py`）。

1. **prefill 结束后，按 decode 的相似度重组 batch，有明显的空间。** 指标是 decode 时每个 token 每层平均要加载的 expert 数（不算缓存）：

   | | B=8 | B=16 | B=32 |
   |---|---|---|---|
   | 随机分组 | 5.92 | 5.04 | 4.04 |
   | 按实际 decode 分布分组（上限） | −20% | −22% | −19% |
   | **CANDFIRST**（生成的第一个 token + 检索到的候选实体 → 推出答案的 token → 查"该 token 在 decode 位置走哪些 expert"的表） | **−16%** | **−18%** | **−14%** |

   CANDFIRST 能拿到上限的 68–82%。之前的检索查表预测器（OURS_ADMIT、RPP_R）只能拿到 5–24%，按 prefill 实际分布分组只有 8–16%。

2. **decode 的路由主要由"生成了哪些 token"决定。** 直接用真实答案的 token 去查表，能拿到上限的 86–98%。所以"按 decode 的相似度分组"本质上就是"按答案像不像来分组"。候选答案只能来自检索路径，所以这个信号和检索是直接绑定的。

3. **反面结果**：prefill 按相似度分组没有用，只要 batch 有 4 个以上请求，每层都会用到 125–128 个 expert（共 128 个）。把整个长 decode 当成一个整体来分组，也几乎没用（W2 只有约 2%）。这正说明长 decode 应该**分段**来处理。

## 1. 本机硬件（2026-10-18 实测）

| 项目 | 数值 |
|---|---|
| 芯片 | Apple M5 Max：CPU 18 核（6 超大核 + 12 性能核），GPU 40 核，Metal 4 |
| 统一内存 | 64 GB；GPU 推荐的工作集上限 55.7 GB；单个 buffer 最大 41.7 GB；给模型的预算按 ≤ 48 GB 计 |
| 内存带宽（MLX） | 读 519 GB/s；读写混合 386 GB/s |
| SSD 读（文件 96GB，大于内存；绕过页缓存） | 单线程 2.8–8.0 GB/s；4–8 线程 7.0–9.6 GB/s；块大小 17–35MB 时最好（约 9.5 GB/s） |
| SSD 写 | 5.4 GB/s |
| 可用磁盘 | 内置 313 GB；外置 ZBW-SSD1 630 GB（见 §1.1） |
| 单个 expert FFN（MLX，单独调用） | 140–200 µs，主要是调用和同步的开销；4bit 的 GLM expert（9.7MB）按带宽算只需约 19 µs，所以要用融合的 gather kernel |

和 H200 的对照：

| | 快存储 → 计算 | 慢存储 → 快存储 | 比值 |
|---|---|---|---|
| H200 | HBM 4.8 TB/s | PCIe 54 GB/s | 约 89× |
| M5 Max | 内存 519 GB/s | 内置 SSD 约 9 GB/s | 约 55–75× |

两者属于同一类问题。从 SSD 读一个 4bit 的 GLM expert 约 1.0 ms，是在内存里计算它的约 50 倍。

### 1.1 存储层级：把 Mac 当成一台"缩小版的 offload 服务器"

| Mac 上的存储 | 容量 | 读带宽（实测） | 对应服务器上的 | 用途 |
|---|---|---|---|---|
| 统一内存 | 64 GB（模型预算 ≤ 48 GB） | 519 GB/s | GPU 显存（HBM） | 常驻的非 expert 权重、expert 缓存、KV |
| 内置 SSD | 剩余 313 GB | 7–9.6 GB/s | 主机内存（CPU DRAM） | **当前实验模型的全部权重**；expert 按需从这里加载 |
| 外置 SSD（ZBW-SSD1，USB 10 Gb/s） | 剩余 630 GB | 约 1.1 GB/s（写 0.58 GB/s） | 服务器的磁盘 / 模型仓库 | 所有模型的长期存放位置 |

**流程**：所有模型下载到外置盘（`HF_HOME=/Volumes/ZBW-SSD1/hf`）。跑某个模型之前，把它整个拷到内置盘（60GB 约 1 分钟，133GB 约 2 分钟）；做完再从内置盘删掉。内置盘同时最多放一个大模型加小模型（133 + 62 GB），留 ≥ 50GB 余量。

**这个类比的两个局限，实验时要注意：**

1. **macOS 的页缓存也在统一内存里。** 如果从内置盘读文件时不加控制，读过的 expert 会被系统悄悄缓存在内存里，"主机内存"和"显存"两层就混在一起了。所以我们自己的加载器一律用 `pread` + `F_NOCACHE`，测量前用大于内存的文件冲掉页缓存。mlx-lm 默认用 mmap 读权重（由系统分页），这是端侧真实的默认行为，可以作为一个基线，但要单独说明它混用了两层。
2. **"主机"这一层不能计算。** 服务器上可以让 CPU 直接算冷门 expert（Fiddler 的做法），Mac 上的内置盘做不到这一点。所以"冷门 expert 在 CPU 上算"这条路只能在 H200 场景里研究。

外置盘还可以当作**第三档、更慢的存储**（内存与它的带宽比约 470 倍，接近手机闪存）。同一套 trace 和模拟器可以分别用"内置盘"和"外置盘"两组参数跑，看各个策略的收益随存储带宽怎么变化。不过它的主要用途还是存放模型。

**预取的时间窗口有多紧**：以 B1（4bit GLM）单请求的 decode 为例，算一层大约 0.2 ms（非 expert 权重约 0.1GB），加载一个缺失的 expert 约 1 ms。所以只靠提前一层预测，每层只能藏住约 1/5 个 expert 的加载。要藏住更多，必须更早知道要哪些 expert：
- 提前多层预测；
- prefill 后的请求级预测；
- 分段预测。

## 3. 模型

外置盘解决了空间问题，所以分两档：**A 档**是能整体放进内存的小模型，用来快速采集长 decode 的 trace；**B 档**就是 H200 计划里的四个模型（4bit），在 Mac 上做真实的 offload。全部存放在外置盘上，合计约 466GB。

| 编号 | 模型 | 结构（路由 expert / 选几个 / 共享） | 版本与大小 | 能否放进 48GB 预算 | 作用 |
|---|---|---|---|---|---|
| A1 | OLMoE-1B-7B-0924-Instruct | 64 / 8 / 0，16 层，从零训练 | bf16，13.8GB | 能 | 结构干净、数据开放 |
| A2 | DeepSeek-V2-Lite-Chat | 64 / 6 / 2，27 层 | bf16，31.4GB | 能 | 与 V2.5 同一家族；Cache-Conditional Experts 也用了它 |
| A3 | Qwen3-30B-A3B | 128 / 8 / 0，48 层 | 4bit，17.2GB | 能 | 与 Qwen3-235B 同一家族 |
| B1 | GLM-4.5-Air | 128 / 8 / 1，45 层 MoE | 4bit，60.2GB | 不能（约 70% 能常驻） | 和 H200 上 bf16 的 trace 是同一个模型，可以检验量化对路由的影响 |
| B2 | Mixtral-8x22B-Instruct | 8 / 2 / 0，56 层 | 4bit，79.1GB | 不能（约 55%） | 由 dense 改造的 MoE；expert 少而大 |
| B3 | Qwen3-235B-A22B | 128 / 8 / 0，94 层 | 4bit，132.3GB | 不能（约 33%） | 重度 offload |
| B4 | DeepSeek-V2.5-1210 | 160 / 6 / 2，59 层 MoE | 4bit，132.7GB | 不能（约 33%） | MLX 社区只有 1210 版；H200 上用的是原版 V2.5，两者结构相同 |

- **A 档**：采集 trace 很快，W2（2048 个 token）的长 decode 主要在这一档上做；offload 在模拟器里通过限制缓存容量来模拟。
- **B 档**：权重在内置盘上，按需加载。采集 trace 会比较慢，因为没缓存的 expert 要从内置盘读。估算如下：
  - B3 / B4 每一步 batch decode 最坏要读约 85GB，约 10 秒；
  - 所以 B 档只采 W1、Wsyn、Wsyn-rand 和 Wtrain（1000 题），W2 只采 32 题、最多 1024 个 token；
  - 原型（阶段 D）在 B 档上实测。

软件用 MLX 0.32.4 + mlx-lm 0.32.2，原生支持以上全部结构。

## 5. 实验（沿用 H1–H4，按 v2 的认识修正）

### E1：预测力，按"什么时候知道"分三档（H1）

| 档 | 时间点 | 预测器 |
|---|---|---|
| T0 准入时 | 请求进来、prefill 之前 | GLOBAL、TOKAGG、RPP（基于 token）；SCHEMA、RELBAG、CANDTOK、RPP_R（基于检索） |
| **T1 prefill 后** | 拿到第一个生成的 token | **CANDFIRST**（新）；PREFILL；"第一个 token 的 decode 表 + 全局"（不用检索的对照） |
| **T2 分段在线** | decode 过程中，每 S 步（S ∈ {8, 16, 32, 64}）预测下一段 | 上一段的 expert 分布（时间局部性）；最近生成的 token 查表；CANDFIRST 剩下的答案 token；提前一层的 gate（逐 token） |

- **分组方法**：在 Wtrain 上按实际 decode 的分布（整段或分段）聚类，得到"目标分组"。再训练一个分类或回归模型，从 T0、T1、T2 能拿到的特征映射到这些组。
- **指标：**
  - 每档的 recall@B；
  - 每档的提前量：从知道到需要，中间有几层、几步；
  - 用每档预测去做分组时，能拿到上限的多少（和 §0 的表口径一致）。
- **判据（H1 修正版）**：在 T1 或 T2，基于检索的预测比不用检索的对照多拿到 ≥ 20 个百分点的"上限比例"，或者 recall@2k 高 ≥ 5 个百分点；4 个模型里至少 2 个成立。
  - 在 GLM 上，CANDFIRST 能拿到上限的 68–82%，不用检索的 token 基线只有 8–13%，已经满足这一条。
  - 还需要做不用检索的对照："只用第一个 token 的表"，不匹配候选。

### E2：按阶段、按段组 batch（H2 扩展，S2 场景）

三层策略，依次叠加：

1. **prefill**：多个请求合成一个 batch，一起扫一遍 expert（MoE-Gen 的做法），作为基线。prefill 的分组不按相似度（已知没用）。
2. **prefill 后重组 decode batch**：按 T1 的预测（CANDFIRST）把请求分到 decode 组里。
3. **分段重组 + continuous batching**：
   - 同时在跑的请求数 N 大于每一步的 batch 槽位 B 时，每 S 步按 T2 的预测，挑出下一段要一起跑的 B 个请求，让它们的 expert 尽量重合；
   - 新请求随时加入、跑完的随时退出；
   - 用最长等待步数 τ 保证公平。

- **对照**：FCFS 的 continuous batching；随机分组；完美分组的上限（按实际的下一段分布）。
- **扫描**：N ∈ {8, 16, 32}，B ∈ {4, 8}，S ∈ {8, 16, 32, 64}，τ，到达率。
- **离线上限先做**：在现有 GLM 的 W2 trace（384 步，截断）上，算分段重组的上限和各预测器能拿到的比例。不需要 GPU，在阶段 A 完成。
- **判据**：在 P99 延迟增加 ≤ 10% 的前提下，每 token 从 SSD 读的字节减少，或吞吐提高 ≥ 15%（相对 FCFS 的 continuous batching）。

### E3：缓存 + 预取（H3，按时间评估）

- **预取策略：**
  - 按需加载（基线）；
  - 提前一层的 gate（HOBBIT 式）；
  - 提前 p 层（p = 2、3）；
  - T1 的请求级预测在 prefill 尾部预取；
  - T2 的分段预测在每段开始时预取；
  - 以上的组合。
- **缓存替换**：LRU、MoE-Infinity 式、HYB（请求内计数 + 预测先验），以及按阶段切换（prefill 用全局热度，decode 用预测）。
- **指标**：停顿时间、每 token 延迟、浪费的预取字节（预取了但没用上）、SSD 带宽利用率。
- **判据**：相对"提前一层 + MoE-Infinity 式缓存"这个最强基线，S1 下每 token 的停顿时间减少 ≥ 20%。

### E4：prefill 结束时保留哪些 expert（H4）

- 用 T1 的预测（CANDFIRST）决定 prefill 扫描时各层留下哪些 expert。中期报告里用的是 T0 的预测，只减少了 7–13% 的前 8 步未命中；完美的请求级预测能减少 80–90%。
- 指标：前 N 步（N = 1、8、32）的停顿时间，S1 场景。

### E5（次要，保留 v1 的想法）：复用检索上下文的 KV，减少 prefill 要加载的 expert

- 已缓存 KV 的 token 不必再经过 FFN。在 GLM 上，只 prefill 问题 token 时，每层用到的 expert 从 94% 降到 38–49%。
- 测路径段的跨请求复用率、准确率影响、prefill 从 SSD 读的字节，以及首 token 延迟。
- 只在 E1–E4 的主线推进之后、时间允许时做。

### E6（可选）：只对检索上下文 token 做"偏向已缓存 expert"的有损路由

- 参照 Cache-Conditional Experts，但只用在路径 token 上。画出"SSD 字节 vs Hit@1"的曲线。
- 优先级最低。

## 6. 实现

1. **按时间推进的模拟器**（`experiments/moe/tsim.py`，新写）：
   - 逐层、逐步地模拟计算时间和 SSD / PCIe 的传输队列，记录每个预取请求发出和完成的时间；
   - 支持多请求、分段重组和 continuous batching；
   - 硬件参数有 `--hw mac` 和 `--hw h200` 两套，Mac 用本机实测值，H200 用解析值，GPU 恢复后再换成实测；
   - 输入沿用现有的 trace 格式。
2. **MLX trace 采集器**（`experiments/moe_edge/collect_traces_mlx.py`）：
   - 包装 mlx-lm 的 MoE 块，记录每层 top-k；
   - 同时实现各模型的"提前一层 gate"，在 A1（OLMoE）上用 HF 版本交叉验证（自洽性要达到 100%）；
   - 输出格式和 H200 版一致，额外记录生成的 token。
3. **预测器**：在 `e1_analysis.py` 里加入 T1（CANDFIRST 等）和 T2（分段）两档，以及"目标分组 + 学习映射"的流程。
4. **离线重组分析**：把 `regroup_bound.py` / `regroup_pred.py` 扩展成分段版本。
5. **B 档原型**（`experiments/moe_edge/offload_engine.py`；先做 B1，再扩展到 B2–B4）：
   - 运行前把模型从外置盘拷到内置盘，权重按 (层, expert) 重新排成连续的文件；
   - 非 expert 权重常驻内存；
   - expert 按 (层, expert) 连续存放，用 `pread` + `F_NOCACHE`、8 个线程读入预先分配的 buffer 池；
   - 预取线程和计算流水并行；
   - S2 下加入分段重组的调度器；
   - 基线是 mlx-lm 默认的 mmap，以及 LRU 缓存。

```
                     → MLX 采集器 + 一致性检查 → 阅读器检查

                     → E1：A 档 3 个 + B 档 4 个，共 7 个模型（B 档的四个就是 H200 计划的四个模型）
        │
阶段 C（第 8–11 天）：在 4 个模型的 trace 上，用按时间推进的模拟器做 E2（S2）、E3、E4
        │   决策：E2、E3、E4 中至少一个达到判据 → 阶段 D；否则写报告，和导师讨论
        │
阶段 D（第 11–16 天）：B 档原型（先 B1，再 B3 / B4），实测 S1 的首 token 延迟和每 token 延迟，以及 S2 的吞吐；
                      时间允许再做 E5
```

每个阶段结束都写报告，放在 `developer-log/report/`。H200 恢复后，守护脚本会自动续跑 Mixtral、Qwen3-235B、DeepSeek-V2.5；阶段 A 写好的模拟器可以直接用在那些 trace 上，W2 也会按 2048 的上限重新采集。

## 8. 风险

| 风险 | 应对 |
|---|---|
| CANDFIRST 只在答案就是候选实体时有效（GLM 的 CWQ 上有 66% 的请求能匹配上） | 匹配不上时退回到 T0 的预测；分开报告匹配上和匹配不上的请求；在 WEB 和其他模型上验证 |
| 分段重组需要切换 KV：同一组 KV 一直在内存里，只是每步挑一部分请求来算 | 统一内存里不需要搬运 KV；调度开销计入模拟和原型 |
| 分段重组降低公平性，拉高 P99 | 用 τ 限制等待；判据要求 P99 增加 ≤ 10% |
| 小模型（OLMoE）读不懂证据 | 按 E0 标准，把它排除在 H1 的结论之外，仍然可以用来分析路由 |
| 4bit 量化改变路由 | B1 和 H200 上 bf16 的 GLM trace 比较一致率；A2 用 bf16 |
| 本机磁盘和日常使用干扰计时 | 模型存外置盘，内置盘同时只放一个 B 档模型；计时实验放在晚上跑，重复 3 次取中位数；测量前先冲掉页缓存 |
| 外置盘（USB）断开或变慢 | 实验运行时只读内置盘，外置盘只在拷贝时用；拷贝后校验文件大小和哈希 |
| 页缓存让"主机内存"和"显存"两层混在一起 | 自己的加载器用 `F_NOCACHE`；mmap 基线单独说明（§1.1） |
| B 档采集太慢 | B 档不采长 W2；必要时把 Wtrain 降到 500 题，用 A 档补齐长 decode 的分析 |
| 模拟器里的计算时间不准 | 用本机实测的融合 kernel 耗时校准；阶段 D 用原型实测来核对模拟 |
