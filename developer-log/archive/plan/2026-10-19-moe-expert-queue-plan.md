# Plan：每个 expert 一个等待队列，"快满了再加载"（offload 下的多请求 decode）

*Bowen · 2026-10-19 · 状态：Q0、Q1、Q3 完成（2026-10-21，见 §8 和 `report/2026-10-21-moe-queue-pool-subst.md`）；原始的异步队列设计不成立；同步框架下的缓存感知路由在"被改动的 expert 使用 ≤ 约 10%"时不掉准确率*

> **2026-10-21：已并入 `plan/2026-10-21-moe-multiuser-scheduling-plan.md`，以后在那份 plan 里推进。**


依据：

- profiling（`outputs/moe_edge/profile/`，slides：https://claude.ai/artifact/2JhG3EUVVkCLQzYVhynXWY）：offload 的 decode 有 **84–89% 的时间在等 SSD**；而且每层只零碎地读几个到二十几个 2.65MB 的小块，有效读取速度只有 **1–5.5 GB/s**，远低于约 9 GB/s 的峰值。
- 分组矩阵乘法的微基准：同一步里，一个 expert 分到 1 个 token 和分到 8 个 token，耗时几乎一样（43–54 μs）。所以全部常驻时攒 token 没有意义；但 offload 时一次加载约 1 ms，**每个 token 摊到的加载成本 ≈ 加载时间 ÷ 这次加载服务的 token 数**，攒 token 就能直接摊薄这个成本。
- 讨论中提出的想法：每个 expert 前面一个 buffer，快满了再加载。

---

## 0. 想法

现在的做法（同步的 continuous batching）：每一步，batch 里所有请求一起走完全部层；某一层要用的 expert 不在内存里，就立刻加载，所有请求一起等。一个只被 1 个 token 用到的冷门 expert，也要为它完整读一次。

新做法：**每个请求独立往前走，每层每个 expert 一个等待队列。**

1. 请求走到第 l 层、路由到某个不在内存里的 expert e 时，先在 (l, e) 的队列里排队，不立刻加载；
2. 队列里的 token 快攒够时，就发出加载；阈值设成"加载完成时队列刚好攒满"，让加载和攒 token 重叠进行；
3. SSD 的加载顺序按"排队的 token 数 ÷ 加载代价"排，先加载等的人多的 expert，每读一个字节服务的 token 最多；
4. 每个 token 设一个最长等待时间：冷门 expert 迟迟攒不满时，到时间就加载；或者用已经在内存里、分数接近的 expert 顶替（expert 替换，见 `2026-10-19-moe-trajectory-anchor-plan.md` 的 §3.5）；
5. 已经在内存里的 expert，照常立刻计算，不排队。

**心跳（最小推进粒度）**：完全异步会让 GPU 上冒出大量零碎的小活。profiling 测到：一次 expert 计算即使只有 1 个 token 也有约 43 μs 的固定成本，每个小操作还有几十微秒的启动和同步开销，offload 引擎在路由后还必须同步一次。所以加一个全局心跳：每跳一次（或每隔几跳）统一检查所有队列，把超过阈值的、加载已完成的、已就绪的工作攒在一起，一次往前推一步；两跳之间到达的工作等下一跳。每一跳依次做三件事：

1. **发起加载**：超过阈值（或预计加载完成时能攒满）的 expert 在这一跳统一发出读取，读取也成批；
2. **执行计算**：对每个有就绪 token 的层各做一次，attention、路由、分组矩阵乘法都是这一层所有就绪 token 拼成的一个批次；
3. **推进状态**：k 个 expert 都完成的 token 进入下一层；等待超时的 token 按"直接加载"或"用常驻 expert 顶替"处理。

**和"attention / expert 交替重叠"的关系**：前沿系统（DeepSeek 的双微批次、MegaScale-Infer 的乒乓、NanoFlow）的本质是"一批请求等待时，让另一批用 GPU"。同一个请求内部没法重叠（第 l+1 层的 attention 要等第 l 层的 MoE），重叠只能来自不同请求之间，而请求独立推进 + 心跳天然就是这样：一个请求在等 expert 时，别的请求做 attention 或算已加载的 expert。固定两组的乒乓是它的特例。需要注意两点：（1）重叠的前提是等待时有就绪的活；一个 token 要等它最慢的 expert，大部分请求可能同时卡住，GPU 就没活干；（2）offload decode 里 GPU 计算只占约 10–15%，重叠最多藏住这部分，大的收益仍在减少和摊薄加载。所以每一跳内部的顺序要安排成**先给就绪 token 做 attention 和路由、尽早发出加载，再算已经加载好的 expert**，让加载尽早开始。

心跳长度是一个连续的旋钮：最长时一跳等于整个模型走一步，就是现在的同步 continuous batching；最短时来一个处理一个，就是完全异步。最优点取决于每层计算时间（Mac 上约 0.2–0.6 ms）和一次 SSD 加载时间（约 1 ms）。

**一个必须正视的约束**：每个 token 每层要用 k 个 expert（Qwen3 是 8 个），8 个都算完才能进入下一层。所以**一个 token 的速度取决于它最慢的那个 expert**。只要 8 个里有 1 个在排冷门队列，这个 token 就得等。最长等待时间和 expert 替换都是为此准备的。这一点决定了这个方法能不能成立，Q0 要先量出来。

## 1. 一个粗略的模型

- 同时在 decode 的请求数为 N，每个 token 选 k 个 expert，每层共 E 个 expert。每一步、每个 expert 平均分到 λ = N·k/E 个 token。
  - Qwen3-30B（k=8，E=128）：N=64 时 λ=4；要攒 16 个，大约要等 4 步。
  - OLMoE、DeepSeek-V2-Lite（E=64，k=8 / 6）：λ 是 Qwen3 的 1.5–2 倍，更容易攒满。
- 但 expert 的热度不均匀（之前在 GLM 上统计过：单个请求内部，用得最多的 16 个 expert 承担了它 decode 约 84% 的使用；跨请求的全局热度分布还没有量过）。热门 expert 一直在内存里，不需要攒；冷门 expert 的 λ 远小于平均值，攒满要很久。**真正要靠队列摊薄的，是"中间热度"的那批 expert。** Q0 要从 trace 里量出各层 expert 的到达率分布。
- 吞吐的上限：如果每次加载平均服务 n 个 token，每 token 摊到的 SSD 时间约为（每个 token 缺的 expert 数 × 2.65MB ÷ SSD 带宽）÷ n。另外，攒批之后一次能读更多个 expert，读取更"整"，有效带宽也会从 1–5.5 GB/s 往 9 GB/s 靠近。两项一起作用。

## 2. 相关工作和区别

| 工作 | 做法 | 区别 |
|---|---|---|
| MoE-Gen（调研过） | 离线吞吐场景：按模块攒大量 token，再成批加载 expert、成批计算 | 所有请求同步推进，一次攒一大批；没有每个 expert 的队列、触发阈值和等待上限，不适合在线服务 |
| Klotski（调研过） | 多个 batch 交错，让 expert 加载和计算重叠 | 粒度是 batch，不是"每个 expert 一个队列" |
| MoE-Lightning（调研过） | CPU、GPU、I/O 三者流水，batch 推理 | 同上 |
| ExpertFlow（调研过） | 相邻 decode batch 之间重新分组 token | 不攒 token，也没有等待上限 |
| 多卡 expert 并行的负载均衡（DeepSeek EPLB 等） | 复制热门 expert | 解决的是多卡的长尾，不是 offload 的加载 |

待补查：Lina、SiDA 之类的工作里有没有"按 expert 排队"的调度；数据库 / 存储里"攒批 I/O"的经典做法（group commit 等）可以作为设计参考。

## 3. 要验证的假设

| 编号 | 假设 | 判据 |
|---|---|---|
| **Q-H1 能攒起来** | 在实际的并发和 expert 热度下，"中间热度"的 expert 能在可接受的等待内攒到足够的 token | Q0 给出：等待 ≤ 2 步时，平均每次加载服务的 token 数比同步做法多 ≥ 2 倍 |
| **Q-H2 不被最慢的 expert 拖垮** | 有最长等待时间（必要时加 expert 替换）之后，"token 等最慢的 expert"带来的延迟可控 | 每 token 延迟的 P99 ≤ 同步做法的 1.5 倍 |
| **Q-H3 吞吐提升** | 队列 + 触发阈值 + 按收益排序加载，在 offload decode 下明显提高吞吐 | 和最强的同步基线比（同步 continuous batching + MoE-Infinity 式缓存 + 提前一层预取），在 P99 满足 Q-H2 的前提下，吞吐提高 ≥ 30% |
| Q-H4 读得更整 | 攒批后单次加载的 expert 更多，有效 SSD 带宽更高 | 有效带宽从 1–5.5 GB/s 提到 ≥ 7 GB/s |
| Q-H6 心跳 | 合适的心跳长度，能在完全异步和完全同步之间取得比两端都好的吞吐 / 延迟 | 存在某个心跳长度，吞吐不低于完全异步的最好结果，同时每 token 的启动和同步次数至少减半 |
| Q-H5 和预测结合 | 用轨迹池 / 提前一层的预测，提前知道"接下来哪些 expert 的队列会涨"，可以更早触发加载 | 在 Q-H3 的基础上，P99 再降 ≥ 15% |

## 4. 实验步骤

### Q0：从现有 trace 量出"能不能攒起来"（CPU，约半天）

- 数据：A 档三个模型的 chat 版 W2（长 decode），以及 W1；后续加上 B 档。
- 把 N 个请求的 trace 叠在一起，按步统计每层每个 expert 的到达 token 数：λ 的分布、热门 / 中间 / 冷门 expert 各占多少使用量。
- 不考虑时间，只按"步"算：给定缓存（50% 常驻，LFU）、阈值 n 和最长等待 w 步，算出
  - 平均每次加载服务的 token 数；
  - 一个 token 每层要等的步数（取它 k 个 expert 里最慢的那个）的分布。
- 这一步直接回答 Q-H1，以及 Q-H2 的大致情况。如果"最慢的 expert"让大部分 token 都要多等好几步，后面就要以 expert 替换为前提来设计。

### Q1：写一个按事件推进的异步模拟器 `tsim_async.py`（约 1.5 天）

- **请求各自推进**：每个请求有自己的当前层和当前步。引擎每一拍挑一层执行，把这一层所有就绪的 token 一起做 attention、路由和 expert 计算（attention 各自用自己的 KV，权重共用）。挑哪一层：先实现"就绪 token 最多的层"，再试轮转。
- **expert 计算**：已常驻的 expert 立刻算；不常驻的进队列。队列被清空（expert 加载完）时，这批 token 一起算。一个 token 的 k 个 expert 都算完，才进入下一层。
- **加载器**：沿用 `tsim.py` 的 SSD 模型；新增"按收益排序"和"按队列阈值触发"；并发读的数量可调（用来体现 Q-H4 的读取更整）。
- **计算时间**：用 profiling 的实测值校准。attention 和非 expert 部分按"就绪 token 数"查表；分组矩阵乘法按（token 数，不同 expert 数）用微基准拟合。
- **固定开销必须计入**：每次 kernel 启动、每次同步（包括路由结果同步到 CPU）、每次 expert 计算的固定成本（约 43 μs），都按 profiling 的实测值加进去。否则完全异步在模拟里会显得不切实际地好，心跳的价值也看不出来。
- **心跳**：支持完全异步、固定间隔 T、每跳一层、自适应（攒够工作量或等满 T，先到先触发）几种模式。
- **对照组**：
  1. 同步 continuous batching + LRU；
  2. 同步 + MoE-Infinity 式缓存 + 提前一层预取（最强基线）；
  3. MoE-Gen 式的大批量攒（吞吐上限，不管延迟）；
  4. 异步但不设阈值（来了就加载），用来分离"异步推进"和"攒批"各自的作用；
  5. 同步 batching + 两个微批次乒乓重叠（attention 和 expert 交替，前沿系统的做法），用来回答"按请求独立推进是否已经包含它的收益"。

### Q2：策略扫描（约 1 天）

- 阈值 n ∈ {2, 4, 8, 16}，或"预计加载完成时恰好攒满"的自适应阈值；最长等待 w；加载优先级（先到先服务 / 按队列长度 / 按收益）；并发 N ∈ {8, 16, 32, 64, 128}；缓存 25%、50%、75%。
- **心跳**：完全异步、固定间隔 T ∈ {0.25, 0.5, 1, 2} ms、每跳一层、自适应、同步 continuous batching（心跳最长的极端）。
- **一跳内部的顺序**：先路由（尽早发出加载）vs 先算已加载的 expert。
- **指标**：吞吐、每 token 延迟的 P50 / P99、每 token 摊到的 SSD 读取量、有效 SSD 带宽、GPU 忙碌比例；以及衡量"零碎程度"的指标：每个 token 摊到的 kernel 启动次数和同步次数、每次 expert 计算平均处理几个 token、每次 SSD 读取平均读几个 expert；以及衡量重叠的指标：GPU 忙碌比例、"所有请求都在等加载"的时间占比、计算被 I/O 藏住的比例。
- 输出：吞吐对 P99 延迟的曲线（每种策略一条），对照组画在同一张图上。判定 Q-H3、Q-H4。

### Q3：最长等待之后怎么办（约 1 天，和轨迹池 plan 的 P4 合做）

- 到时间的冷门 expert：（a）照常加载；（b）用分数接近的常驻 expert 顶替；（c）在服务器上交给 CPU 算（Mac 上没有这个选项，CPU 一样要先读进来）。
- (b) 要在真实模型上测准确率（W1 的 Hit@1，W2 的答案准确率）。判定 Q-H2 的完整版本。

### Q4：和预测结合（约 1 天）

- 用提前一层的 gate 和轨迹池的多层预测，估计"接下来几层、各 expert 的队列会涨多少"，提前触发加载。判定 Q-H5。

### Q5：原型（只有 Q-H3 成立才做，约 3 天）

- 在 MLX 上写一个按层调度的执行器：请求各自维护进度，引擎每次挑一层，把就绪的 token 拼起来算，expert 队列和加载线程用 `offload_engine.py` 的存储和缓存池。
- 在 B1（GLM-4.5-Air 4bit）或 Qwen3-30B 上实测吞吐和 P99，核对 Q2 的模拟。

Q0（trace 统计）──能攒起来──→ Q1（异步模拟器）──→ Q2（策略扫描）──Q-H3 成立──→ Q5（原型）

## 5. 适用范围

- **适用**：多请求、看吞吐的 offload 服务（edge plan 的 S2：Mac Studio 当小型服务器、agent 并发子查询；也包括单卡服务器 + 主机内存）。
- **不适用**：单用户（S1）。没有别的请求可以凑，队列攒不起来，退化成按需加载。
- **和检索的关系**：这个想法本身是通用的 MoE offload 调度。检索可以起的作用是：同一批请求如果来自同一个主题（比如 agent 对同一个知识图谱子区域的多个子查询），它们用的 expert 更集中，队列更容易攒满。可以在 Q2 里加一个"按主题聚集的请求流"和"随机请求流"的对比。

## 6. 风险

| 风险 | 应对 |
|---|---|
| 一个 token 要等它最慢的那个 expert，P99 被拉长 | Q0 先量；用最长等待 + expert 替换；替换的准确率在 Q3 测 |
| 按层调度让 attention 的 batch 变小、变碎，非 expert 部分变慢 | 模拟器里按就绪 token 数计 attention 的耗时（用 profiling 的实测）；调度时优先选就绪 token 多的层 |
| 异步推进需要为每个请求保存层间的中间状态，占内存 | 统计中间状态的大小（每个 token 每层一个 hidden state，几 KB），在模拟里计入内存预算 |
| 模拟器太乐观 | Q5 的原型实测核对 |
| Mac 的 GPU 正在跑 B 档采集 | Q0–Q4 只用 CPU 和现有 trace，不受影响；Q5 需要 GPU，排在 B 档之后或暂停 B 档 |

## 8. Q0 / Q1 结果（2026-10-21，GLM-4.5-Air bf16 W2c CoT 200 个请求，请求从随机位置开始）

### 8.1 H200 微基准（GLM 的形状，`outputs/moe/queue_microbench_h200.json`）

| 项 | 数值 |
|---|---|
| 一个 expert（34.6 MB）走 PCIe 从主机内存读入 | 约 1.0 ms（35 GB/s）；一次读 16 个时 50 GB/s |
| 分组矩阵乘法（`torch._grouped_mm`） | 约 50 µs + 每多一个 expert 12.5 µs，和 token 数（1–64 / expert）几乎无关 |
| attention + 投影 + 路由（每层，非融合实现） | B=1–16 约 140–170 µs；B=256、上下文 2k 约 1.05 ms |
| kernel 启动 / 路由同步到 CPU | 12.6 µs / 20 µs |

加载一个 expert 约是算一个 expert 的 80 倍。

### 8.2 Q0：能不能攒起来（只按步算，不算时间）

- 每层最热的 25% / 50% / 75% expert 分别承担 52% / 78% / 93% 的使用。
- 最多等 2 步、阈值 n = 8–16 时，加载次数降到同步的 36–45%，也就是每次加载服务的 token 数 ×2.2–2.7。**Q-H1 成立。**
- 但 40–90% 的（token, 层）至少有一个 expert 在排队（"等最慢的 expert"）。每层平均要等 0.5–1.4 步，45 层累加起来不可接受。

### 8.3 Q1：按时间推进的模拟（`outputs/moe/q1_async.json`）

| 设置 | 同步 | 同步 + 提前 1 层预取 | 异步队列（最好的设置） |
|---|---|---|---|
| H200，N=64，缓存 50% | **27.3 tok/s** | 14.5 | 12.8 |
| H200，N=64，缓存 75% | **65.1** | 36.2 | 50.5 |
| H200，N=64，缓存 90% | **214** | 150 | 114 |
| H200，N=128，缓存 90% | **291**（p99 482 ms） | 193 | 147（p99 1153 ms） |

只有 N=16、缓存 75% 时，异步略好（45 对 42 tok/s）。**Q-H3 不成立。**

原因：
1. 同步时，N 个 token 同时到达第 l 层，缺的 expert 一次加载服务所有需要它的 token，这本身就是最好的攒批。异步后，同一个 expert 被需要的时刻分散开，每次加载服务的 token 更少，还更容易在两次需要之间被换出。
2. 加载通道一直满载，阈值 n 和等待上限 W 都不起作用。
3. 缓存大时（90%），异步方案反而卡在 GPU 上：每次心跳都要给多层各做一次小 batch 的 attention，固定开销累积起来超过收益。这里的 attention 用的是非融合实现，固定开销偏大；但即使去掉这部分，第 1 点仍然成立。
4. 提前 1 层预取在带宽受限时让加载量翻倍、吞吐减半，和 anchor P3 的结论一致。

### 8.4 同步框架下的两个变体（`outputs/moe/q1_sub.json`、`q1_pool.json`）

**冷门 expert 顶替（有损）**：本步需要某个缺失 expert 的 token 少于 n 个时，不加载它，这些 token 跳过这个 expert（剩下的重新归一）。H200，N=64：

| 缓存 | 同步 | 顶替 n=4 | 被跳过的 expert 使用 / 每 token 每层被跳过的路由权重 |
|---|---|---|---|
| 90% | 214 tok/s | 789（×3.7） | 1.2% / 0.012 |
| 75% | 65 | 562（×8.6） | 5.4% / 0.054 |
| 50% | 27 | 139（×5.1） | 14% / 0.14 |

能不能用，取决于准确率掉多少：Q3 在真实模型上测。

**按相似性挑请求（decode 池，见 `2026-10-21-moe-affinity-decode-pool-plan.md`）**：N=128，B=32，最多多等 2 步：

| 设置 | 轮流前进 | 用上一 token 预测着挑 | 用真实路由挑 |
|---|---|---|---|
| Mac，缓存 75% | 37.3 tok/s | 43.0（+15%） | 44.0（+18%） |
| Mac，缓存 90% | 89.7 | 98.2（+9%） | 101.8（+13%） |
| H200，缓存 90% | 164.8 | 182.5（+11%） | 187.9（+14%） |

### 8.5 结论

- "每个请求独立推进 + 每个 expert 一个队列"在带宽受限的 offload 下不划算。在这种情况下，**决定谁一起跑**（同步框架下按相似性挑请求）比**让每个请求独立跑**更有效。
- 想跨步攒批，只有两条路：故意让 token 多等（尾延迟变差），或者不等、用常驻 expert 顶替（有损）。后者的吞吐空间非常大，准确率是关键。
