# Plan：检索过程中流式预取 / 预算 KV，让 GraphRAG 的 prefill 和检索重叠

*Bowen · 2026-10-19 · 状态：计划阶段*

依据：

- NSF proposal 第 4 页（师兄的预研，A100）：CWQ 上不剪枝的多跳路径枚举，从 1 跳的 0.20 ms（82 条路径）涨到 4 跳的 1,139 ms（4,826 条路径），此时**检索占 CWQ 端到端延迟的 53.6%**；跨请求有 37–52% 的路径 prefill 是重复的。师兄提到的"约 90% 时间在检索"，proposal 里没有找到对应数字，需要向他确认设置。
- MoE 方向的结论（`report/2026-10-19-moe-edge-phase-a.md`）：检索信息很难指导 MoE 的 expert 调度。但**检索信息可以直接决定 KV**：检索出哪段内容，prompt 里就会有这段内容，它的 KV 就能提前准备。
- 本次讨论：RAG / GraphRAG 里有大量重复片段，位置不同；GraphRAG-Opt 已经做过"预先算 KV、最后拼接"，也可以借鉴 KVComm 维护偏移池。如果检索本身耗时可观，就可以"找到一条就预取或预算一条"，把 prefill 和检索重叠起来。

---

## 0. 为什么现在用的设置检索这么快

1. **RoG 的数据集自带每道题的子图**：每题主题实体周围几跳的邻域，作者离线从 Freebase 抽好了。运行时只是在内存里几千条边的小图上走，不是在完整的 Freebase 上查询。
2. **先规划、再沿规划走**：RoG 先用 LLM 生成关系路径规划，再用 `bfs_with_rule` 只沿规划的关系走。Phase 0.5 实测：落地约 0.2 ms，组装 prompt 约 1 ms；规划约 0.6 秒，但那是 LLM 在 GPU 上生成，不是图检索。
3. **我们的实验用的是预先算好的路径**（`precomputed_paths_v2`），运行时没有检索开销。

所以要研究"检索和 prefill 重叠"，就必须换到检索真正耗时的设置。

## 1. 目标场景（检索和生成接近五五开，且检索期间 GPU 空闲）

| 场景 | 数据集 | 检索耗时（文献 / proposal） | 检索期间 GPU | 用途 |
|---|---|---|---|---|
| **S-A：KG 上不剪枝或弱剪枝的多跳路径枚举** | RoG-CWQ、RoG-WebQSP、MetaQA-3hop；3–4 跳 | CWQ 4 跳约 1.1 s（proposal） | 空闲（CPU 图遍历） | **主场景**。师兄的设置；路径随遍历逐条出现 |
| S-B：文本图 RAG | HippoRAG 2 在 MuSiQue、2WikiMultiHopQA 上 | 约 2.4 s（GraphRAG-Bench）；只算图检索 10–120 ms（ISO-RAG） | 部分空闲（检索里有 LLM 抽实体） | 通用性：非 KGQA 的图 RAG |

## 2. 想法

```
检索（CPU 图遍历，逐跳产出路径）:  ──p1──p2────p3──p4──────p5──|
GPU（原本空闲）:                     [查池/预算 p1][p2]  [p3][p4]  [p5]|[拼接 + 问题 prefill]→ decode
```

1. **片段 KV 池**：以路径（或三元组、或"实体–关系"行）为单位，存与位置无关的 KV。池子分层：GPU / 统一内存 → CPU 内存 → SSD。按跨请求的热度（Zipf）管理。
2. **流式处理**：检索每产出一条路径：
   - 池里有：从下层存储预取到 GPU；
   - 池里没有：趁 GPU 空闲，立刻把这条路径单独 prefill 成片段 KV，同时放进池子。
3. **最后拼接**：检索结束后，按最终 prompt 的顺序拼接各片段的 KV；修正位置（对 RoPE 重新旋转到新位置）；处理片段之间缺失的 attention（选一部分 token 重算，参考 CacheBlend；或沿用 GraphRAG-Opt 的 trie / M2 结构）；最后只 prefill 问题部分，开始 decode。
4. **按遍历方向提前取**：图遍历的前沿可以预告"接下来大概会出现哪些路径"，在遍历真正走到之前就从池子里预取。

**和已有工作的区别：**

| 工作 | 做了什么 | 我们不同的地方 |
|---|---|---|
| RAGCache | 把检索出的文档 KV 存成知识树；向量检索还没结束时，就用中间结果推测式地开始生成，结果不对再重做 | 面对的是一次返回 top-k 的向量检索；我们利用多跳检索"逐跳产出片段"的特点，按路径粒度流式处理，不需要推测 |
| CacheBlend、TurboRAG、EPIC、KVLink、Block-attention | 同一段文本在不同位置时复用预先算好的 KV，部分重算 | 都在检索结束后才开始；我们和检索重叠，并且以 KG 路径 / 三元组为单位 |
| KVComm | 维护 anchor / 偏移池，跨上下文复用 KV | 借鉴它的偏移估计，用在路径片段上 |
| GraphRAG-Opt（本组） | 预先算好 KV，最后拼接；trie 结构的 attention | 在它的基础上加入"和检索重叠的流式预算 / 预取"和分层的 KV 池 |

## 3. 要验证的假设

| 编号 | 假设 | 判据 |
|---|---|---|
| **K-H1 检索够长** | 在 S-A（3–4 跳）中，检索和生成接近五五开，且检索期间 GPU 空闲 | 实测检索占端到端 30–70%；GPU 在检索期间的空闲时间 ≥ 同一请求 prefill 时间的 50% |
| **K-H2 片段会重复** | 跨请求有可观的片段复用 | 按到达顺序、给定池容量时，片段（路径或三元组）的命中率 ≥ 30%（proposal 测得 37–52% 的路径 prefill 重复；我们之前在 RoG cap 8 设置下测到 6–35%，S-A 下需重测） |
| **K-H3 首 token 延迟下降** | 流式预算 / 预取加最后拼接，明显降低首 token 延迟 | 相对"检索完再 prefill"降低 ≥ 30%；相对"检索完再用 CacheBlend / RAGCache 式复用"降低 ≥ 15% |
| **K-H4 准确率不掉** | 片段拼接（加部分重算）的准确率接近完整 prefill | Hit@1 / F1 下降 ≤ 1 pt |
| K-H5 存储代价可控 | 片段 KV 池的存储和预取带宽在端侧 / 单卡可承受 | 给出池容量、命中率、SSD 预取带宽三者的关系；预取比重算更省时的条件 |

## 4. 实验步骤

### K0：实测检索 / prefill / decode 的时间占比（约 2 天）

- 实现或复用检索流水线：
  - S-A：RoG 子图上 k 跳（k = 1…4）的简单路径枚举。最好直接用师兄的代码，以便和 proposal 的数字对齐；同时保留 RoG 规划 + `bfs_with_rule` 作为"快检索"的对照。
  - S-B：HippoRAG 2（MuSiQue、2Wiki），检索里的 LLM 步骤用本机的 MLX 模型。
- 生成：Mac 上用 MLX，至少一个 dense 模型（Qwen3-8B 或 Llama-3.1-8B）和一个 MoE 模型（Qwen3-30B-A3B）；H200 恢复后在 A100 / H200 上和 proposal 对齐。
- 记录：每个请求检索、prefill、decode 的耗时；GPU 在检索期间的空闲时间；**每条路径被检索产出的时刻**（到达曲线）。这决定了能重叠多少。
- 输出：K-H1 判定，以及选定后续用的设置（跳数、路径上限）。

### K1：片段复用分析（CPU，约 1 天）

- 在 S-A 和 S-B 的请求流上（按数据集顺序，以及按 Zipf 重放），统计三种粒度的复用率：三元组、路径、"实体–关系"行。
- 在不同池容量和替换策略（LRU、LFU、按频率常驻）下模拟命中率。
- 估算存储：每个 token 的 KV 大小 × 片段长度。例如 Qwen3-30B 约 98KB/token，一条 20 token 的路径约 2MB；从 SSD 读一条约 0.2 ms，对比重新 prefill 它的耗时，得出"什么时候预取比重算划算"。
- 输出：K-H2、K-H5 判定。

### K2：拼接的准确率（约 2–3 天）

- 对比几种方式：
  1. 完整 prefill（上限）；
  2. 直接拼接 + RoPE 重新旋转；
  3. 拼接 + 部分重算（CacheBlend 式，扫描重算比例）；
  4. GraphRAG-Opt 的 trie / M2 结构。
- 数据：CWQ、WebQSP、MetaQA（S-A），MuSiQue（S-B）；指标 Hit@1 / F1。
- 复用之前的结论：exp3 的跨 prompt 复用存在位置冲突的问题（见 10-15、10-16 的报告），arrow-recompute 是一种修补；这里重新在 S-A 的长上下文下验证。
- 输出：K-H4 判定，选出准确率和重算量的折中点。

### K3：重叠调度的模拟和原型（约 3 天）

- **模拟**：用 K0 的路径到达曲线、K1 的命中情况、K2 的重算比例，计算每个请求的首 token 延迟。
- **对比**：
  1. 检索完再完整 prefill；
  2. 检索完再做前缀缓存；
  3. 检索完再按 CacheBlend 式复用；
  4. RAGCache 式（检索结束后的文档级 KV 树 + 推测）；
  5. 我们的流式预算 / 预取 + 拼接。
- **原型**：在 MLX 上实现片段 prefill（给定位置偏移）、片段 KV 的拼接和 RoPE 重新旋转、部分重算，以及一个后台线程，在检索产出路径时就开始处理。在 Qwen3-8B 和 Qwen3-30B-A3B 上实测首 token 延迟。
- 输出：K-H3 判定。

### K4：分层 KV 池与提前预取（约 2 天，视 K1 / K3 结果）

- 池子放在 统一内存 → 内置 SSD 两层（Mac），或 HBM → 主机内存 → SSD 三层（H200）。
- 按图遍历的前沿，预测即将出现的片段，提前预取。
- 测量预取命中率、浪费的带宽，以及对首 token 延迟的额外收益。

### K5（可选）：和 MoE 结合

- 在 MoE 模型上，检索期间流式预算片段 KV，同时也会把这些片段用到的 expert 读进缓存。观察这对后面问题 prefill 和 decode 的 expert 命中率的影响。这是 MoE 方向里少数和检索直接相关的点。

```
K0（实测时间占比）──K-H1 成立──→ K1（复用率）──→ K2（拼接准确率）──→ K3（重叠调度：模拟 + 原型）──→ K4（分层池 + 预取）
        │
        └──检索不够长──→ 换设置（S-B / S-C / S-D），或把重点改成"复用"本身（不依赖重叠）
```

## 5. 风险

| 风险 | 应对 |
|---|---|
| "不剪枝的路径枚举"被认为是不现实的设置 | 同时报告 S-B（HippoRAG 2）等现成系统；说明不依赖 LLM 规划的有界检索（子图 / 路径类 GraphRAG）是一大类方法；K0 测多种跳数和路径上限，给出"检索占比随设置变化"的曲线 |
| 片段拼接掉准确率（位置冲突、缺失的跨片段 attention） | K2 系统比较几种修补方式；用部分重算控制掉点 |
| 复用率不够高 | K1 先量；按 Zipf 的真实请求流（proposal 里 MS MARCO 的实体访问分布）重放；粒度从路径降到三元组 |
| 和 RAGCache / CacheBlend 区分不够 | 把"逐跳流式、与检索重叠、按遍历方向提前取"做成核心，并在 K3 里直接和它们比 |
| H200 不可用 | K0–K3 先在 Mac 上做；和 proposal 的 A100 数字对齐的部分等 H200 恢复 |
| Mac 的 GPU 被 B 档采集占用 | K1 只用 CPU；K0 / K2 / K3 需要 GPU，排在 B 档之后或暂停 B 档 |
